# UCN V5-51 三节点 UART 静默检测十轮实测报告

> 状态：2026-08-13 三板 10 轮故障功能门禁通过。FAST UART 的 Core 判疑和同 Neighbor Wi-Fi Backup 接管闭环已在实机重复出现；本报告不把它解释为零丢帧、端到端可靠交付或硬实时保证。

## 1. 台架与证据

| 角色 | 节点 | 开发板 / 端口 | 物理连接 |
| --- | --- | --- | --- |
| A | `0x10000001` | ESP32-S3 / COM5 | UART0 RX/TX=`15/16`，连接 B UART0 |
| B | `0x10000002` | ESP32-S3 / COM34 | UART0 RX/TX=`15/16` 连接 A；UART1 RX/TX=`19/20` 连接 C |
| C | `0x10000003` | ESP-WROOM-32 / COM35 | UART0 RX/TX=`16/17`，连接 B UART1 |

- A—B、B—C UART 均为 `115200 bit/s`、基础 Cost 34、FAST=`250/1250/2000 ms`。
- 三板 ESP-NOW 同时在线，基础 Cost 45、存活档为 DEFAULT=`1000/3000/4000 ms`。
- 监测脚本一次打开 COM5/COM34/COM35，之后不重新开串口，避免串口监测动作触发板卡复位。
- 原始日志：`test_results/v5_51_liveness_20260813_011133.log`，持续约 467 s、1896 行；逐轮 CSV：`test_results/v5_51_liveness_rounds_20260813.csv`。
- 分析入口：`scripts/v5_liveness_analyze.py`，正式轮次从 Core 时间 `364000 ms` 后开始识别。

第 1 轮断开时间明显长于标准动作；第 2～10 轮按约 5 s 断开、约 8 s 恢复执行。因此第 1 轮用于状态机闭环，但比较固定动作下的业务缺口时单独列出。

## 3. 验收判断

| 项目 | 实测 | 判断 |
| --- | --- | --- |
| 故障状态机 | A、B 各 10 次 `SUSPECT` 和 10 次 `DOWN`；C 为 0 | 10/10 动作完整，无额外假阳性 |
| Backup 接管 | 每轮 UART Primary 在 SUSPECT 时让位给 Wi-Fi；A/B `bearer_quality_switches` 均净增 10 | 通过 |
| Route 收敛 | 9/10 轮 Route 事件在 0～16 ms 内出现；第 10 轮约 1 s | 最大 1 s；该轮业务仍只缺 1 个离散序号 |
| 恢复 | 10/10 最终恢复 UART Primary；最终 A↔C 为 2 Hop、Cost 68，B 两条直连均 Cost 34 | 通过 |
| 业务缺口 | 全 10 轮 A 端 11 个、C 端 13 个；标准第 2～10 轮分别 9 个和 11 个 | 仍非零丢帧，但每个方向最大连续缺口均为 1 |
| 重复/乱序 | 467 s 内 A/C 边缘序列分别观测 297/300 帧；重复 0、倒序 0；Core `dup=0` | 通过 |
| 业务提交 | 三板 Ping Request/Reply 的 rejected 字段始终为 0 | 通过 |
| 稳定性 | 日志内 BOOT、Panic、Exception、Watchdog 均为 0 | 通过 |
| UART Carrier | 四个 UART 口的 decode/length/overflow/noise/no-space/partial 始终为 0，RX Queue `dropped_full=0` | 通过 |

第 2～10 轮固定动作下，A→C 方向对应 C 端 11 个缺口；与 V5-50 九轮 A→C 的 26 个缺口相比，当前台架的离散缺口减少约 57.7%。两批人工插拔时间并非严格同步仪器触发，因此这个比例只作为同台架趋势，不作为统计学或产品 SLA。

Adapter Queue 的 `rejected_by_core` 在 A/B-uart0/C 分别增加 40/4/48；`dropped_full` 始终为 0，Ping 提交拒绝也为 0。该字段表示完整 Carrier 帧已入队、随后被 Core 的控制面/准入/重复等规则拒绝，不是 RX Queue 溢出，也不能当成业务缺口计数。

| B | 4133 | 4058 | 8116 | 142 ms | 310648→310648 B | 309564 B | 5036→4972 B |

三板合计新增 Heartbeat Request 8254 个，约 17.75 request/s；这是两段双向 FAST UART 在断线窗口内自然减少后的实测控制帧率。最大维护延迟 142 ms，满足 FAST `250 ms` 调度和 `1250 ms` 判疑窗的当前台架余量。Internal Heap 无下降趋势，栈高水位无持续恶化。

当前 Bench 未启用 FreeRTOS Run-Time Stats，因此只有调度延迟、Heap 和栈余量，没有可发布的 CPU 利用率百分比。CPU、功耗及不同业务负载下的绝对资源标定继续归真实 Adapter/目标板资源任务，不能由本次 Heartbeat 延迟反推成精确 CPU%。

## 5. 观测边界与后续

10 轮中 17/20 个端点的 Adapter 代理年龄为 1248～1249 ms；其余为 1104、1166、1312 ms。这不是 Core 提前或延后判疑的直接证据：UART Adapter 在 Carrier/COBS 完整时记录 `last_valid_rx_ms`，Core 只有在协议解码、安全、准入、重复与控制预算门禁后才刷新 `bearer.last_seen_ms`。当前软件专项测试已直接证明 Core 在 1250 ms 判疑、2000 ms Down；本次实机证明 10 次真实物理静默均完成主备切换。

若发布门禁要求“每一轮都从板端直接打印 Core `last_seen_ms` 到判疑的精确差值”，下一版 Bench 应同时打印 Adapter 和 Core 两个时间源，再做短轮次观测确认；这属于诊断可观测性增强，不改变本轮协议功能结论。

最终结论：V5-51 的**三板十轮故障功能门禁通过**，将 V5-50 的约 2.5 s 静默窗口压缩到 FAST 1.25 s 级别，并保持固定资源、Wire 不变和同 Neighbor Backup 自动接管。它仍不提供断线瞬间零缺口、端到端 ACK/重传或 CPU/功耗绝对指标。
