# 阅读方法、边界与路线图

## 1. 先明确“Core”到底指什么

UCN 的 Core 不是只有 `src/core/`。当前 `ucn_core` 静态库由 CMake 组合以下层次：

```text
Foundation
  core/ucn_core.c
  core/ucn_endpoint.c
  core/ucn_frame.c
  core/ucn_link_cost.c

Transport
  transport/ucn_adapter.c
  transport/ucn_event_runtime.c
  transport/ucn_standard_adapter.c
  transport/ucn_protocol_owner.c

Carrier Source
  adapters/stream/ucn_stream_source.c
  adapters/can/ucn_can_source.c

Node
  Nano: node/ucn_node_nano.c
  Lite/Full: node/ucn_node.c
  Nano/Lite: node/ucn_profile_stubs.c

Routing
  Full only: routing/ucn_path.c + routing/ucn_policy.c

Service（独立开关）
  service/ucn_service.c + service/ucn_service_bridge.c
```

因此可以把运行时核心理解为：

```text
业务 API
   ↓
Service（可选）
   ↓
Node：协议状态唯一 Owner
   ↓
Frame / Route / Path / Policy
   ↓
Link
   ↓
Adapter / Source / 产品驱动
```

`src/core/` 是基础层，不是完整协议状态机；真正决定入网、选路、发送、转发和维护行为的是 Node 层。

本目录的“全部函数”严格以 `CMakeLists.txt` 中组成 `ucn_core` 静态库的源文件为边界。以下代码与 Core 有关系，但不计入 Nano/Lite/Full Profile 本体：

- `src/ports/`：由具体裸机或 RTOS 产品另外选入的调度/临界区适配；
- `src/extended/ucn_transfer.c`：建立在 Core 消息之上的可选大消息 Transfer；
- `src/extended/ucn_cluster*.c` 与 `src/extended/cluster/`：建立在 Core 之上的独立 Cluster 控制体系；
- `tests/`、`tools/` 和板级 Driver：验证或集成代码，不是 `ucn_core` 运行时实现。

这样划界以后，阅读 Profile 时不会把“核心转发能力”“大消息服务”“簇控制面”和“操作系统适配”混为一套状态机。

## 2. 三种 Profile 的关系

| Profile | Node 实现 | Dynamic Mesh | Security | Candidate | Path/Policy | 高级诊断 |
| --- | --- | --- | --- | --- | --- | --- |
| Nano | `ucn_node_nano.c` | 否 | 否 | 否 | 否 | 否 |
| Lite | `ucn_node.c` 条件裁剪 | 是 | 是 | 否 | 否 | 否 |
| Full | `ucn_node.c` 完整分支 | 是 | 是 | 是 | 是 | 是 |

三档共享同一 Wire W0～W3 Decoder。Build Profile 表示“本地编译进了哪些能力”，不是 Wire 地址宽度等级。

### 为什么先读 Nano

Nano 只有一条直接/静态路由视图，Node 主流程短，适合认识：

- Node 初始化；
- Link 注册；
- 静态 Route；
- Frame 编解码；
- Endpoint 分发；
- Q0/Q1 固定队列；
- 中继时 Hop 递减。

理解 Nano 后再读 Lite，可以把新增复杂度归因到“动态邻居和路由”；最后读 Full，可以把新增复杂度归因到“多候选、Path、Policy、负载均衡和诊断”。这比直接面对 Full 的几百个函数更容易建立因果关系。

## 3. 每个函数的六步阅读法

对任一公共函数，都按以下顺序记录：

1. **入口合同**：谁能调用，任务上下文还是 ISR；
2. **参数域**：NULL、ID、长度、枚举、容量和时间是否合法；
3. **读取状态**：依赖 Node、Link、Route、Session 中的哪些字段；
4. **状态写入**：成功前后改变了什么；
5. **下游调用**：进入 Frame、Link、Provider、回调还是 Queue；
6. **失败结果**：错误码、输出是否不写回、状态能否重试。

建议使用下面的简表做笔记：

| 函数 | 调用上下文 | 参数合法域 | 读取状态 | 写入状态 | 下游 | 失败是否不写回 |
| --- | --- | --- | --- | --- | --- | --- |
| `ucn_node_receive` | Owner | 注册 Link、完整 Buffer | Profile、Security、Route | 去重/邻居/路由/统计 | handler/forward | 分阶段核对 |

## 4. 阅读顺序

### 第一轮：只建立地图

1. `CMakeLists.txt` 的 `UCN_*_SOURCES`；
2. `include/ucn/ucn_profile.h`；
3. `src/README.md`；
4. `docs/calltree/index.yaml`；
5. 三档 `ucn_node_t` 条件字段。

第一轮不要判断实现好坏，只回答：这个能力在哪一层、由哪个对象持有、在哪个 Profile 编译。

### 第二轮：公共基础合同

按顺序阅读：

```text
ucn_types.h
  → ucn_config.h
  → ucn_profile.h
  → ucn_time.h
  → ucn_frame.h / ucn_frame.c
  → ucn_link.h
  → ucn_adapter.h
```

这一步重点理解 ID、错误码、时间回绕、Frame、MTU、Link Ops 和固定队列所有权。

### 第三轮：单一 Profile 主链

对选择的 Profile 只追三条链：

```text
TX：send_endpoint / enqueue → send → Frame → Link.send
RX：Adapter pump → node_receive → Decode → Forward/Endpoint
STEP：Owner step → Node step → Queue/Timer/Route maintenance
```

不要在第三轮展开每个控制帧 handler；先知道控制帧在 RX 总入口的哪个阶段被分派。

### 第四轮：控制面和异常路径

按 HELLO、Heartbeat、RREQ、RREP、RERR、Path、Diagnostic 的顺序逐族阅读。每一族同时检查：

- 结构校验在状态写入之前；
- 来源与 Session 是否绑定；
- Token/预算在什么时机消耗；
- 重放、重复、旧 Epoch 和错误长度如何拒绝；
- 表满、Link Down、超时后如何恢复。

### 第五轮：测试反推审计缺口

测试不是结论，而是已有问题集合。对每个测试再问：

- 有没有只测成功，没测相邻失败值；
- 有没有只检查首尾字节，没有检查完整输出；
- 有没有 parser 和 builder 同时写错仍能 round-trip；
- 有没有只测 `deadline - 1`，没测 `deadline` 和回绕；
- 有没有检查返回码，但没检查对象逐字节不变。

## 5. 源码定位命令

在仓库根目录可使用：

```powershell
# 找定义
rg -n "^ucn_result_t ucn_node_receive" src include

# 找所有调用点
rg -n "\bucn_node_receive\(" src tests

# 找一个 Profile 的条件编译区域
rg -n "UCN_FEATURE_|UCN_PROFILE" src/node/ucn_node.c

# 找一个结构字段的所有读写位置
rg -n "authority_active|route_epoch|next_attempt_ms" src tests
```

判断调用顺序时，不要只搜索函数名；还应检查函数指针，例如 `link->ops->send`、Security Provider、Endpoint handler 和 Source `service()`。

## 6. 阅读完成标准

当你能不看文档回答下面问题时，才算真正理解一个 Profile：

1. 一帧从任务到驱动经过哪些对象；
2. 收到一帧后，哪些校验先于任何状态写入；
3. 没有 Route、Link Down、Queue Full 分别返回什么；
4. `step(now_ms)` 不执行会停止哪些能力；
5. 当前 Profile 哪些 API 是原生实现，哪些只是明确失败 Stub；
6. 一个远端帧怎样被转发，为什么不会投递给本机业务任务；
7. 哪些状态只能由 Protocol Owner 修改；
8. 当前测试覆盖了哪些边界，仍缺哪些实机证据。
