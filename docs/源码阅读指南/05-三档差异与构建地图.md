# 三档差异与构建地图

## 1. Build Profile、Wire Profile、Service 是三件事

| 概念 | 决定什么 | 当前取值 |
| --- | --- | --- |
| Build Profile | 本地编译进哪些状态和功能 | Nano/Lite/Full |
| Wire Profile | 一帧字段宽度和可表达范围 | W0/W1/W2/W3 |
| Service Feature | 是否链接任务 Router/Bridge | ON/OFF，独立于 Build Profile |

Nano 可以保留 W3 RX；Full 也可以用 W0 发送。不能从 Wire 档推断对方编译了 Path、Policy 或 Security。

## 4. 公共 API 为什么三档都能编译

`ucn_node.h` 对公共函数采用统一声明。这样上层业务可以用同一套头文件，但能力必须在运行结果中明确区分：

```text
Full-only修改API  → Nano/Lite返回 UCN_ERR_CONFIG
Full-only查找API  → Nano/Lite返回 NULL
Full-only布尔更新 → Nano/Lite返回 false
Full-onlyvoid维护 → Nano/Lite无状态写入
```

这是“源码可链接”，不是“功能自动兼容”。应用如果忽略返回值，仍可能在低档产品上产生逻辑错误。

## 5. Node API 原生实现差异

### Nano 原生主干

- Wire/Profile/Session 基础配置；
- Link 注册；
- 静态 Route；
- Handler；
- send/send_endpoint/enqueue/step/receive/stats。

Neighbor、Discovery 和 Security 函数在 `ucn_node_nano.c` 中保留统一入口，但明确返回不支持；高级 Path/Policy/Diagnostic 在 Stub 文件中。

### Lite 原生新增

- Security 全部配置和 Provider 边界；
- Join Policy、Neighbor observe/probe/HELLO/admit/reject；
- Neighbor summary；
- Route Constraints/Quality；
- discover/refresh/pending；
- 动态控制帧收发和维护。

### Full 原生新增

- 四类管理 Authorizer；
- Path 安装/撤销/发送/查询；
- Route Policy、Policy Path、Q1 Flow；
- Link Quality/Policy Stats；
- Path Trace、Node Snapshot、Policy Diagnostic。

## 6. 对象布局差异

`ucn_node_t` 的存储布局随 Profile 和容量宏变化。公共头要求所有翻译单元使用完全相同的：

```text
UCN_PROFILE
UCN_FEATURE_SERVICE
UCN_MAX_LINKS / ROUTES / NEIGHBORS / ...
产品覆盖配置头
```

否则可能出现“应用按 Nano 大小分配，库按 Full 布局访问”的严重内存破坏。运行中的 `ucn_node_t` 也不能在不同 Profile 库之间复制或持久化复用。

## 7. 构建命令

建议为每档使用独立目录：

```powershell
cmake -S . -B build_read_nano -DUCN_PROFILE=NANO -DUCN_BUILD_TESTS=ON
cmake --build build_read_nano --config Debug

cmake -S . -B build_read_lite -DUCN_PROFILE=LITE -DUCN_BUILD_TESTS=ON
cmake --build build_read_lite --config Debug

cmake -S . -B build_read_full -DUCN_PROFILE=FULL -DUCN_BUILD_TESTS=ON
cmake --build build_read_full --config Debug
```

检查 Service 边界时再单独构建：

```powershell
cmake -S . -B build_read_full_nosvc `
  -DUCN_PROFILE=FULL -DUCN_FEATURE_SERVICE=OFF -DUCN_BUILD_TESTS=ON
```

## 8. 人工比较一个函数的办法

以 `ucn_node_send_endpoint()` 为例：

```text
Nano
  endpoint → ucn_node_send → 直连/静态Route → Link

Lite
  endpoint → 自动活动Route → 当前Primary Bearer → Security → Link

Full
  endpoint → Route Policy
           → Pinned / Failover / Auto Best / Auto Balance
           → Path或Route → Security → Link
```

再以 `ucn_node_receive()` 为例：

```text
Nano
  普通Frame + 静态转发；控制/安全/Path/诊断拒绝

Lite
  增加Security、HELLO/Heartbeat、RREQ/RREP/RERR

Full
  再增加Candidate Probe、Path Control/Forward和Diagnostic
```

比较时不要只比较函数是否存在，而应比较：条件编译保留了哪些分支、结构体多了哪些表、Step 多维护了哪些状态、测试 target 实际启用了什么宏。

## 9. 审计 Profile 裁剪的必查项

1. 公共头的 Feature 依赖关系是否合法；
2. 低档静态库是否仍导出无条件声明的符号；
3. Stub 是否明确失败且无状态写入；
4. Full-only Frame 在低档 RX 是否 fail-closed；
5. Service OFF 时公共对象布局和调用点是否一致；
6. 默认产品 archive 是否意外包含实验组件 object/symbol；
7. Full/Lite/Nano 是否各自运行公共头链接测试；
8. 资源报告是否来自相同容量宏，不能只比较 Profile 名称。

## 10. 选档阅读建议

- 想最快理解协议骨架：Nano → Lite → Full；
- 产品只用固定 CAN/UART：重点 Nano + 公共基础层；
- 产品需要自动入网：重点 Lite 的 Neighbor/Route/Security；
- 产品有多介质和指定路径：重点 Full 的 Candidate/Path/Policy；
- 做全仓库安全审计：三档都审，尤其要审 Full-only API 在 Lite/Nano 的 Stub 行为。
