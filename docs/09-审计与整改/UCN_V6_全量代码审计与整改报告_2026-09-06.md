## 2. 审计方法

逐层复核顺序为：Config/Types → Wire → Identity/Bootstrap → Security → Capability → Route →
Message Journal → Owner → QoS/Metric → Transfer → Realtime → Cluster → Adapter/FreeRTOS。
每层检查以下问题：

1. 公共输入合法域、负枚举、保留值与拒绝不写回；
2. 父代际、Session/Capability/Route/Path 当前性与失效扇出；
3. 状态机终态、重放、timeout、整数溢出和 deadline 半开边界；
4. Provider/Driver 回调前重入门及任务/ISR 所有权；
5. 固定容量、表满策略、不可驱逐状态和无动态分配；
6. Wire/AAD、Hop/E2E 安全域与原始 Principal 授权；
7. Profile、Feature-Off、默认 archive 和安装 consumer 隔离。

机械与动态手段包括 Windows GCC/MSVC、WSL GCC/Clang、ASan/UBSan、`-fanalyzer -Werror`、
clang-tidy、cppcheck、Valgrind 和定向并发检查。TSan 二进制可构建，但当前 WSL runtime 在进入
测试前以 `unexpected memory mapping` 退出，因此该项只记录为环境限制，不能算 PASS。

## 3. V6X-S16 / P1：16-bit 标识符域不统一

### 3.1 原问题

Message、Security、Capability、Owner、Transfer Path Reference、Realtime 与 Cluster Tunnel 已把
`UINT16_MAX` 当作无效哨兵；但 Wire Message/Path Context、Adapter Link 注册、Bootstrap Link、
Transfer Credit、Metric Path 和 Cluster Directory 仍只拒绝零。结果是同一个值可通过前层
canonical 校验，却在后层永久不可消费。例如 Link 65535 可以注册到 Adapter，但不能建立
Security Session；Path 65535 可以进入 Wire，却不能安装 Capability/Route。

### 3.2 整改

在 `ucn_v6_types.h` 冻结三类公共上限：

```text
Endpoint ID      1..65534
Link Instance ID 1..65534
Path ID          1..65534
0                absent/unbound
65535            invalid/exhausted sentinel
```

Wire、Bootstrap、Adapter 及四类参考配置、Security transcript、Route、Metric/QoS、Transfer、
Realtime 与 Cluster Directory 均在自身入口独立复核。Protocol Opcode 保持独立命名空间，不
错误套用这条规则。测试覆盖 Wire 三类拒绝、Bootstrap 精确 Link、Adapter 配置、Transfer
Credit、Route/Metric、Realtime Policy 与 Directory 编码，并验证拒绝不写回。

## 4. V6X-S17 / P1：Adapter 跨 Link 队首阻塞

### 4.1 原问题

旧 `service_tx()` 先从全局 TX 表选择最早的 `QUEUED` 项，再检查该项所属 Link 是否 READY。
若 Link A 在排队后变为 Offline/Faulted，调用会持续命中 A 并返回 `UCN_V6_ERR_STATE`；Link B
即使 READY 且已有待发项也永远得不到提交机会。一个故障 Bearer 因而可以阻塞整个多 Bearer
节点。

### 4.2 整改

调度改为在所有结构合法的 `QUEUED` 项中，只从 READY Link 选择全局最早项。正常 Offline/
Faulted 项保留给显式取消或 reopen 回收，但不参与当前发送；若没有 READY 项则返回
`UCN_V6_OK + submitted=false`。队列引用不存在 Link 或错误 Generation 仍说明 Owner 内部
不变量损坏，此时设置 fault 并失败关闭，不能被当成普通断链静默跳过。

定向回归按 `enqueue A → enqueue B → A offline → service` 构造，要求 B 首次调用立即提交、
A 的 Driver 零调用，第二次无 READY 项只报告零进度。

## 5. V6X-S18 / P2：测试读取未初始化备用字节

Identity 的 caller-owned Opaque Storage 容量可以大于当前私有对象大小，初始化只承诺写入
实际对象，不承诺清零调用方全部备用容量。若测试未初始化整个 Storage 却对整块 union 做
`memcmp`，Valgrind 会正确报告未定义字节参与比较。Security 测试也曾保存并比较完整编码
数组，而有效编码长度之外的尾部未初始化。

整改只修改测试：所有参与整块比较的 Opaque Storage 和编码数组先显式清零。产品代码没有
为了迎合测试而额外清零未承诺的调用方容量，避免掩盖真实所有权合同。

整改后的最终工作树通过以下门禁：

- Windows GCC 14.2 八配置全部通过：Full Debug `26/26`、Full Release `26/26`、Lite Debug
  `26/26`、Nano Debug `26/26`、Nano Feature-Off `21/21`、Realtime-Only `22/22`、
  Cluster-Only `24/24`、Adapter-Only `22/22`；
- MSVC 19.51 Full Debug `/W4 /WX`：`26/26`；
- WSL GCC 13.3 ASan/UBSan：`27/27`；GCC `-fanalyzer -Werror`：`27/27`；
- WSL Clang 18.1.3 Full Debug：`27/27`，工程既有严格警告门保持通过；
- Valgrind 3.22 对 16 个 `ucn_v6_*tests` 可执行文件逐一运行，`16/16` 无泄漏、
  越界或 undefined-value 错误；
- 1k/10k Scale、安装 consumer、旧源码与移除 CMake surface denylist、当前文档门、API
  索引和公开聚合头均包含在上述 CTest 并通过；
- `git diff --check` 无空白错误，仅报告工作树既有的 LF/CRLF 转换提示。

cppcheck 与 clang-tidy 的补充扫描未产生经源码复核后成立的新缺陷。TSan 测试二进制可以
构建，但当前 WSL runtime 在执行测试前以 `ThreadSanitizer: unexpected memory mapping` 退出，
故不计为通过；已有 Adapter pthread 并发回归在 GCC/Clang、ASan/UBSan 和 Valgrind 下通过。

最终软件自审结论：`V6X-S16/S17/S18 = IMPLEMENTED / SELF-REVIEW PASS / WAIT EXTERNAL`。
本结论不替代真实 MCU、ISR/DMA、掉电、物理 Bearer 与长期并发验证。
