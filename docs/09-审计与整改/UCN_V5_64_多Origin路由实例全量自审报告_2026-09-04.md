# UCN V5-64 多 Origin 路由实例全量自审报告

> 审计日期：2026-09-04
> 审计对象：当前未提交工作区，相对 `main@0f8738e`
> 结论：Host 软件范围自审通过；按用户要求暂缓单项外审；多板实机未验证
> Wire：Core Wire v5 未改变
> Storage：Node Storage Layout 8 → 9 → 10 → 11

## 1. 审计目标

V5-64 要关闭的问题不是“能否找到一条到 Destination 的路”，而是多个业务 Source 同时经过共享中继访问同一 Destination 时，Route Epoch、Candidate、RERR 和旧 Epoch Grace 是否仍属于正确的业务方向。

本轮冻结以下不变量：

```text
DynamicRouteKey = (traffic_origin, destination)
CandidateKey    = (traffic_origin, destination, candidate_id)
StaticRouteKey  = (0, destination)  // explicit wildcard
```

不同 `traffic_origin` 的 Request ID、Route Epoch、Current/Previous、Cost、Expiry 和 Candidate 不能比较、合并或相互失效。

## 2. 分项自审

### R01｜Route 实例键与查表方向

结果：PASS。

- 动态 Route 新增 `route_origin`；精确查找要求 Origin 和 Destination 同时匹配；
- 本地发送使用 `(local_node,destination)`；中继业务使用 `(frame.source,frame.destination)`；
- 静态 Route 以 `route_origin=0` 表示 Destination 通配，并保持直连 Link 优先；
- Route Epoch 接收验证只在同一二元键内接受 Current 或尚未过期的 Previous。

区分度：若恢复旧的 Destination-only 查找，A/B 共享目标测试会出现表项覆盖、伪造 Epoch 被接受或其中一个 Source 无法交付。

### R02｜RREQ Reverse 与 RREP Forward 所有权

结果：PASS。

对于 `A→T` 发现：

```text
RREQ 沿途学习 (T,A)  // T 发回 RREP/控制消息时使用
RREP 沿途学习 (A,T)  // A 发送业务时使用
```

目标生成 RREP 时从 `(T,A)` Reverse Route 取得对应 Epoch；中继收到 RREP 后只更新 `(A,T)`。不同 Origin 的 RREP 即使交叉到达，也不覆盖另一实例。

### R03｜Candidate/Probe/Activate 分域

结果：PASS。

- Candidate 身份已扩为 `(route_origin,destination,candidate_id)`；
- Probe/ACK/Activate/Activate ACK 按消息方向选择对应 Candidate；
- A/B 可在共享中继同时使用相同 `candidate_id`；
- 新增内部防护：只有 `originated_here` 且 `route_origin == local node` 的 Candidate 才能触发本机主动 Probe/Activate。

自审额外发现并关闭一个跨域 Grace 边界：Candidate 激活在 Route 表中复用“已过期但 `valid` 仍为 true 的其他 Origin 槽”时，旧实现会把外域 Epoch 复制为新实例的 Previous。当前只在确实找到同域、未过期的活动 Route 时建立 Previous；复用空槽或过期槽一律清空 Previous。定向反例固定外域 Epoch=9、新域 Epoch=10，断言激活后 Previous 无效。

### R04｜RERR 单域撤销

结果：初审发现缺陷，整改后 PASS。

缺陷：普通控制转发原本可以直接使用 `frame.source` 查 Route，但 RERR 的 Source 是检测故障的中继 X，不是原业务目标 T。A→T 发现建立的是 `(T,A)` Reverse Route，不保证存在 `(X,A)`，因此旧写法会让 RERR 在中间节点找不到回程实例。

整改：RERR 转发先严格解析 Payload word 0 的 `unreachable_target`，用：

```text
route_origin = unreachable_target
destination  = original traffic origin
```

RERR 到达 Origin 后只失效 `(origin,unreachable_target)` 的 Route/Candidate。本轮五节点回归确认 A 域撤销后 B 域仍可交付业务。

### R05｜表满与固定内存

结果：PASS。

- 没有增加堆分配；
- `UCN_MAX_ROUTES` 现在限制 Route Instance 数，不是不同 Destination 数；
- 无空闲/过期槽时返回 `UCN_ERR_NO_SPACE`；
- 不覆盖任一有效 Origin 实例；
- `route_instance_table_full` 饱和统计满载；
- 反例用静态 Route 填满整表，再注入新 Origin 的合法 RREQ，断言整表逐字节不变。

### R06｜诊断、Profile 与兼容边界

结果：PASS。

- 新增只读 `ucn_node_copy_route_summaries()`，导出 Origin、Destination、Link、Hop、Cost 和 Current/Previous Epoch；
- Lite/Full 返回动态 Origin；Nano 静态 Route 返回 Origin 0；
- Core Wire v5、RREQ/RREP/RERR Payload 和 Cluster Record 均未改变；
- Node Storage Layout 升为 9，要求库与应用全量重编；
- Nano 不包含动态 Mesh，节点大小不变。

### R07｜测试工具与辅助遍历

结果：PASS。

动态压力和规模模拟中直接遍历 Route 的逻辑已携带 `route_origin`，测试 fixture 中手工构造的动态 Route 也显式写入本地 Origin。这样工具不会用零值或 Destination-only 假设掩盖生产代码错误。

### R08｜低资源产品的 Cluster Scale 容量门禁

结果：初审发现测试注册缺口，整改后 PASS。

额外 Product128 构建把固定容量限制为 `UCN_MAX_LINKS=3`、`UCN_CLUSTER_MAX_PEERS=4`、`UCN_CLUSTER_MAX_MEMBERS=6`。八节点一组的 Cluster 模拟需要每个节点看到 7 个 Peer，超出该产品合同；模拟器拒绝初始化是正确行为，旧 CTest 却把它误报成协议失败。

整改后：

- 模拟器在 `group_size - 1` 超过 Peer 或 Member 固定容量时输出明确的 `skipped=capacity`；
- 只对这种已识别容量不支持返回专用退出码 77；非法参数和真实初始化失败仍返回失败；
- Cluster Scale CTest 识别退出码 77 为 Skip，不吞掉其他错误；
- Product128 的 group=2/4、Scale capacity/address-limit 与端到端用例仍实际执行。

这项整改不扩大低资源产品能力，只保证测试报告能区分“拓扑不受该产品容量支持”和“协议实现失败”。

### R09｜外审 V564-A01：静态通配与动态 Epoch

结果：外审问题属实，整改后自审 PASS。

旧查找虽然识别静态 Route，却仍要求其固定 Epoch 0 等于业务帧携带的动态 Epoch，导致
“动态 Origin → 静态中继 → 静态目标反向 Route”黑洞。现在动态项仍严格按
`(origin,destination,epoch)` 检查，静态项则只在没有动态匹配时作为不参与 Epoch
所有权的明确 fallback。

新增三节点生产路径回归：源端动态 Route 携带 Epoch 7，中继和目标只配置静态 Route；
业务必须完整交付，转发帧仍保留 Epoch 7，且不产生 RERR 或 Epoch rejection。
外审原探针在当前生产库上重新编译后输出
`result=0, origin_business=1, static_egress_business=1, relay_route_errors=0`。

### R10｜外审 V564-A02：PATH_ACTIVATE 原子激活

结果：外审问题属实，整改后自审 PASS。

旧顺序会先写 Reverse、再发送下游、最后写 Forward，容量或发送失败可留下半提交。
当前改为 `prepare_candidate_activation()` 与 `commit_candidate_activation()` 两阶段：

- 中继在零写入状态下同时预检双向 Candidate、Profile、Epoch、Link 和两个不同 Route 槽；
- 任一预检失败时不写 Route、不删除 Candidate、不发送控制帧；
- 全部通过后先同时提交双向 Route，再允许外部发送，以支持同步递归 ACK；
- 下游发送失败时恢复双向 Route 快照；目标 ACK 发送失败时恢复目标反向 Route；
- Candidate 保留到有界过期，用于重试；精确已激活事务不再次写入或重复计数。

定向反例覆盖：只剩一个 Route 槽、下游 `LINK_DOWN`、目标 ACK `NO_SPACE`、失败后成功
重试，以及成功后的重复 Activate。所有失败路径的 Route/Candidate 均逐字节核对。
外审容量探针重编译后输出
`result=-3, sends=0, reverse=0, forward=0, table_full=1, reverse_candidate=1, forward_candidate=1`。

### R11｜外审 QA-A03：非 ASCII 构建路径

结果：外审问题属实，整改后自审 PASS。

不再通过编译命令行宏传递源目录/构建目录的 UTF-8 绝对路径。CMake 在 configure 阶段把
已提交 golden 复制为构建目录中的 ASCII 文件名，CTest 明确把该构建目录设为工作目录；
测试只打开 `cluster_golden_reference.txt` 与 `cluster_golden_actual.txt`。维护模式仅生成
候选 actual，要求人工审阅后复制回源码 golden，避免测试静默改写基线。

最终在全新的“中文源码目录/中文构建目录”副本中配置、构建并运行 Full `58/58`，证明
不是仅靠 ASCII 工作区绕开问题。该门禁使用 Ninja；本机 MinGW Makefiles 生成器不能
可靠处理中文源码根路径，报告不把生成器边界表述为 UCN Runtime 失败。

### R12｜外审 V564-A04：Activate ACK 精确事务绑定

结果：外审问题属实，整改后自审 PASS。

旧实现用 ACK Payload 中的 Epoch 直接执行 Candidate 激活，没有证明该 Epoch 就是发起端
实际发送的事务。当前 ACK 在任何 Route/Candidate/统计写入前同时验证：

- Candidate 属于 `(local_origin,ack_source,candidate_id)`；
- `originated_here=true`；
- Probe 发送数与匹配 ACK 数均达到门限；
- Activate 至少尝试并成功提交过一次；
- Candidate 已绑定非零 Epoch，且与 ACK Epoch 精确相等；
- Wire Profile 一致且 ACK 尚在总截止期内。

首次合法 ACK 安装 Route 并进入 ACKED；精确重复 ACK 只有在同一活动 Route 仍存在时才
幂等成功，不能复活已过期/撤销 Route。中继和目标的 Candidate 也在首次 Activate Commit
时绑定 Epoch，换 Epoch Activate 在预检阶段零写拒绝。回归对错误 Epoch、未发送、Probe
未完成、非本地 Candidate 和中继改绑分别快照 Route、Candidate 与 Stats，确认失败不写。
旧 A04 探针重编译后由 `result=0/installed_epoch=9` 变为
`result=-16/installed=0/switches=0`，原漏洞断言退出码变为 1。

### R13｜外审 V564-A05：Activate ACK 丢失有界恢复

结果：外审问题属实，整改后自审 PASS。

发起端 Candidate 新增 `activation_attempts`、`activation_ack_deadline_ms`、
`next_activation_retry_at_ms` 和 `activation_acknowledged`。默认合同为：

```text
总 ACK Deadline = 1000 ms
重试间隔        = 250 ms
最大重试次数    = 3（初发之外）
最大总发送次数  = 4
```

每次重发保留 Candidate ID、Route Epoch、Destination 与 Wire Profile，由正常控制发送路径
分配新的外层 Sequence。ACKED 后不再发送；最后一次重试仍保留一个完整间隔供 ACK 到达。
重试耗尽或总 Deadline 到达时清 Candidate、增加耗尽统计并返回 `UCN_ERR_EXHAUSTED`，已
存在的旧 Active Route 不改变。配置头、Header fallback 和用户覆盖合同已同步；持续丢 ACK
回归观察到 4 个相同事务身份、4 个不同 Sequence，并在 1000 ms 清除 Candidate。旧 A05
探针不再得到“整个 Candidate 生命周期仅发送一次”，而在 1001 ms 收到明确 Exhausted。

### R14｜外审 V564-A06：Candidate 路径快照不可变

结果：外审问题属实，整改后自审 PASS。

旧实现允许同 `(origin,destination,candidate_id)` 的更低 Cost RREP 直接改写 Candidate 的
`egress_link/route_cost/hop_count`，却保留旧 Probe、RTT、Epoch、Activate 和 ACK Deadline，
使路径 A 的 ACK 可以错误提交路径 B。

当前 `candidate_route_transaction_is_frozen()` 统一识别 Probe 已开始、RTT 已验证、Epoch 已
分配、Activate 已尝试/发送/确认或 ACK 定时器已建立等状态。冻结后：

- 路径字段不同的同 ID RREP 返回 `UCN_ERR_STATE`，Candidate、Route 不写；
- 精确重复 RREP 只幂等返回，不刷新 Candidate 生命周期；
- ACK 使用冻结 Candidate 快照安装 Route；
- Neighbor Bearer 若在事务中切换，则清除 Candidate，要求新 ID 重新发现和证明。

三组定向回归分别覆盖等待 ACK、Probe 完成但尚未 Activate、本地 Activate 提交失败；三者
都注入同 ID 更优 RREP，确认路径不移动，随后仅旧路径可被 ACK 或重试使用。外审 A06 探针
重编译后输出 `rrep=-16 candidate_moved=0 ack=0 route_moved=0 route_epoch=10`，旧漏洞断言
退出码变为 1。另以真实 Neighbor 双 Bearer 回归确认：Candidate 已产生 Probe 证明后发生
主 Bearer 硬切换，旧 Candidate 会被清除，不会把证明迁移到备用 Bearer。

### R15｜V564-A06-B：中继与目标的每跳证明冻结

结果：对抗复查发现原 R14 只闭合 Origin，整改后自审 PASS；最终外审按用户要求延期到
v6 全部任务完成后的统一外审。

独立反例证明：中继在路径 A 上转发 Probe 后、ACK 返回前，同 ID 的更优 RREP 可以把本地
Candidate 改写到路径 B；旧状态没有显式标记“本跳已开始证明”，后续 Activate 会把从未
Probe 的 B 安装为 Active。原探针输出为
`after_probe_frozen=0, candidate_moved=1, new_activate=1`。

整改采用显式、不可推断的 `path_snapshot_frozen`：

- Origin、中继、目标在首次 Probe/ACK 进入外部发送回调前冻结各自拥有的 Candidate；
- Activate 预检要求待提交的正反 Candidate 均已冻结；
- 同 ID 但路径字段变化的 RREP 在所有上述阶段均零写拒绝；
- 发送失败不解冻事务；相同路径可重试，换路径必须使用新 Candidate ID；
- 所有新 Candidate 均由零初始化建立，不存在未初始化冻结标志。

正式回归还验证冻结位在同步 Send callback 入口已经可见。整改后定向探针输出：

```text
probe=0 old_probe_sends=1 forward_frozen=1
rrep=-16 candidate_moved=0
probe_ack=0 reverse_frozen=1
activate=0 old_activate=1 new_activate=0 installed_new=0 epoch=10
PROBE_EXIT=0
```

## 3. 确定性多节点反例

`test_multi_origin_route_epoch_isolation()` 使用 A、B、R、X、T 五节点：

1. A/B 同时对 T 发起 Discovery；
2. A 扩圈为 2→4 Hop，B 使用 2→3 Hop，并走不同首段；
3. 暂存返回帧后按 B→A 交叉交付 RREP；
4. 在 R 上同时观察 `(A,T)` 和 `(B,T)`，Epoch 不同；
5. A/B 业务均完整送达 T；
6. 构造 Source=A、Epoch=B 的帧直接送达 T，必须 `UCN_ERR_NOT_FOUND`，不触发业务投递且增加 `route_epoch_rejected`；
7. Full 下 A/B 复用 `candidate_id=200`，仍生成两个独立 Candidate；
8. 独立 Candidate 反例复用过期外域 Route 槽，确认不继承外域 Previous Epoch；
9. X↔T 断开后触发 A 的 RERR，只撤销 A 域；B 随后继续送达。

该用例不是两个相互独立的点到点测试，而是让两个 Origin 共享中继、目标和固定表，专门区分旧 Destination-only 实现。

## 7. 未完成与禁止扩大表述

本轮没有证明：

- 多块 ESP32 上的双 Origin UART/ESP-NOW 并发；
- Wi-Fi 广播冲突、RREQ 风暴、RF 丢包和真实重排；
- 多 Bearer 切换中 Transfer、Path 与 Route Epoch 的联合行为；
- 目标 MCU 的 RAM/Flash/栈/CPU/功耗；
- 超过固定槽容量仍可无损；
- 生产逐跳认证或恶意节点无法伪造控制面。

因此当前签字仅为：**V5-64 Host 软件实现和内部自审完成；按用户要求暂缓单项外审，等待
v6 全部任务完成后的统一外审与硬件验收**。
