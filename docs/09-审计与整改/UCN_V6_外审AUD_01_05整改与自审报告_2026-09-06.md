## 2. V6-AUD-01：Cluster 历史票复活

### 2.1 原问题

旧 transition 只持久化 old/new voter bitmap。成员 Lease 到期后，Commit 会把票从 bitmap 剪除；
但是如果该成员先以新 Session 或新 Capability 重新准入，同一逻辑位会再次变为 live，旧票便能
被错误解释为新父代际下的票。

### 2.2 整改

Cluster Record 破坏性升级为 schema v3。每个 old/new voter 位都具有同索引的持久化证据：

- voter Principal；
- Address Binding；
- Session Generation；
- 入站 Link ID 与 Link Generation；
- Capability Generation 与 Capability Digest。

收票时写入 bitmap 与对应证据。Commit 不再只做 bitmap 与 live bitmap 相交，而是逐票核对当前
成员记录及全部父代际。成员失效或重新准入时，Cluster 先通过 Provider 原子持久化清除关联票，
成功后才改变 RAM 成员状态；持久化失败保持旧成员和旧 transition 不变并失败关闭。

### 2.3 对抗回归

- Takeover：投票 → Lease 到期 → 新 Session 重新准入 → 不重新投票直接 Commit，必须拒绝；
- Recovery：同一攻击顺序必须拒绝；
- Stable/Joint old/new 集合分别重验；
- Capability Generation/Digest、Binding、Link Generation 任一变化都使旧票无效；
- 新父代际下重新投票后才能恢复 quorum；
- crash/reload 对 schema v3 canonical 记录执行精确校验，旧 schema 明确拒绝。

## 3. V6-AUD-02：公共调用链大栈对象

### 3.1 原问题

Security、Identity、Message 初始化或提交路径曾把完整 Owner/Snapshot 复制到自动对象；Full
配置下单个栈帧可达数 KB 至数十 KB。它没有被调用方 Opaque Storage 预算记录，可能直接击穿
MCU/RTOS 任务栈。

### 3.2 整改

- Security、Identity、Message 的 candidate/verify/staging scratch 移入调用方静态 Storage；
- Runtime 初始化直接构造目标 Storage，不再创建完整 Runtime Owner 自动副本；
- scratch 仍由唯一 Owner 和 callback gate 串行拥有，Provider 回调期间不能递归覆盖；
- 所有生产 v6 target 在 GCC 下生成 `.su` 栈使用记录；
- `v6_stack_usage_gate` 扫描 `src/v6` 的生产函数，拒绝 dynamic/unbounded 栈和超过 3072 B 的函数。

当前最终重建门禁扫描 433 个生产函数，Host GCC 最大静态栈帧为 2432 B，函数为
`ucn_v6_route_candidate_commit_ack()`。这只是编译器静态上界，不替代目标 MCU 的调用链和任务栈
高水位实测。

## 4. V6-AUD-03：Canonical AAD Payload 别名

`ucn_v6_wire_write_canonical_aad()` 现在在首次输出写入前执行 overflow-safe 双向区间检查，拒绝：

- Payload 与 AAD 输出完整重叠；
- Payload 与 AAD 输出任意方向的部分重叠；
- Payload 与 `written_bytes` 对象重叠；
- 输出与长度对象重叠。

负例保存 Payload、完整输出区和长度哨兵；拒绝后逐字节不变。这样调用方不能用输出覆盖仍在参与
canonical 认证的输入证据。

## 5. V6-AUD-04：Runtime Realtime 四事件所有权

### 5.1 新公共合同

删除由调用方直接交给 Runtime 的任意 T3 event key。Runtime 对每个交换签发仅本实例可验证的
`ucn_v6_runtime_time_handle_t`，handle 绑定 Runtime Instance Generation、slot generation、
cookie、Domain、Sequence、身份和双向 Route Ref；跨 Runtime、篡改、过期 handle 均失败关闭。

标准交换顺序为：

1. Master Runtime 构造并通过 Security 保护 `TIME_SYNC`，再提交 Adapter；实际 TX completion
   产生 T1；
2. Member 从 Security 已打开的精确帧和当前 Adapter 原子 RX item 取得 T2，冻结反向 Route；
3. Member Runtime 自行构造、保护并提交 `TIME_DELAY_REQUEST`；实际 TX completion 产生 T3；
4. Master 从已认证 Request 与当前 RX item 取得 T4，自行构造并发送 Response；
5. Member 打开 Response，校验 Principal、Binding、Session、Opcode、Domain、Sequence、双向
   Route/Path 和期限后，才把 T1～T4 交给 Realtime Domain。

Master 保留固定 response replay slot，以相同语义响应精确重复 Request；表满不驱逐其他事务。

### 5.2 双向 Path 自审纠偏

Forward 与 Reverse Route Ref 已拆开保存和验证，不再假设 A→B 与 B→A 拥有相同 Path ID。
完整集成回归固定 A→B 为 Path 2、B→A 为 Path 3，验证两个方向各自经过 Capability、Route、
Security、Adapter、Runtime 和 Realtime。

## 6. V6-AUD-05：回调内 Link reopen

Runtime 增加 callback/phase gate。ingress dispatcher、Buffer release、Endpoint fence 和依赖失效
回调执行期间，任何 Link reopen 都在调用 Driver、改变 Generation、清理 RX 或更新统计之前返回
`UCN_V6_ERR_STATE`。reopen 同时拒绝 active RX 和尚未完成的 invalidation。

测试在每类回调中主动调用 reopen，并比较完整 Runtime view、Adapter view、Generation、RX item、
统计及 Driver 调用次数，证明拒绝无副作用。新集成测试的 caller-owned callback gate 也显式使用
规范零初始化，避免依赖自动对象的偶然字节值。

## 7. Profile、Schema 与资源变化

Cluster 的 per-vote evidence 增大了真实私有对象。首次自审发现旧 Lite/Nano 公开 Storage 上界不足，
因此统一将 Storage Layout 从 8 破坏性升级为 9。随后使用合法极值
`CLUSTER_MEMBERS=32/CLUSTER_VOTERS=32` 独立构建，又发现旧 4096 B Record 无法容纳完整 v3
canonical 票证据，且 allowed-mask 不能执行未定义的 `1 << 32`。当前改用显式 `UINT32_MAX`
分支，并把 Record v3 固定为 8192 B；删除任何旧 Record 读取兼容。Cluster 静态上界相应为：

| Profile | Cluster Storage | Runtime Storage | Security Storage |
| --- | ---: | ---: | ---: |
| Full | 35072 B | 13760 B | 47104 B |
| Lite | 26432 B | 8032 B | 20992 B |
| Nano | 22272 B | 4784 B | 10816 B |

Nano 的 Realtime exchange 容量为 1：完成 Master Response 后该槽必须保留到期限，以支持精确重复
Request 的幂等响应。因此 Nano 测试不再错误要求同一时刻启动第二个 Master exchange；完整第一轮
T1/T2/T3/T4 和所有安全门禁仍实际执行。容量大于 1 的 Profile 继续覆盖并发 slot。

## 9. 外审建议

下一轮外审应重点重放：

1. Takeover/Recovery 的“历史票 → 重新准入 → 无新票 Commit”攻击，以及 32-Voter Record；

5. forged/cross-runtime/expired handle 与 callback 内 reopen。

生产密码、MCU ISR/DMA、任务栈水位、物理多跳和长稳仍是独立发布门禁。
