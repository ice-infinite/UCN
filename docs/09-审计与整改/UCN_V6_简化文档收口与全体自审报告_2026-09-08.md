## 1. 本轮为什么需要收口

前一轮简化文档已经分别描述基础通信、安全、可靠传输、Service、Realtime、Group、Cluster 和 Persistence，但跨文档仍存在三个风险：

1. 基础 RREQ/RREP 与高级 Route Stage/Commit 被写成两种可任选的动态路由实现；
2. 用户 Intent 已经要求协议自动选 Contract，但缺少唯一 Capability/Resolver 判定链；
3. 用户 API、Driver 事实入口和内部 Owner SPI 分散在多份文档中，Handle 和 Receipt 名称发生漂移。

本轮没有为了“少写文档”删除安全合同，而是把正常主线放进 15～26，把失败、恢复和对抗边界保留在 00～14。两组是同一协议的不同阅读层级，不是两套实现。第 26 篇是跨模块不变量和对接登记表，不是新增运行时模块。

## 3. 关键架构收口

### 3.1 基础路由与高级 Flow 分离

基础路径固定为：

```text
RREQ → RREP → SoftRoute → C1
```

`SoftRoute` 只是有绝对截止期的本地下一跳提示。它允许途中部分安装并在超时后自清理，不携带全路径 Authority，不持久化，也不能被 Pinned Path、Network Time Sync 或 Cluster Authority 消费。

高级路径固定为：

```text
Probe → immutable Proposal
      → PATH_ACTIVATE_STAGE → PATH_STAGE_ACK
      → PATH_ACTIVATE_COMMIT → PATH_COMMIT_ACK
      → FlowPath ACTIVE
```

显式 Abort 使用 `PATH_ACTIVATE_ABORT`。只有同一 ActivationKey 的下游确认与本地提交都完成，ACK 才能向上游传播。Commit 已可能发生时不能伪造全网回滚，必须保留对账或 `IN_DOUBT` 状态。

### 3.2 Resolver 成为唯一自动选型入口

[第 23 篇](../10-理论与规划/建议方案/UCN_v6_逻辑模型与伪代码/23-Capability与Contract-Resolver简化设计.md)把 Build、Peer、Path 与 Resource Capability 分层，并按下列固定顺序裁决：

```text
参数与枚举
→ Product/Endpoint/Per-send 硬 Policy
→ Identity/ACL/Authority
→ Security
→ Delivery/Interaction
→ Route/Flow
→ MTU/Transfer
→ Realtime
→ Completion
→ Resource admission
→ 确定性评分和 tie-break
```

Planner 只能提供候选和评分，不能越过硬门禁；Resolver 只读，不能分配资源或发帧；Runtime Coordinator 才能调用各 Owner 的 `ensure/use/cancel/retire`。

### 3.3 一个公共 API，两个互斥的本地执行层级

[第 25 篇](../10-理论与规划/建议方案/UCN_v6_逻辑模型与伪代码/25-统一公共API与内部SPI冻结候选.md)统一规定：

- `publish/request/respond/publish_group` 共用同一个 Intent/Resolver 入口；
- 严格满足 `PUBLISH + ONE_WAY + operation_id=0 + BEST_EFFORT + COPY + 单帧 + LOCAL_ACCEPTED`、无 callback 且 `out_handle==NULL` 的发布，只创建一个 TX Slot；
- 要求 Handle、callback、Operation/dedup、Latest、Reliable、Transfer、Zero-copy、Group、远端 Completion 或独立 Setup 时，必须在接受前创建完整 Request/Receipt/Attempt；
- 受跟踪路径统一使用 `ucn_send_handle_t`，Handle 包含 Runtime/Owner Instance、slot/generation 和 object kind；
- `UCN_OK` 只代表固定本地资源已经稳定接受提交；
- Send View 分别呈现 admission、Completion、execution outcome、Buffer release 和 plan generation；
- 内部 Completion Receipt 不是公共 View，Buffer Released 也不是业务完成；
- Driver 只发布 RX/TX/Link/timestamp 事实，不参与协议决策；
- 模块内部只使用统一 `view/ensure/use/cancel/on_event/retire/step` SPI 形状。

这样普通用户不需要知道 C/H/O Contract，也不必为 fire-and-forget 消息承担完整事务对象；需要跟踪时又不会因为请求、发布或群发而学习多套同构 Handle。

外部复审给予 R22 文档语义受限 GO，但证明 R23 初版门禁仍把“表本身等于常量”误当成“每条图边都命中表”，并发现当前 Cluster 图已经存在表外 Coordinator 往返边、非规范虚线边和等价基础设施调用漏检。四项意见均成立：R24～R26 是实际门禁/文档缺陷，R27 是前一轮整改后尚未重新生成候选清单导致的证据漂移。

本轮按整改架构本身收口，而不是继续堆叠互不关联的特例：

1. 第 26 篇为 Coordinator、Identity、Security、Capability、Route、Flow、Transport、Operation、Time、Group、Cluster、Persistence、Adapter、Admission、Request、Sequence、QoS 和通用 Module 分配规范 `OWNER_*` ID，并显式登记所有允许的双向有向边；

## 6. 对抗式交叉检查

本轮按以下错误实现反查全部主线文档：

- RREP 丢失后把 Relay 的部分 SoftRoute 当成全路径 Commit；
- 只有 SoftRoute 时接受 Pinned、Realtime Network Sync 或 Cluster Authority；
- 同 Candidate 在 Probe/Stage 后改写路径字段并继承旧证明；
- Planner 因评分更高而放宽 REQUIRED Security/Completion；
- Feature OFF 返回伪成功或把错误推迟到链接期；
- `UCN_OK` 被解释成远端已完成；
- 未跟踪发布被要求返回 Handle，或接受后才发现要补建 Security/Flow/Transfer/Persistence 状态；
- `operation_id != 0` 的 dedup Event 被错误塞入未跟踪 TX-Slot 路径；
- Buffer 归还被解释成业务成功；
- Durable PREPARED/EXECUTING 未完成 reload proof 就调用执行器；
- Best-Effort Group 用本地 fanout 数冒充 ANY/ALL/QUORUM/SUBSET；
- 不同类型 Handle 的 slot/generation 数值相同而 object kind/Owner 未校验；
- Provider/Driver 回调前没有建立精确 continuation 与重入门；
- 表满时驱逐正在被 Attempt/Authority 引用的槽；
- 当前源码事实 RFC 与下一轮低开销 Wire 混合取字段。
- 业务 Owner 绕过 Coordinator 直接调用 Persistence/Adapter/另一 Owner；
- 原始 Driver/Link Fact 在 Wire/Security 验证前被标记成 authenticated；
- Owner step 用固定严格优先级让 Timer、控制、取消或退休饥饿；
- 两个 canonical requirements 的 digest 碰撞后复用同一个 Pending slot/Handle；
- RERR 只凭 Destination 或 causal digest 删除 Route，未精确匹配 original traffic RouteDomain 和 route generation。
- 任一 00～26 Mermaid/伪代码把业务 Owner 直接连到 Persistence/Adapter，或把 reload proof 绕过 Coordinator 直接返回请求 Owner；
- 检查器只识别固定别名/固定字符串，无法检出等价的 Owner 直连变异。
- Coordinator 边被无条件跳过，或 Cluster 等具体 Owner 未进入唯一有向登记表；
- `participant SecurityOwner`、对象成员调用和局部别名使表外连接/调用逃过检查。

这些路径均已在文档中明确禁止或导向确定错误/有界等待；实现阶段仍需把每一项转成独立负向测试。
