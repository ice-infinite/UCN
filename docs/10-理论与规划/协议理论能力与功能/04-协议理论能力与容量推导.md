# 04 · UCN 协议理论能力与容量推导

> 所有数字来自代码常量或实测；⚠️ 处为需要实机标定的项目。
> 实测依据：8/16/32/64/254 节点 two-hop 交付率 100%/68.8%/43.8%/28.1%/15.0%；128 节点 local 高压力 100%（512,000/512,000）；4096 节点 all-to-all 接受 1.2%、交付 15.9%；全部场景零崩溃/零重复业务/零路由环。

## 1. 理论上应该实现的功能（对照当前状态）

### 1.1 协议定位

UCN 理论上应该是"无中心、异构介质、安全可信、可扩展数千节点的完整 MCU 自组网协议栈"。覆盖 L2.5~L7：链路抽象、自组网路由、QoS 传输、安全、会话、应用服务。

### 1.2 功能全景（33 项，已实现 24 项 = 73%）

完整分层表格见 [01-项目介绍与架构.md](01-项目介绍与架构.md) 第 3 节。未实现的 9 项：
1. 跨域 Gateway（V5-06 设计完成，不进 Core）
2. Q2 可靠传输（Extended 规划）
3. Q3 批量传输（Extended 规划）
4. 组播/群组（Extended 规划）
5. 服务发现（Extended 规划）
6. 时间同步（Extended 规划）
7. 生产安全闭环（S02：真实身份/AEAD/密钥/逐跳认证）
8. Linux Host / ROS2 / MAVLink Bridge（规划）
9. 完整会话生命周期管理（部分）

## 2. 容量推导（基于代码常量）

### 2.1 寻址与规模

| 口径 | 上限 | 公式/依据 |
| --- | --- | --- |
| 地址空间 | 4,294,967,294 | 32 位 − 0 非法 − 广播 |
| W0 单域 | 254 | 1B 地址，255 广播保留 |
| W1 单域 | 65,534 | 2B 地址 |
| W2 单域 | 16,777,214 | 3B 地址 |
| W3 单域 | 4,294,967,294 | 4B 地址 |
| **单节点活跃目的地** | **8** | UCN_MAX_ROUTES（硬瓶颈） |
| **单节点并发寻路** | **4** | UCN_MAX_ROUTE_DISCOVERIES |
| 单节点邻居 | 8 × 2 Bearer | UCN_MAX_NEIGHBORS × UCN_MAX_BEARERS |
| 单节点注册 Link | 4 | UCN_MAX_LINKS |

> **全网节点数 = 无硬上限（受档位域限制），但每节点工作集 = 8 个活跃目的地。**
> 推导：N 节点全网任意互通的必要条件 = 每节点同时缓存 ≥N−1 条路由 → **N ≤ 9 才能全连通**。
> 现实假设：MCU 网络是"局部性"流量（传感器→汇聚点、编队领航→僚机），每节点活跃对端通常 ≤8，此时网络规模不受路由表限制。

### 2.2 跳数

| 口径 | 数值 | 依据 |
| --- | --- | --- |
| 线格式最大 | 254（W3） | hop_limit 8 位 |
| 编译默认 | 16 | UCN_MAX_HOPS=16 |
| 扩圈发现预算 | 2→4→8→16，单环 250ms，总 1000ms | UCN_ROUTE_RING_TIMEOUT_MS |
| 长链验证 | 100~200 跳 Host 正向基线 | V5-14 报告 |
| **实用上限** | **16~32** | 泛洪开销 O(每跳节点数) 指数增长；>32 跳控制面风暴 |

### 2.3 单节点吞吐（协议调度上限）

**发送**（ucn_node_step 每次调用发送 1 帧业务）：
- 裸机/主循环：**1 帧/step = 100 帧/s**（10ms step）
- Event Runtime：最多 8 轮/周期 → **峰值 800 帧/s**
- 每帧最大 256B → **TX 上限 25.6~204.8 KB/s**

**接收/转发**（ucn_adapter_rx_pump 预算，产品配置 4~32 帧/step）：
- 中继为同步路径（收 1 转 1）→ **转发峰值 ≈ 3,200 帧/s ≈ 819 KB/s**（理论）

**介质实际瓶颈（通常卡在这）：**

| 介质 | 典型净速率 | 256B 帧率 | 协议层是否瓶颈 |
| --- | --- | --- | --- |
| UART 115200 | ~11.5 KB/s | ~45 帧/s | 否（介质瓶颈） |
| UART 921600 | ~92 KB/s | ~360 帧/s | 接近调度上限 |
| UART 4M | ~400 KB/s | ~1560 帧/s | 需 Event Runtime 多轮 |
| ESP-NOW @1Mbps | ~60-120 KB/s | ~400 帧/s | 介质瓶颈 |
| CAN-FD @4Mbps | ~350 KB/s（64B 为主） | ~5500 帧/s（64B） | 帧率受调度上限 |
| LoRa SF7 | ~3-10 KB/s | ~20 帧/s | 介质瓶颈 |

### 2.4 全网容量模型（★ 实测曲线的数学解释）

- 心跳固定开销：每邻居 1 帧/s → 8 邻居 = 8 帧/s/节点
- **RREQ 泛洪是共享瓶颈**：
  - 中间节点 RREQ 接收预算 = 5 帧/200ms = **25 帧/s**
  - 254 节点同时寻路 → 中间节点每秒收到 ~254×度 个 RREQ → 只能放行 25
  - **寻路成功率 ≈ 25/(254×度) ≈ 5~15% —— 与实测 254 节点 two-hop 15% 交付率完全吻合**

> **结论：多跳容量由控制预算决定（25 帧/s/中间节点），工作集由路由表决定（8 目的地/节点）。两者均为编译期常量，这就是"节点翻倍→交付率约减半"的根本原因。**
> **扩容手段**：调大 UCN_MAX_ROUTES / UCN_ROUTE_REQUEST_RX_TOKEN_REFILL_MS，并重新评估 RAM（每路由条目 ~40B）。

### 2.5 时延

| 环节 | 理论 | 依据 |
| --- | --- | --- |
| 一跳调度 | 0~10ms | 10ms step 量子 |
| 一跳介质 | 帧长/波特率（256B@115200 ≈ 22ms） | 物理 |
| 多跳端到端 | 每跳 10ms+介质 | 线性累加 |
| 冷路径寻路 | 250ms~1s | 扩圈单环 250ms |
| Transfer ACK | 250ms × 最多 3 重试 | ack_timeout_ms |
| 断链感知 | 默认 3~4s；fast 1.25~2s | Suspect/Remove 常量 |
| 断链恢复 | ~1-2s（RERR+重发现） | RREQ 预算 1s |

### 2.6 可靠性

| 层 | 机制 | 极限 |
| --- | --- | --- |
| 帧 | CRC16 | 检错不纠错；漏检 ~2⁻¹⁶ |
| Q0/Q1 | 无 ACK（尽力/最新值） | 丢帧由上层业务容忍 |
| Transfer | CRC32 整消息 + ACK + 3 重试 | 理想链路 ~100%；重试耗尽即失败 |
| 链路 | 心跳 + Bearer 主备 | 断链 4s 内切换备份或标记 Suspect |
| 防重放 | 32/64 位窗口 + 会话轮换 | 窗口内重复拒绝；大跳跃重置有界重放风险 |

### 2.7 消息大小

| 档 | 上限 | 场景 |
| --- | --- | --- |
| 单帧 | 256B（可调） | 遥测/控制 |
| T32~T128 | 32~128B | 单帧直发 |
| T256~T8K | 256B~8KB | 配置下发/日志/固件块 |
| **硬上限** | **8KB** | UCN_TRANSFER_MAX_MESSAGE_BYTES=8192（静态槽） |

### 2.8 控制面开销占比（效率）

| 流量 | 线效率 | 实测 |
| --- | --- | --- |
| 128B 负载 local | **80.8%** | 模拟实测 |
| 16B 负载 two-hop | 2.4~7% | 模拟实测（控制面占大头） |
| 256B 满载 | 理论 ~88% | 30B 头 |

## 3. 业务场景推演

### 场景 A：50 架无人机编队（FANET）

假设：50 节点；每机 WiFi/ESP-NOW 邻机 3~6 架；遥测 10Hz×64B、控制 50Hz×16B、状态 1Hz×128B；2~3 跳。

| 维度 | 需求 | 协议能力 | 判定 |
| --- | --- | --- | --- |
| 节点数 | 50 | 工作集 8/节点 ✓（只跟 3-6 邻机+领航） | ✅ |
| 跳数 | ≤3 | 默认 16 | ✅ |
| 每机吞吐 | ~1.4KB/s | 调度上限 25KB/s+ | ✅ 余量 18× |
| 全网吞吐 | ~70KB/s | ESP-NOW 空口 ~100KB/s | ⚠️ 接近空口上限，需实测 |
| 时延 | 控制 <100ms | 2-3 跳 20-30ms+介质 | ✅ |
| 断链恢复 | <5s | 4s 感知+1-2s 恢复 | ⚠️ 临界，建议 fast liveness |
| 安全 | 防劫持 | 需 S02（当前仅框架） | ⚠️ 开发可用，生产不可 |

**结论：✅ 规模/吞吐/时延满足；建议开 fast liveness、用 W0/W1 压缩档、每机限 4 邻居；生产前必须完成 S02。**

### 场景 B：200 节点工厂传感器/执行器网

假设：200 节点；星型+树型（传感器→区域网关一跳为主）；读表 1Hz×32B、报警 Q0 突发；80% 一跳、20% 两跳。

| 维度 | 需求 | 协议能力 | 判定 |
| --- | --- | --- | --- |
| 节点数 | 200 | W3 单域 ✓（但工作集 8） | ⚠️ 必须按"区域网关分组"部署，每网关管 ≤8 节点 |
| 一跳读表 | ~6.4KB/s | local 100% 交付 | ✅ |
| 两跳汇聚 | ~40 节点经中继 | 64 节点两跳实测 28% | ⚠️ **关键约束**：每中继 RREQ 预算 25 帧/s → 每中继只服务 ≤8 个叶子 |
| 报警突发 | 100 节点同时报警 | Q0 仅 4 槽/节点+预算 | ⚠️ 全同时报警会丢，需错峰 |
| 稳定性 | 7×24 | 静态内存+长跑实测稳定 | ✅ |

**结论：⚠️ 可行但有硬约束——必须按"8 节点/汇聚点"分组设计拓扑；全网任意互连不可行（实测 15%），但"传感器→本地汇聚"是 100%。**

### 场景 C：车队/移动机器人协同（车内 CAN + 车际无线）

假设：12 辆车；每车 2 MCU（动力 CAN、感知 WiFi）+ 车际 1 无线；编队控制 20Hz×32B、状态 10Hz×128B；2~3 跳链式。

| 维度 | 需求 | 协议能力 | 判定 |
| --- | --- | --- | --- |
| 节点数 | 24 MCU | 工作集 ✓（2 车内+2 邻车） | ✅ |
| 车内 CAN | 100Hz×8B | CAN-FD 64B 帧 5500 帧/s | ✅ |
| 车际 | ~1.9KB/s/车 | 空口 ~100KB/s | ✅ 余量 50× |
| 时延 | 编队 <50ms | 2 跳 20ms+介质 | ✅ |
| 移动断链 | 车距变化 | Suspect/Remove+重发现 4-5s | ⚠️ **移动弱项**：建议 ADMITTED_SLOW 保持广播避免重复入网 |
| 多介质 | CAN+WiFi 同机 | MAX_LINKS=4 ✓、Bearer 主备 ✓ | ✅ |

**结论：✅ 完全满足，且是最佳场景——车内 CAN + 车际无线正是 T21 设计目标。注意移动重入网时延（4s 级）与实时控制预算。**

## 5. 一句话总结

> UCN 理论上应该是一个"无中心、异构介质、安全可信、可扩展到数千节点"的完整 MCU 自组网协议栈；当前已实现其中约 73% 的功能骨架，现实能力是"几十到两三百节点的域内、每节点 8 个活跃目的地、16 跳、8KB 消息、Q0/Q1 实时优先级、带主备冗余与断链恢复"的可靠通信系统；其理论极限（42.9 亿节点寻址、254 跳、生产级安全、跨域互联）受静态资源预算和未完成的 S02/网关/Extended 模块约束，实际只发挥到约 1/10~1/100。
