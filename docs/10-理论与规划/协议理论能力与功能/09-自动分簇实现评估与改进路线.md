## 2. 设计优点（代码审查确认）

- **边界冻结正确**：单层、一跳、不改 Core Wire、不猜硬件权重（评分产品注入）——首阶段范围克制
- **防分裂考虑充分**：满容量 Head 仍续旧成员租约（不误判不可用）；双 Head 用确定性评分+样本+任期收敛
- **fail-closed 完整**：非准入 Peer 拒绝、坏版本/长度/枚举拒绝、明文拒绝、陈旧 nonce 拒绝
- **控制面有界**：广告轮转 + 租约驱动，无需全网广播
- **与 Core 正交**：复用邻居摘要（只读）、Endpoint 0xA0 走正常 QoS/安全路径
- **资源极小**：860B 对象 + 0.04-0.07% CPU，MCU 完全可接受

## 3. 发现的问题与不足（按优先级）

| # | 问题 | 影响 | 现状/建议 |
| --- | --- | --- | --- |
| P1 | **无独立 Token Bucket**（文档自认） | 高密度/反复重选时控制面峰值无硬预算 | 仅靠广告轮转（≤14/s 实测）；C07 需补 Cluster 级预算 |
| P2 | **Head 失效感知 ~8s**（租约 8s） | 故障恢复慢于 Core 邻居 Suspect（3s） | 建议复用邻居心跳加速：Suspect 后立即置租约过期 |
| P3 | **单节点自动成 Head**（无 Peer 也选举） | 孤岛 Head（C05 的 D 即如此），产品需知 | 建议增加"无 Peer 不成 Head"或孤岛退出策略 |
| P4 | 成员容量默认 16（UCN_CLUSTER_MAX_MEMBERS） | 80 台/簇的推演需调大宏（每成员 ~16B） | 按场景配置；文档已列 |
| P5 | 恢复的高分 Head **不抢占**（稳定优先） | 最优 Head 长期缺席 | 首阶段明确；C07 需设计"何时恢复最优"避免抖动 |
| P6 | require_protected_control 实机未开 | 明文控制面可被伪造（依赖 S02） | 生产必须开启；受 S02 门禁 |
| P7 | nonce 防重放仅在同 (cluster_id, term) 内 | 切换后窗口重置，受限重放窗口 | 依赖 S02 AEAD 最终解决 |
| P8 | 跨簇数据面仍未完成规模闭环 | C06.3 已让显式单帧业务走“成员→本簇 Head→目标 Head→成员”，但跨簇 Transfer、自动 Gateway/聚合和实机验证仍缺失 | C06.4～C06.6 后再评估规模收益 |
| P9 | 单 Bearer 实测 | 独立 Bearer 插拔/冗余介质未测 | C05 遗留项 |
| P10 | 评分完全产品注入 | 产品必须自行滤波（瞬时 RSSI 会抖动） | 文档有公式建议；属正确解耦 |

## 6. 总结

> **当前簇设计质量高**：首阶段范围克制、状态机完整、fail-closed、资源极小（860B + 0.05% CPU）、模拟与实机证据齐全（10/10 测试通过、4/4 故障恢复、120s 稳定）。**它已闭环"簇的形成与维持"（愿景 12 项中的 7 项）。**
> **主要差距**：① 规模收益尚未完成闭环（已有 Host 单帧簇间 Tunnel，但无跨簇 Transfer、自动 Gateway、规模/MCU 证据）；② 生命周期机制缺位（备用 Head、拆分合并、独立预算）；③ 故障感知偏慢（8s，可复用邻居心跳到 3s）；④ 生产安全依赖 S02。**下一步完成 C06.4～C06.6，再进入 C07（生命周期）→ C08（多级验证）；C06 仍是“万级能力成立”的必要条件。**
