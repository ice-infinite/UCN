## 3. 实施顺序

### IMPL-00：冻结共同类型

- Runtime/Owner Instance；
- Handle/Generation/Fence；
- checked time/serial；
- error/no-write contract；
- callback/reentry contract。

### IMPL-01：最小通信闭环

- Static Identity/Binding；
- Copy 小消息；
- Basic Queue；
- Adapter RX/TX token；
- 严格未跟踪 Best-Effort Copy 的单 TX-Slot 路径；
- 要求 Handle/callback/高级语义时的 Request/Receipt/Attempt/Buffer obligation；
- stop/quiescent/storage reuse。

### IMPL-02：Persistence Foundation

- 每个 durable domain 的小型 Record/Operation DTO、独立 slot/witness/pending/Fault/Fence；不得使用一个全局巨型 Snapshot；
- 单一 Provider I/O Owner、Record/Journal/Witness；
- durable transaction identity 与 RAM-only completion routing 分离；
- `write inactive → verify → atomic commit marker → advance witness → reload`、load-before-owner-start、撕裂写和反回退；
- 为后续 C1 Transport Parent/Transfer-ID high-water 提供唯一 checked-next、persist-before-use 基座；
- 本阶段不接 Dynamic Admission、C1 Transfer、Durable Operation 或 Cluster Authority；
- Persistence OFF 时最小易失通信仍完整可运行；
- 当前 Identity/Security/Message/Realtime/Cluster 私有 Store 按 domain 逐一迁移；旧 Store adapter 只允许进入隔离迁移测试，禁止生产双写；
- 每个 domain 切换后用 `rg/nm/CMake` denylist 删除旧 writer，再允许下一个消费者接入。

Persistence Foundation 必须先作为独立模块实现和自审；消费者不得各自复制 Provider I/O、Record 或 completion 路由逻辑。

### IMPL-02A：物理解耦先决门禁

开始移动业务代码前，先冻结[第 26 篇](26-全局不变量与模块对接登记表.md)的 typed dependency 与连接登记。当前源码的三个主要开关、较长 `PUBLIC` 静态库链、Adapter 与 Runtime 绑定、Runtime config 的大 Owner 指针集合，以及多个私有 Store vtable 都属于已知迁移输入，不能写成“已经完成”。

每次拆分必须同时给出：

| 证据 | 必须回答 |
| --- | --- |
| CMake target graph | Feature OFF 是否仍被传递依赖拉入 |
| `nm`/link map | 专用符号、Provider callback、旧 Store writer 是否为零 |
| installed consumer | 头文件和 target 是否只暴露可链接能力 |
| Storage/resource report | RAM/Flash/Stack/Timer/queue 是否真的随模块消失 |
| behavior regression | 最小 C1/O0/H0 与原安全合同是否保持 |

逻辑 Feature bit、运行时 `UNSUPPORTED` 或目录重命名都不能单独通过本门禁。

### IMPL-03：Security Session 与静态安全直连

- 不启用 Dynamic Admission；
- 完成重启/reopen 后的新鲜会话；
- canonical AAD、overlap、Replay；
- Endpoint/Opcode ACL。

### IMPL-04：Dynamic Admission

- Cookie/限流；
- 双向身份认证；
- Address Binding persist-before-use；
- 动态设备到普通 Session 的唯一转换。

只有 IMPL-02 的 submit/reload/recovery 和 completion binding 门禁通过后，才允许 Admission 调用 Persistence。禁止在 Admission 内再实现一套私有 Provider 路径。

### IMPL-05：Route/Discovery/Forwarder

- 先静态 Route；
- 再角色化 Discovery，使 RREP 只安装可过期、非 Authority 的 SoftRoute；
- 用 C1 Best Effort/Latest 验证 `RREQ → RREP → SoftRoute → send`，不编译 Advanced Flow 也能完整运行；
- 再单独实现 Advanced Candidate/Probe 与逐跳 `STAGE_PENDING → STAGED → COMMITTING → ACTIVE/IN_DOUBT`；
- 在写任何实现前，由 Wire 权威文档冻结五个 C0 Opcode：`PATH_ACTIVATE_STAGE`、`PATH_STAGE_ACK`、`PATH_ACTIVATE_COMMIT`、`PATH_COMMIT_ACK`、`PATH_ACTIVATE_ABORT`；
- 同时冻结五类消息的完整 Route Domain、Candidate ID、Route Generation、Proposal Digest、阶段/结果、租期/错误、角色方向、byte offset、保留位和 canonical authentication coverage；
- 为五个 Opcode 分别建立正向 Golden、字段级 Negative、重复/冲突/乱序/迟到向量，并把 raw↔typed 映射固定到不可双向漂移的独立 fixture；
- RERR 和切路不变量。

基础 RREQ/RREP/RERR + SoftRoute 可在其自身 C0 Registry/Golden 外审后独立实现，不被高级 Flow 的五个 Opcode 延后。但低开销 Wire 未标记 `FROZEN FOR IMPLEMENTATION`，或任一 Advanced Stage/Commit Opcode、字段、Golden/Negative 尚未外审通过时，高级 Flow 只能写离线模型，禁止生产 Encoder/Decoder、RX 分派或 FlowPath 状态接线。Relay 只有收到下游 exact ACK 并完成本地阶段转换后才向上游发布 ACK；Origin 最后发布 Active。

### IMPL-06：Reliable/Flow/Transfer

- 先 C1 Reliable；
- 再 C4 Flow；
- 最后 Transfer；其中 C1 Transfer 先消费 IMPL-02 的 C1 Transport Parent durable high-water，
  C2/C4 Transfer 只消费其不可变 Flow 父代际；
- 每步复跑最小闭环和公共资源隔离。

### IMPL-07：Service/Operation/QoS

- 普通 Request/Result 不依赖 Persistence；
- Durable Operation 只有在 IMPL-02 已通过后才能单独启用；
- Advanced QoS 不改变单队列所有权链。

### IMPL-08：Realtime、Group 与 Cluster 的独立分支

| 分支 | 最小前置 | 明确不依赖 |
| --- | --- | --- |
| Realtime local-only/LOCAL_STAMP | IMPL-00/01 的 checked time、Runtime、Adapter timestamp（若使用） | Flow、Persistence、Cluster、Group |
| 外部已认证 Time Provider | Runtime + 产品 Provider 合同 + 所选 Security Policy | UCN Network Flow、Persistence、Cluster |
| UCN Network Time Sync v1 | Runtime + Security + Timed Link + Flow + C4 | Cluster、Group |
| Static Manifest Group | Group Core + 选定的 fanout 或 C5/Route/Forwarder | Cluster；无动态状态时不依赖 Persistence |
| Dynamic/Secure Group | Identity + Security + Persistence + Group Core + Realm Manifest 唯一选择的逻辑 Realm Address Authority | Cluster；Cluster 只能请求变更或提供数据面加速，不能取得 Group Policy Owner 身份 |
| Cluster Base | Runtime + Identity + Security + Persistence + Route Store + Flow/C4 | Realtime、Group |
| Cluster Group Acceleration | Cluster Base + Group + C5 | Realtime |

这些分支可以在各自真实前置完成后并行，彼此不得链接。`Realtime local-only` 可以在 IMPL-01 后提前实现；不能为了统一排期把 Flow/Persistence 变成它的隐藏依赖。Cluster 接线前则必须证明 Config/Epoch/Vote/Handover 全部复用 IMPL-02，且 durable Config 总能安装进 Runtime，Authority 只控制发送和权威副作用。

### IMPL-09：全量装配与实机

- 先用户能力需求经纯 Composition Plan 导出最小模块闭包，用户默认不选
  Owner、Wire Contract 或 C/H/O 组合；
- 再按 `Composition Storage → Coordinator typed adapter → durable reload →
  Owner publish → Adapter start` 顺序接线；
- available/compiled/selected 三种模块集合必须分离，未选模块不占运行时 Owner
  Storage、Timer 或任务；
- Feature/Profile 矩阵；
- Flash/RAM/Stack/CPU/Wire 五本账；
- ESP32/目标 MCU；
- 真实 Flash/掉电；
- 物理 Bearer、故障注入、长稳、性能和功耗。

当前实施进度（2026-09-24）：

- `IMPL-09-00` 已完成纯 Composition Plan；
- `IMPL-09-01` 已完成 caller-owned 精确 Storage、Owner Registry 和 Coordinator typed
  adapter；
- `IMPL-09-02` 已完成真实 Owner 初始化、Persistence Foundation 恢复门、Owner 发布、
  Adapter 启动和严格反向 stop/quiescence；恢复仍处于 `RECOVERING` 时不会提前销毁
  任何下游 Owner；
- Registry 固定登记 Foundation、Coordinator 和 Plan 选中的 Owner；业务 Owner 区在
  `IMPL-09-02` 正式初始化前必须逐字节为零；
- typed adapter 只冻结 `{runtime, requester owner, target owner, generation,
  dependency kind, composition digest}`，不保存函数指针，也不能直接调用目标 Owner；
- `PREPARED` 仍不得误记成可通信、可恢复或可生产状态；当前已完成的生命周期也只属于
  私有装配层。业务 Record 语义导入和 Coordinator binding 随 `IMPL-09-04～09-06`
  分模块接线，最小 Static C1 生产 Fast Path 属于 `IMPL-09-03`。

## 5. 最小闭环持续门禁

从 IMPL-01 开始，每新增一个模块都复跑：

```text
static direct C1/O0 send
RX strict decode and Endpoint delivery
synchronous/asynchronous Driver completion
cancel during Driver ownership
stop to quiescent
Feature OFF symbol/state check
```

模块化成功的核心证据不是目录变多，而是增加高级模块后，这条最简单路径仍然轻量、可解释、无隐式初始化。

## 6. 冻结顺序

```text
00 rules
→ 01 overall execution
→ 03/04/05 shared lifecycle
→ 02 minimal closure
→ 12 persistence foundation and recovery
→ 06 security/identity
→ 07 network（先冻结 RREQ/RREP/RERR + SoftRoute，再独立冻结 Advanced Flow 五 Opcode）
→ 08 transport
→ 09 service/qos
→ 10 realtime and 11 cluster
→ 13 global adversarial matrix
```

这里的顺序是“合同最晚冻结依赖”，不是宣称所有能力具有相同运行依赖：

- `12 Persistence` 必须在 Dynamic Admission、C1 Transfer 的 Transport Parent/Transfer-ID 高水位、Durable Operation、Dynamic/Secure Group 和 Cluster 的持久化合同之前冻结并实现基础门禁；
- `06 Security/Identity` 的静态身份和 O0/H0 Policy 可以不使用 Persistence，Session 可以不使用 Dynamic Admission；但任何发布受保护 `ACTIVE` Session 的 Session Generation，以及动态 Binding，都必须消费已冻结的 Persistence 合同或作为其 Provider 接入的等价硬件单调 witness；
- 普通 Service Request/Result 不依赖 Persistence，只有 Durable Operation 分支依赖；
- 普通单帧 C1 与 C1 Reliable 不依赖 Persistence；C1 Transfer 若没有等价硬件单调 witness，则必须依赖 Persistence，不能借用 Security Session 或易失启动代际；
- Realtime local-only 和外部 Time Provider 不依赖 Flow/Persistence；只有 UCN Network Time Sync v1 依赖 Flow/C4；
- Realtime 是能力总称而不是 Flow/Persistence 的同义词：LOCAL_STAMP 只消费本地 Runtime/Adapter 时间事件，不能因为启用 Realtime 就隐式创建网络同步或持久化状态；
- Cluster Base 依赖 Flow/C4 和 Persistence，但不依赖 Realtime 或 Group；Group/C5 只是显式可选加速。

如果后续文档修改让消费者早于 Persistence 定义自己的 durable identity、Provider callback 或 Record，冻结检查必须拒绝，而不是通过实现阶段再统一。

## 7. 完成判据

逻辑设计阶段完成必须满足：

- 每个入口能从伪代码找到唯一 Owner；
- 每个外部副作用前有零写入 preflight；
- 每个异步 completion 有精确 continuation；
- 外部 callback 返回值与回调内早到 completion 通过唯一合并点处理，状态不倒退、不双消费；
- 受跟踪 Request 的 Anchor、Completion Receipt 与执行槽分别具有 exact generation；旧 Handle 先解析 Anchor，再解析其 `live_request_ref/receipt_ref`，不因任一槽复用发生 ABA；未跟踪最小发布不产生 Public Handle；
- durable transaction identity 与 volatile completion routing 不混用、不跨重启恢复 callback；
- 基础 RREP 只产生 SoftRoute，无 Flow/Label/Authority/持久副作用；Advanced Flow 的五个 Stage/Commit Opcode、精确字段与 Golden/Negative 已先于其实现冻结，逐跳 ACK 只能在下游确认和本地状态发布之后向上游传播；
- 每个状态有正常、取消、超时、重启和退休路径；
- 每个 Feature OFF 组合有唯一结果；
- Group 的静态/动态/安全依赖和 RX 生命周期完整且容量有界；
- Dynamic Group 只消费 Realm Manifest 选定的唯一逻辑 Realm Address Authority 证明，ordered commit 在全部资源预留后不再调用可失败/重入的外部函数；
- CONFIG durable 后 Runtime 必须安装 exact Config，Authority 只控制发送/权威副作用；
- Planned Handover 先 durable Stepping Down/Fence 并 reload，每次发送前再验证 current target proof；失败保持 Fence 并进入恢复，不恢复旧 Authority；
- 图、伪代码、Wire、API、模块依赖一致；
- 对抗矩阵能稳定击中已知错误设计。

这些满足后才进入生产代码重构，而不是因为文档数量已经齐全就开始编码。
