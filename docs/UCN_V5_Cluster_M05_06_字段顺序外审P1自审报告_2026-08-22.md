## 1. 外审问题与整改结论

外审指出原 registry test 只证明 Type 编号、结构和 raw→semantic→raw 往返，且样本大量
复用 `1`。该结论成立：parser 与 builder 对同一 Type 同时交换字段时，旧测试可能继续通过。

现已将 Type 20..33 改为独立的冻结 fixture table。每个可写 P0..P5 都使用通过 RFC4
structural gate 的可区分值；仅 RFC4 强制 zero-tail 的 P5 保持零。

## 2. 新的双向冻结门禁

对每一条 fixture，测试分别执行：

1. 不经 `make_valid_frame()`，直接从独立 table 构造 raw frame。
2. `semantic_from_frame()` 后，逐项检查该 Type 的每个具名 payload 字段，而非 union 内存
   或 round-trip 结果。
3. 使用 semantic message 调用 `semantic_to_frame()`，逐项检查 Common Header 与精确
   P0..P5 是否等于 fixture。
4. 对 CONFIG_COMMIT、CONFIG_ABORT、HEAD_WITHDRAW 继续验证 non-zero tail 被拒绝且 output
   不写回。

因此 parser 字段对调会在第 2 步失败，builder word 对调会在第 3 步失败；两者同时对调
也无法绕过独立的具名字段断言。

## 3. 边界核对

- 冻结 Type 20..33 的 numeric ID、role、flag、payload size、zero-tail 和原有双角色/READY
  规则仍保留。
- 未改变 RFC4、public header、codec 生产实现、private payload layout、v4 encoder 开关或
  production RX/TX/FSM。
- 05-07 的外审 GO 已同步为受限完成，但不构成 M05 整体放行。
