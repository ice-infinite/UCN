## 问题—整改—证据

| 编号 | 原问题 | 整改 | 自审证据 |
|---|---|---|---|
| R24 / P0 | 双 quorum 可直接 Commit；Joint 只有 RAM 状态 | 新增 durable `CONFIG_JOINT` operation。`begin_joint()` 对 exact `PREPARED(C_new, txid)` 完成 `submit -> load + journal proof`；runtime enter 和 Commit 都要求该 journal。 | 无 Joint 的双 ACK、重启后仅 PREPARED、Joint runtime 不匹配都在 Provider I/O 前拒绝；完整 `Prepare -> Joint -> enter -> Commit` 通过。 |
| R25 / P0 | Backup gate 在 durable Commit 后才检查 | `begin_commit()` 接受 exact Joint runtime 与 Backup gate，并在 Config store recovery / Provider submit 前检查。runtime apply 保留同一 gate 作二次防线。 | require-Backup 情况下：缺 Backup、未 stage、未 ACK 都是零 submit、durable state 不变；exact ACK 后才提交。 |
| R26 / P0 | Config Owner 绕过 M04 I/O 重入门 | Owner 增加 `io_active`；initial load、submit、poll 回调前置门，poll 的 completion 直到 reload exact proof 成功才清 pending。 | fake Provider 在 load/submit/poll 内递归 Prepare/Joint/Commit/Abort/Poll 均返回 `UCN_ERR_STATE`，无第二 submit。 |

| R28 / P1 | Abort 只绑定 txid，没有绑定 C_new | Abort 首次与 terminal replay 均校验 exact C_old / C_new / txid；v2 terminal Config journal 保留 immutable C_new ref。 | 相同 txid、不同 C_new 的 Abort 零 submit 拒绝；合法 Abort 与 Record encode/decode/replay 通过。 |

## 核心约束复核

1. `CONFIG_COMMIT` 不再是 `PREPARED + quorum` 的直接后继；唯一允许的实验序列为：
   `PREPARED(C_new) -> durable CONFIG_JOINT -> local Joint runtime -> pre-submit Backup gate -> durable CONFIG_COMMIT`。
2. `CONFIG_JOINT` 只写 completed-operation journal，保留 `PREPARED`；它不提交 C_new、不发 wire、不授予 Authority。
3. Provider 声称 `COMMITTED` 但 reload 未精确看到 request journal 时，Owner 保持 pending / fail-closed，不开放下一笔事务。
4. 未发布的旧 terminal v2 Config record 不含 C_new 时会 fail-closed；这是为消除 Abort 重启歧义做的预发布 record 语义收紧，不能将其误述为向后兼容。
