# UCN 路由缓存与自动选路演进建议

> 状态：**UCN v4 Core 已实现 Epoch/grace、Candidate 切换、保守未知 Cost 和源端控制 Token；实机参数仍待标定。**  
> 日期：2026-08-07  
> 适用范围：`UCN-Core` 的动态多跳路由；保持 MCU-first、固定内存、跨介质 `route_cost` 与 Linux 非必需边界。

> v5 更新：当前累计 Route/Candidate Cost 已升级为 32 bit，RREQ/RREP 按 Wire Profile 编码，详见 [V5-14 实现报告](../08-实现与验证/版本演进/UCN_V5_14_长距离Cost与RREQ_RREP实现报告.md)。下文 32 B 基础头、16 bit 累计 Cost 和固定 RREP 长度仅是 v4 历史成本估算。

## 1. 为什么需要这份建议

当前 Core 已能按需发现路径，并在一次发现过程中选择较低累计 `route_cost` 的路径。但动态 Route Cache 默认有效期为 30 秒，且普通业务帧不会续租它；多跳路径在缓存有效期间也不会因质量变化自动重选。

这带来两个风险：

- 持续业务流可能在缓存到期后出现一次“无路由 → 重新发现”的空档；
- 路径没有明确断开、但质量已经持续变差时，Core 仍会沿用旧路径到过期或发送失败。

本建议的目标是消除不必要的 30 秒业务中断，并在质量显著变化时有界地重选路径；它不是要把 Core 变成维护全网拓扑的大型路由协议。

## 2. 当前实现事实与边界

| 项目 | 当前事实 |
| --- | --- |
| 路径发现 | 应用显式调用 `ucn_node_discover_route()`；`ucn_node_send()` 不会自动发现或缓存等待寻路的业务帧。 |
| 路径选择 | RREQ 从 `cost=0` 开始，逐 Link 累加 `route_cost`；同一 RREQ 的较低 Cost 副本可替换较高 Cost 副本。 |
| RREP 度量 | 目标从 `cost=0/hop=0` 回包；每个返回节点按 ingress 对应的目标方向 Link 累加，故缓存字段表示“当前节点到目标”的剩余 Cost/Hop，而不是把源端总 Cost 复制给所有中继。 |
| 直连多 Link | Full 优先使用本地 LC-1 有效分，Lite/Nano 使用基础 Cost；Known 优先，稳定同分以 `link_id` 确定。 |
| 多跳缓存 | 每个目标只保存一个 `destination → egress_link` 动态路由，默认 30 秒到期。 |
| 断链 | 发送发现 `Link Down` 时立即清除相关动态路由，并向上游发送 `ROUTE_ERROR`。 |
| 自动重选 | 已实现：已使用 Active 路由进入刷新窗口后受限发 RREQ，低 Cost Candidate 经 3 次 Probe/ACK 和 Activate 才替换 Active；普通业务始终先走 Active。 |
| 指标来源 | Core 只读取通用基础 Cost 与 LC-1 Metrics；RSSI、SNR、重传、CRC、Bus-Off 等必须由 Adapter 先映射，Full 再统一 EWMA/评分。 |

因此，`UCN_ROUTE_ENTRY_LIFETIME_MS=30000` 当前是“最大缓存寿命”，不是“每 30 秒比较并自动切换一次路径”的周期。

## 3. 设计目标与不做事项

### 3.1 目标

1. 正常通信时不因固定 TTL 到期而被动中断。
2. Link 明确断开时立即失效，优先恢复可达性。
3. 质量变化只有达到阈值并持续一段时间才切换，避免 WiFi/BLE 抖动造成来回跳路。
4. 所有表、候选路径、定时器和队列均固定上限、可编译期配置、无堆内存。
5. `route_cost` 保持跨介质统一；Core 不出现 RSSI、SNR、CAN Error Counter 等专有字段。

### 3.2 不做事项

- 不在每个业务包前发 RREQ 或全网重算路径。
- 不维护全网拓扑图、不使用 Linux 作为路由中心。
- 不把“本地成功送到下一跳”误判成“已端到端到达目标”。
- 不让 Q0 等待寻路；本地安全动作永远优先于网络恢复。
- 不在本阶段承诺 Q1 的可靠送达；可靠确认/重传属于后续 Q2 模块。

## 3.1 R1 当前实现边界

当前 C99 Core 使用固定 `ucn_candidate_route_t` 表保存 `(destination, candidate_id) → egress_link`，RREQ/RREP 的末字节标识 Candidate，`PATH_PROBE/ACK` 载荷为 12 B，`PATH_ACTIVATE/ACK` 载荷为 **6 B**（Candidate ID + Route Epoch）。后台仅在路由已使用、距 30 s 验证期不足 6 s、距上次刷新至少 5 s 时启动一次刷新；候选必须比 Active 至少低 20% Cost，并收到 3 个 ACK 才激活。

已验证“候选失败不覆盖 Active、Q0 先于 Probe、成功后经中继激活新 Active、动态业务携带 Epoch 且新旧路径可在 grace 内区分”。v5 的 Candidate 本地比较已可使用 LC-1 出口贡献，但保存/传播的累计 Cost 不变；同 Neighbor Bearer 另有 20%/3 样本/2 ACK/3000 ms 防抖。Unknown Cost 保留哨兵且不优于 Known，控制帧使用固定源端 Token。真实介质标定仍未完成，因此不能称为绝对无丢包切换。

## 4. 建议的路由状态模型

动态路由至少区分“正在使用”和“正在验证”，而不只用一个过期时间。

| 字段/状态 | 用途 |
| --- | --- |
| `destination`、`egress_link`、`route_cost`、`hop_count` | 当前活动路径的最小信息。 |
| `last_used_at_ms` | 最近被业务使用的时间，只用于 LRU/诊断，**不能**单独证明端到端可达。 |
| `validated_until_ms` | 最近一次 RREP、受确认的探测或端到端 ACK 所证明的有效期限。 |
| `ACTIVE` | 当前业务继续使用该路径。 |
| `REFRESHING` | 保留 `ACTIVE`，同时受限地寻找候选路径；不得先删旧路径。 |
| `CANDIDATE`（可选，最多 1 条） | 新发现的候选下一跳和 Cost；只在满足切换条件后替换 `ACTIVE`。参与该候选路径的中继节点也必须保存对应的候选转发表项。 |
| `INVALID` | 明确 Link Down、RERR、验证超时或安全拒绝后立即不可用。 |

`last_used_at_ms` 与 `validated_until_ms` 必须分开。否则，黑洞路径只要能把包交给第一跳，就可能因持续业务而被无限续租。

`ACTIVE` 与 `CANDIDATE` 同时存在时，不能只由源节点 A 保存候选下一跳。A、候选路径上的中继节点都必须能区分“旧路径的转发”与“候选路径的转发”；否则探测包到达中继节点后仍会被旧 `destination → egress_link` 表项送回原路径，无法真正测试候选路径。

## 5. 建议的刷新与切换流程

```text
业务继续走 ACTIVE 路径
        │
        ├─ Link Down / RERR / 安全拒绝
        │      └─ 立即 INVALID → 受限 RREQ → 建立新 ACTIVE
        │
        ├─ 距 validated_until_ms 尚有刷新提前量
        │      └─ 维持 ACTIVE，不发控制包
        │
        └─ 到达刷新窗口 或 质量持续显著变差
               └─ 进入 REFRESHING，旧路径仍可发送
                      ├─ 收到更优 RREP 且满足防抖 → 原子替换 ACTIVE
                      ├─ 只收到等价/更差路径 → 保留旧 ACTIVE
                      └─ 刷新超时 → 旧路径失效，报告无路由
```

### 5.1 先测后切（Make-Before-Break）

用户提出的“保持旧路径传输，同时让少量测试数据走候选路径，验证后再切换”是本建议的首选方案。流程如下：

```text
1. ACTIVE 业务路径继续发送
2. 受限 RREQ/RREP 找到 CANDIDATE，不能覆盖 ACTIVE
3. 给该候选路径分配 candidate_id / route_epoch
4. 仅发送低频 PATH_PROBE；每个中继按 (destination, candidate_id) 选择候选下一跳
5. 目标返回经认证的 PATH_PROBE_ACK
6. 统计探测成功率、RTT、抖动、Cost 与错误数
7. 满足门限：新业务帧从一个帧边界开始携带新的 route_epoch，转到 CANDIDATE
8. 旧 ACTIVE 保留一个短的 grace window，随后释放；若探测失败，直接清理 CANDIDATE，业务继续走 ACTIVE
```

这里的“测试数据”必须是 Core 控制面的 `PATH_PROBE/PATH_PROBE_ACK`，而不是重复发送真实电机命令、参数写入或普通业务包。探测帧应包含 `candidate_id`、探测序号、时间戳/nonce 和目的地身份校验；目标只回 ACK，不交给业务回调，避免副作用与重复执行。

候选路径使用 `candidate_id`，普通动态业务使用 `route_epoch`。v4 以 `ROUTE_EXTENSION=0x01` 选择 36 B 头：中继按 `(destination, route_epoch)` 选 Current 或 Previous 出口，Previous 到期即释放；RREP 也携带初始 Epoch，使首次动态路径不依赖“无标识”的业务帧。v3 帧会被显式拒绝，不能静默混用。

无环检查也必须按这条实际转发规则执行：从源端活动 Route 的 Epoch 出发，后续节点只能使用同 Epoch 的 Current 或未过期 Previous；直接邻居终止路径。不能把不同 Epoch 的缓存项简单拼成一条链后误判为转发环。

“无缝”在协议层的含义应是：旧路径在候选验证期不中断，新帧在切换点走新路径。已经提交给旧 Link 驱动的帧不会迁移，仍可能出现少量乱序或单帧丢失；Q1 接收方必须依据业务序号/时间戳丢弃过期值，Q2 则依靠 ACK 与去重保证一次执行。

### 5.2 触发条件

| 事件 | 建议动作 |
| --- | --- |
| `Link Down`、Bus-Off、连续 TX 失败、RERR | 立即清除受影响路径并开始恢复；不等待周期。 |
| 路由即将到期 | 在到期前的可配置窗口启动一次后台刷新；旧路径仍可服务业务。 |
| 活动路径 Cost 持续恶化 | 启动受限候选发现；不因单次 RSSI 波动切换。 |
| 已有候选路径显著更好 | 防抖通过后切换到候选路径。 |
| 普通业务发送成功 | 更新 `last_used_at_ms`；除非有端到端确认，不延长 `validated_until_ms`。 |

### 5.3 起始参数建议

这些是 WiFi/ESP-NOW 类 Link 的起始实验值，不是所有介质的硬编码协议常量；CAN、RS485、LoRa、BLE 应由各自 Profile 调整。

| 参数 | 建议起点 | 说明 |
| --- | --- | --- |
| Adapter 指标采样 | 约 500 ms | Adapter 在后台缓存平滑值，`get_metrics()` 只读缓存。故障事件立即上报。 |
| Cost 恶化触发 | 连续 3 个采样窗口超过阈值 | 防止单次无线波动发起 RREQ。 |
| 候选路径切换 | 候选 Cost 至少低 20%～30%，连续 3 个窗口成立 | 形成滞回，避免 A↔B 来回切换。 |
| 候选路径探测 | 低频、固定次数、受每 Link 控制流量预算限制 | 至少同时检查 ACK 成功率、RTT/抖动和错误；不得挤占 Q0 或持续占用无线空口。 |
| 动态路由有效期 | 保留 30 s 作为起始上限 | 改为“验证期限”，并在到期前后台刷新，而非到期后中断业务。 |
| 刷新提前量 | 有效期的约 20% | 需按网络跳数、RREQ 超时和介质速率确定，必须可配置。 |

未知或无效质量不能长期被当作“最佳质量”。实施时应将未知 Cost 独立标识或赋予保守代价，不能仅因默认值较小而压过已测量路径。

### 5.4 探测成本与频率建议

必须区分以下三种动作，它们的成本完全不同：

| 动作 | 网络开销 | 用途 |
| --- | --- | --- |
| Adapter 本地指标采样 | 不发送 UCN 帧 | 读取 RSSI、重传、丢包、Bus-Off、CRC、队列等并更新平滑 `route_cost`。 |
| 候选路径发现（RREQ/RREP） | 与网络分支数相关，最昂贵 | 找到可能更优的多跳候选路径。 |
| 候选路径验证（PATH_PROBE/ACK） | 与候选路径跳数相关，较小 | 确认候选路径的实际可达性、RTT、抖动和丢包。 |

当前 UCN v4 的基础头为 32 B：RREQ 载荷 16 B，单跳为 48 B；非 Candidate RREP 载荷 18 B，单跳为 50 B。真实空口成本还要加上 WiFi/ESP-NOW、CAN、BLE、LoRa 的 MAC 头、ACK、重传与 Link 安全封装。

v4 的 `PATH_PROBE/PATH_PROBE_ACK` 为 12 B，单帧为 `32 + 12 = 44 B`；对一条 `h` 跳候选路径发送 `N` 次“请求 + ACK”，协议层成本约为：

```text
probe_byte_hops ≈ 2 × N × h × 44 B
```

例如，2 跳候选路径、3 次探测约为 `2 × 3 × 2 × 44 = 528 B` 的 UCN 字节跳数，外加下层封装和重传。通常 RREQ 的泛洪成本高于这几次单路径 Probe，因此必须限制“找候选”的频率，而不是为了省几个 Probe 放弃端到端验证。

建议起始策略如下；它们是可配置 Profile 的实验起点，必须在 T14 实机上依据节点数、空口占用和业务时延校准：

| 场景 | 本地指标采样 | 候选发现/刷新 | Probe 验证 |
| --- | --- | --- | --- |
| 稳定 WiFi / ESP-NOW | 约 500 ms，无 UCN 控制包 | 仅在路径距离验证期限约 20% 的刷新窗口，或 Cost 连续恶化 3 个窗口时；同一目的地最短间隔建议 5 s | 3 个 Probe，间隔 100～200 ms；均成功或按业务设定通过率后才切换。 |
| 移动或干扰明显的 WiFi / ESP-NOW | 约 500 ms，无 UCN 控制包 | Cost 连续恶化时可提前触发，但仍受每目的地最短 5 s 间隔与控制流量预算限制 | 3～5 个 Probe；同时比较成功率、RTT、抖动和候选 Cost。 |
| CAN / RS485 等稳定总线 | 以错误事件和收发统计为主 | 优先依赖 Bus-Off、错误计数、Link Down；无异常时不应频繁 RREQ，可在 30～60 s 验证窗口刷新活跃路径 | 通常 1～3 个轻量 Probe 即可，或由可靠总线状态替代。 |
| LoRa / 极低速无线 | 以收发结果更新，不做高频空口采样 | 仅失效、明确业务需求或较长验证窗口触发；建议从 60～300 s 起按法规、空口速率和电池预算调整 | 1～2 个 Probe，严格限制空口占用和重传。 |

如果目的地没有活跃业务，允许其路由自然过期，不为“可能会用到”而周期性探测。对活跃业务，先由本地指标发现异常，再受限地进行候选发现和 Probe；任何 `PATH_PROBE`、RREQ、RREP 都不得抢占 Q0，也应各自受每 Link 控制流量预算限制。

## 6. 切换期间的数据规则

路径切换只影响尚未选择出口 Link 的新帧：已经交给旧 Link 驱动的帧不迁移、不撤回。上层需根据业务类型选择处理方式。

| 数据类别 | 切换期规则 |
| --- | --- |
| Q0 安全/关键控制 | 不等待发现或候选切换；只能使用直连、预建路径或本地失效安全动作。 |
| Q1 状态/传感器流 | 可允许少量旧帧丢失；使用 `latest_value` 时只保留最新状态，路径恢复后继续发送。接收方应使用业务序号/时间戳丢弃乱序旧值。 |
| 后续 Q2 可靠命令 | 由 ACK、请求编号、去重和超时重传处理；只重发未确认帧，避免切换后重复执行。 |
| Q3 大数据 | 不在 Core 队列内隐式续传；由 Extended 的分片/流控模块单独负责。 |

## 7. 推荐实施顺序与验收

本节对应任务表 T17。每个子阶段都必须先单测、再虚拟拓扑模拟、最后纳入完整集成测试；未通过不进入下一阶段。

| 子任务 | 实现内容 | 单元测试 | 模拟/集成验收 |
| --- | --- | --- | --- |
| T17.1 | 已实现 `last_used_at_ms`、验证期限、固定 Candidate 超时和保守未知 Cost。 | 路由到期、表项回收、未知 Cost 不压过有效测量。 | 连续业务流不会仅因“已使用”无限续租黑洞路径。 |
| T17.2 | 已实现后台刷新、活动/候选并存、Candidate ID 与 v4 `route_epoch`/grace。 | 刷新去重、提前量、候选表满、路径标识与 v3 拒绝。 | A→B→C 持续流不断，A→D→C 可建立候选但不覆盖旧路径。 |
| T17.3 | 已实现 `PATH_PROBE/PATH_PROBE_ACK`、单候选三次验证、20% Cost 滞回、Activate Epoch。 | 探测 ACK、超时、伪造/重放拒绝、单次抖动不切换、持续更优才切换。 | 业务继续走 A→B→C 的同时，探测仅走 A→D→C；验证成功后只切换一次。 |
| T17.4 | 已实现固定 grace/切换统计、Q0 不等待、Endpoint Q1 最新值等待；Q1 业务序号/乱序过滤仍属应用 ABI。 | 断链、恢复、抖动、候选失败、乱序与持续传感器流组合测试。 | T14 实机验证收敛、时延、空口和干扰。 |

建议新增的统计至少包括：后台刷新次数、候选发现次数、切换次数、因滞回拒绝的候选数、刷新超时数、切换期 Q1 丢弃数。它们都应是固定计数器，不保存无限历史。

## 8. 修改前置检查清单

后续真正实现 T17 前，先确认以下产品参数，避免把实验数值写死进所有 MCU：

1. 最大节点数、最大邻居数、最大活动目的地数与可分配 RAM。
2. 目标介质及其可观测指标：ESP-NOW/WiFi、CAN、RS485、BLE、LoRa 等。
3. Q0、Q1、后续 Q2 的业务清单与可接受的丢包、时延、恢复时间。
4. 是否存在必须长期保持的静态路由或网关路径。
5. 真实硬件可用于故障注入、移动、干扰和吞吐测试的范围。

v4 Core 已按本文件完成线格式、公共 API 和虚拟测试更新；上述产品参数仍用于确定目标板 Profile 与实机验收，不应被默认宏替代。
