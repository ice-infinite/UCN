# UCN 节点入离网与网络稳定性建议

> 状态：v5 Core 已实现 Heartbeat/邻居回收和每 Link DEFAULT/FAST 存活档位；RREQ/Probe/Activate 使用通用源端 Token，周期 Heartbeat 由固定档位节拍独立约束。随机 HELLO 退避已实现，真实介质参数仍需实机标定。
> 日期：2026-08-07  
> 适用范围：一跳邻居发现、入网、存活检测、离网回收与入网波动控制；不改变 MCU-first、固定资源和 Linux 非必需边界。

`UCN_MSG_HEARTBEAT` 现为一跳 8 B 请求/ACK：它不转发、不进入应用回调；通过既有 Security Provider 授权后才刷新已准入邻居。它仍不是生产身份/AEAD 的替代品。

### 1.1 已实现的 Heartbeat 范围与调度语义

Heartbeat 只属于一对已准入的**直连**邻居，不属于一条多跳 Route。以业务路径 `A → B → C` 为例：A 与 B 单独交换 Heartbeat，B 与 C 单独交换 Heartbeat；B 不会把 A 的 Heartbeat 继续转给 C，C 也不会收到 A→B 的那一帧。该帧固定 `hop_limit=1`，目标必须是对应直连邻居的 Node ID。

因此，Heartbeat 只能回答“我的下一跳邻居是否仍活着”，不能回答“A 到 C 的完整多跳路径是否可达”。多跳问题由下一跳 Link Down、`ROUTE_ERROR`、动态路由老化、已使用路径刷新和 Candidate `PATH_PROBE/ACK` 共同处理。

`HELLO` 也不能被误认为 Heartbeat：HELLO 是 Discovery Link 上的一跳物理广播，用于发现/准入；它不经过中继。当前 ESP-NOW 测试 Profile 每秒发送一次 HELLO，但该节奏是测试应用/Adapter 的 Profile 行为，不是 Core 强制的全网定时器。只有未知多跳目的地或候选刷新才会触发受限的 `ROUTE_REQ` 扩散。

当前调度顺序还意味着：`ucn_node_step()` 优先取一个本地 Q0，再取一个本地 Q1；仅在二者暂无待发项时才发送到期 Heartbeat。持续业务压力下 Heartbeat 可以延后，但来自同一邻居的任何有效入站帧都会刷新 `last_seen`。后续实机 Profile 必须在持续 Q0/Q1、丢包和干扰组合下验证是否需要为 Heartbeat 预留独立控制预算。

### 1.2 两条路径的并行与相互影响

UCN 没有“全网一条路径发完，另一条才允许发送”的机制。各节点维护自己的固定队列和协议任务，不共享节点的路径可逻辑并行推进。只有共享资源才会造成等待：共享同一中继时，该中继逐帧处理和转发、Q0 优先；共享同一 ESP-NOW/WiFi 信道时，空口竞争、重试和每板队列会造成实际时延与丢帧；使用彼此独立的物理介质时，影响可进一步隔离。

这条规则说明“逻辑并行”不等于“无线空口可无限同时发送”。必须在 T14 多板压力测试中测量不同路径数量、是否共享中继、空口占用、RX 队列溢出和 Q0/Q1 时延，才能冻结具体节点规模和发送频率。

## 2. 当前真实流程

### 2.1 节点离开

```text
节点 C 断电或离开
        │
        ↓
与 C 直连的邻居（例如 B）先发现
        │
        ├─ Driver/Link 报告 Down：下一次 `ucn_node_step()` 立即移除该一跳邻居
        │
        └─ Driver 未报告 Down：C 不再回复 Heartbeat/发送有效帧
                 ├─ 默认约 3 s：`ADMITTED → SUSPECT`
                 └─ 默认约 4 s（自最后有效帧起）：`SUSPECT → REMOVED`
        ↓
B 只做本地回收：失效所有以 B→C 为出口的动态 Active/Previous/Candidate 路由，
注销 Link、调用 Link `close`、清 `peer_node_id`、释放固定邻居槽
        ↓
其他节点不会收到“C 全网离开”的广播
        │
        └─ A → ... → C 的下一帧业务到达 B
                 ├─ B 已没有去 C 的下一跳：向入站上游回送 `ROUTE_ERROR(C)`
                 │      └─ 路径上的节点收到后各自清除“到 C”的动态/候选路由
                 └─ A 后续 Q1：受限 RREQ 寻找替代路径；无替代则等待超时/丢弃
```

这是一种**局部发现、按需传播**的离网处理：只有 C 的直连邻居能先通过 Link 状态或一跳存活检测确认离网；非相关节点不会重算或清空自己的全部路由表。RERR 也不是在 Heartbeat 超时的瞬间全网泛洪，而是在某条仍尝试经失效下一跳转发的业务路径上，沿原业务上游返回。若 C 是中继而非叶子节点，则它的每个直连邻居各自执行同样的本地移除；使用 C 作为出口的路径会在这些邻居处立即失效，源节点在下一次业务时按需恢复。

`invalidate_routes_by_link()` 只自动清理动态 Active/Previous/Candidate 路由；静态路由是应用明确配置的例外，不能假定会被自动重新规划，产品应由配置层或 Adapter 的明确 Down 事件处理。30 秒 Route Cache 到期只是防止动态旧路径永久保留，不是节点离线检测。普通业务成功送到下一跳也不会单独提供端到端可达性保证。

### 2.2 节点加入

```text
物理载体发现 MAC / CAN 端点 / 站号
        ↓
Adapter 从固定 Link 池绑定 Candidate Link（peer_node_id = 0）
        ↓
双方一跳 HELLO
        ↓
Core 校验 Network ID、Node ID 与准入策略
        ↓
Admitted：可单跳通信；需要多跳时由业务首次请求触发 RREQ
```

`Open` 仅适合实验网；生产网必须使用 `Provider` 验证身份和 ACL。新节点加入不应自动改变既有节点间的活动路径，也不应广播完整节点名单。

## 3. 为什么单节点加入通常不会使全网波动

UCN 的正确控制面应保持局部性：

1. 新节点只和一跳邻居做 HELLO/准入。
2. 一跳邻居只更新本地邻居表和空闲 Link 槽。
3. 不向全网发布拓扑表，也不因新节点出现而替换所有 Route Cache。
4. 只有真正要与该 Node ID 通信的源节点才发一次受 Hop Limit、去重和限速约束的 RREQ。

因此，正常单节点接入的固定成本是少量一跳 HELLO 与本地表项；**不是**全网波动。风险来自大量节点同时上电、所有节点同步广播、候选表耗尽或大量源节点同时 RREQ。这些风险需要随机退避、每 Link 令牌桶/配额、固定 Candidate 表和 RREQ 限速抑制。

## 4. 建议的 T18：邻居健康、平滑入网与离网回收

### 4.1 目标状态机

```text
EMPTY → CANDIDATE → ADMITTED → SUSPECT → REMOVED
                  └──────────→ REJECTED
```

| 状态 | 建议行为 |
| --- | --- |
| `CANDIDATE` | 已看到物理端点，等待 HELLO 与准入；沿用当前短超时回收。 |
| `ADMITTED` | 允许一跳业务和路由；按 Profile 发送/接收一跳保活。 |
| `SUSPECT` | 连续丢失保活或错误累积；保留极短恢复窗口，但不接受为最优新路径。 |
| `REMOVED` | 使相关路由失效、解除 Adapter 地址绑定、清 `peer_node_id`、将固定 Link 槽复用。 |
| `REJECTED` | Provider/ACL 拒绝；不转发其业务或路由控制帧。 |

### 4.2 一跳保活与时间建议

实现应使用已准入节点之间的认证 `HEARTBEAT`（或等价的最小 Keepalive），只更新一跳 `last_seen_ms`，不转发、不进入应用回调、不携带服务目录。

| Profile | 保活周期起点 | 失联判定起点 | 说明 |
| --- | --- | --- |
| 稳定 WiFi / ESP-NOW | 1 s 加随机抖动 | 连续 3 次未收到，约 3～4 s | 驱动明确 Link Down 仍应立即触发，不等保活。 |
| 移动 WiFi / ESP-NOW | 0.5～1 s 加随机抖动 | 3～5 次未收到 | 由功耗、干扰、空口占用和允许恢复时延标定。 |
| CAN / RS485 | 优先使用驱动错误/总线状态 | 依介质与控制周期配置 | 不应机械套用无线心跳频率。 |
| LoRa / 低功耗无线 | 数十秒至数分钟 | 按业务离线容忍度配置 | 必须受法规、空口时长和电池预算限制。 |

这些值是待 T14 实机标定的起点，不是当前实现能力或通用协议常量。若节点主动发业务或完成受认证 Probe，也可刷新一跳存活时间；但“只成功交给下一跳”仍不能单独证明远端目的地可达。

### 4.3 入网的时间与控制开销

目标不是追求“所有节点零等待同时加入”，而是在有界时间内稳定加入：

```text
物理发现 → 随机退避 HELLO → 双向 HELLO/准入 → 单跳可用
```

对 WiFi/ESP-NOW，初始 HELLO 应施加随机退避和每 Link 速率限制，避免同一时刻上电的多个节点同步冲突。完成一轮双向 HELLO 后即可单跳通信；首次多跳通信仍另需 RREQ/RREP。最终入网时间由扫描/发现、队列调度、退避、Provider 校验和介质重传决定，必须在实机测试中报告 P50/P95/最坏值。

### 4.4 与 T17 的关系

```text
T18：我身边这个一跳邻居还活着吗？何时接纳/清理它？
T17：多个可用路径中，哪个到远端目标更合适？怎样先测后切？
```

T18 报告 `Link Down`、连续保活失败或恢复事件；T17 据此立即失效路径、启动受限候选恢复或继续探测。二者共用 Adapter 的通用 `route_cost`，但不能把 WiFi 专有指标放进 Core。

### 4.5 可借鉴的 Reticulum 与 ESP-WIFI-MESH 机制

两者解决的问题与 UCN 有交集，但都不是 UCN 的直接替代品。UCN 应借用已经验证有效的**控制面约束**，不要把其拓扑、资源模型或平台前提整体复制进 MCU Core。

| 参考系统 | 其做法 | UCN 应吸收的部分 | UCN 不应照搬的部分 |
| --- | --- | --- | --- |
| Reticulum | 目的地以签名 `Announce` 建立可达路径；未知目的地才发 `Path Request`；Transport 节点保存路径并转发。它对 Announce/Path Request 设置带宽上限、随机转发、限频、暂存与丢弃机制，以避免新节点或错误应用淹没业务。 | 保持按需 RREQ，不因入网全网重算；为 HELLO/RREQ/Probe 分别设置固定队列、随机退避、令牌桶/最小间隔、去重和最大重试；控制面超过预算时优先延迟或丢弃控制帧，不能挤占 Q0 安全业务。 | Reticulum 的 Destination/密钥目录、多类 Interface Mode、可持久化的大路径表和长寿命缓存面向通用主机/低速广域网；不进入 UCN-Core，也不能以其较长的路径生命周期作为 MCU 离线检测时间。 |
| ESP-WIFI-MESH | 周期 Beacon 暴露邻居状态；节点依据 RSSI 门限、层级与子节点数量选择父节点；父节点失效后先重连，再扫描替换。WiFi 关联的空闲子节点可由父节点超时移除。 | T18 使用一跳认证 `HEARTBEAT`、`ADMITTED → SUSPECT → REMOVED` 状态、主动断链的快速通知、入网随机退避和可测量的 P50/P95 离线/入网时间；Adapter 可将 RSSI、重试、断连事件归一化为 Core 可用的 `route_cost` 和 Link 状态。 | 不采用 Root/Parent/Child 全局树、完整子树路由表或“全网仅一个 WiFi 根”的语义。单 WiFi STA 不能同时关联两个父节点，因此不能承诺仅靠一张 WiFi 网卡实现双父链路 Make-Before-Break；真正的候选先测后切仍由 UCN T17 在可并存路径或跨介质条件下实现。 |

这两类参考共同给出三个 UCN 设计结论：

1. **发现与寻路必须按需且受预算约束。** 新节点接入只做本地 HELLO/准入；远端路径只在业务需要时发现。任何控制帧都必须有固定内存上限、抖动与限速。
2. **邻居健康和远端最优路径必须分层。** T18 只回答“一跳邻居是否还活着”；T17 才回答“到目标的哪条路径更好”。不能用一次 RSSI 变化直接切断一条正在工作的多跳业务路径。
3. **切换能力受载体物理限制。** 对 CAN、RS485 或能够并存的双无线 Link，可做候选探测后切换；对单射频、单 STA 上游关联的 WiFi，最多做到快速恢复与业务序号容错，不能宣传为绝对无缝双路径切换。

以上为架构参考；当前 UCN 已是 v4 线格式。外部项目的具体默认周期、缓存寿命、节点规模和恢复时间不能直接作为 UCN 指标；T14/T18 必须以指定 ESP 芯片、介质、功耗预算和实机测试结果冻结最终参数。
