# 10 · 主备簇头 + 快速代理恢复方案评估

> 状态更新（2026-08-15）：本页记录最初可行性判断。经当前 Cluster/C06.3 源码核对，原文关于“Format v1 不变”“直接复用 Keepalive”“C06 目录无阻塞”的简化假设不成立；后续实施以 [C07 主备簇头、快速恢复与目录交接整体方案](../UCN_V5_C07_主备簇头与快速代理恢复整体方案.md) 为准。

> 用户方案：① 选主簇头 + 备用簇头；② 主断 → 备用无缝接管；③ 主备双断 → 任意节点快速选代理簇头（不看质量、只求快速临时恢复）；④ 后台观察最优节点重选主/备；⑤ 无缝切回新主。
> 结论：**完全可行，且与当前 ucn_cluster 架构高度兼容**（BACKUP 角色、HEAD_TAKEOVER/HEAD_STEPDOWN 消息均已预留）；当前已实现 FAST_FIXED 快速档案（恢复 3.68s），你的方案可再压到 1-2s 且业务中断更平滑。

## 3. 方案设计细化（每步怎么落地）

### 步骤 1：选举主 + 备用（初始阶段扩展）
- 选举完成后，Head 从 CANDIDATE 中选**评分第二者**为 BACKUP（或成员自荐：评分最高者申请）
- 新增消息：BACKUP_ASSIGN（Head 通知当选者）/ BACKUP_ACCEPT
- 备用进入 BACKUP 角色：持续监听租约，但不广播广告（静默）

### 步骤 2：成员表同步（无缝接管的前提）
- 方案 A（推荐）：成员 KEEPALIVE 时**同时抄送备用**（成员侧多一个目标，成本低）
- 方案 B：Head 定期（如 1s）向备用发 MEMBER_SYNC（成员 ID + 租约摘要）
- 备用持有与 Head 一致的成员视图 → 接管时无需重新加入

### 步骤 3：主断 → 备用无缝接管
- 备用检测：连续 N 次（如 3×500ms）收不到 Head 的广告/成员保活回执 → 宣布 TAKEOVER（term+1）
- 成员侧：租约过期（FAST 2s）前收到 TAKEOVER → 跟随备用（免重新加入）
- 控制面恢复：**~1-2s**；数据面：在途帧丢失 ≤1-2s（Q1 无端到端 ACK，业务层需容忍或 Transfer 重试）

### 步骤 4：主备双断 → 快速代理（不考虑质量）
- 触发：成员在"双倍快速租约"（~4s）内既无主也无备用接管
- 代理选举：**最短退避 + 最小 ID**（随机退避 0-500ms，先到先得），跳过评分/观察窗
- 代理职责：只维持成员连接与数据转发，**不做容量管理**（可临时超容）
- 代理寿命：**硬上限 30s**（代理期间必须完成后台重选）
- 恢复控制面：**2-3s**

### 步骤 5：后台重选最优主/备 + 无缝切回
- 代理期间正常评分选举（复用现有观察+选举流程）选出新主/新备
- 新主就绪 → 代理发 HEAD_STEPDOWN → 成员按租约跟随新主 → 代理转为普通成员
- 切回控制面：**1-2s**；全程业务只中断在步骤 3/4 的窗口内

## 4. 时间线总览（你的方案 vs 当前）

```
t=0      主 Head 失联
当前(FAST):  ── 2s 租约 ── 0.5s 恢复观察 ── 1s 选举 ──▶ 3.7s 恢复（重选，非最优）
你的方案:    ── 1-2s 备用 TAKEOVER ──▶ 控制面恢复（成员免重入）
            主备双断: ── 4s 检测 ── 0.5s 退避 ──▶ 2-3s 代理恢复（临时）

```

## 5. 必须注意的设计坑

| # | 风险 | 对策 |
| --- | --- | --- |
| 1 | **双主脑裂**：主没真断（链路抖动），备用抢先接管 | 备用接管需"连续 3×500ms 无主"确认 + term 仲裁（高 term 胜）；复用现有分裂收敛 |
| 2 | "无缝"的真实语义 | 控制面可 <1s 切换；数据面在途帧会丢（Q1 无 ACK）——建议定义为"控制面秒级恢复 + 业务 ≤1-2s 中断"，或用 Transfer 保证关键命令 |
| 3 | 代理可能是孤立节点 | 代理选举自然约束：广播响应者即"邻居最多者"；代理必须能连通多数成员才被接受 |
| 4 | 代理超容/劣质链路 | 明确代理寿命（30s）+ 代理期间数据降级声明；到期强制切新主 |
| 5 | 频繁切换抖动 | 备用接管后同样适用 min tenure；切回新主需"新主评分显著更优"（20% 门槛）而非立即抢占 |
| 6 | 控制面风暴（双断时全员响应） | 退避随机化 + 独立 Token Bucket（C07 必备） |
| 7 | 成员表同步的流量 | KEEPALIVE 抄送备用 ≈ 每成员 2 帧/2s（FAST 500ms 下 4 帧/s/成员）——每簇 16-80 成员可接受 |

## 6. 工作量评估（在 ucn_cluster 库内完成，不改 Core Wire）

| 后台重选 + STEPDOWN 切回 | 中 | 复用现有选举 + 切换仲裁 |
| 防双主强化 + 独立预算 | 中 | 复用分裂收敛 + 新 token |
| 模拟/测试扩展 | 中 | 新增场景：backup-failover / dual-fail / proxy-return |
| **合计** | **约 1 个完整开发迭代** | 与 C07"备用 Head/优选恢复"任务重合，建议直接并入 C07 |

## 7. 结论

> **你的方案完全可行**，且是当前 C07"备用 Head + 快速接管"任务的正确具体化：
> ① 相比已实现的 FAST_FIXED（恢复 3.68s），备用接管可再压到 **1-2s**，双断代理 **2-3s**；
> ② 架构零冲突——BACKUP 角色、TAKEOVER/STEPDOWN 消息、term 仲裁都已预留，工作量约一个迭代；
> ③ 关键设计点：成员表同步（备用持有成员视图）、双主仲裁（连续失联确认 + term）、代理寿命（30s 硬上限）、切回门槛（20% 评分差）；
> ④ 建议：将本方案作为 C07 的设计输入立项，先做"备用接管"（收益最大、改动最小），再补"快速代理 + 后台重选"。
