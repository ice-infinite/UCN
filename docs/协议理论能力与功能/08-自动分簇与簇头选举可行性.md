# 08 · 自动分簇与簇头选举可行性分析

> 问题：协议能否自动根据最优解挑选出一群"终端（簇头）"，由它们负责其下的设备，自动形成层级结构？
> 即无线自组网中的 **自动分簇（Clustering）/ 簇头选举（Cluster Head Election）**。
> 结论先行：**概念可行、收益巨大（规模可 ×10~×100），但当前协议代码没有任何选举机制，需要作为新功能扩展；现有原语可复用约 60%，推荐"应用层原型 → Core 扩展固化"的两步路径。**

## 1. 现状核查（已核实）

| 核查项 | 结果 |
| --- | --- |
| 协议代码中的选举/分簇机制 | **无**（全库 0 处真实引用） |
| Coordinator 概念 | 仅文档中的**角色描述**（MCU Coordinator 档案），无协议机制 |
| 任务表规划 | 无分簇/选举条目 |
| 最接近的机制 | Node Snapshot（连通域清单，单次 8 结果）、PATH_INSTALL（受认证路径安装）、JOIN_PROVIDER（成员准入授权）、LC-1 Cost（链路质量评分） |

## 2. 可复用的现有机制（约 60%）

| 现有机制 | 在分簇中的用途 | 限制 |
| --- | --- | --- |
| HELLO/邻居表 + 心跳 | 每个节点天然知道自己的一跳邻居及存活状态（选举输入） | 邻居表 8（可调大） |
| LC-1 Cost / 质量快照 | 给"谁适合当簇头"打分：链路质量、队列压力、失败率、RTT | 每 500ms 采样 |
| JOIN_PROVIDER 准入回调 | 簇头"批准"成员加入（把选举结果固化为准入） | 需扩展为簇级语义 |
| PATH_INSTALL（受认证） | **选举完成后自动安装分层路径**，成员只需 1 条到簇头的路径 | 转发表 8（可调大） |
| Node Snapshot | 管理节点收集连通域拓扑（选举的全局视野来源） | 单次 8 结果，需多轮/调大 |
| Policy Diagnostic | 查询各节点状态用于选举评分 | 单表项查询 |
| 控制预算（token bucket） | 防选举风暴（选举帧也走预算） | 需为选举帧分配预算 |

## 3. 缺少的机制（需要新增，约 40%）

| 机制 | 说明 | 新增面 |
| --- | --- | --- |
| 选举信令 | ELECTION_REQUEST/ACK/REJECT/DECLARE 控制帧（新消息类型 + 载荷编解码） | 新控制帧 4-6 种 |
| 选举算法 | 分布式启发式：lowest-ID / 最大度 / 加权评分（质量+容量+稳定性） | 新状态机 |
| 簇绑定状态 | 成员→簇头映射、簇头容量计数（每簇 ≤N 台）、簇 ID | 节点新增状态块 |
| 簇头代理 | 簇头代成员发起寻路/转发（成员只认簇头） | 转发规则扩展 |
| 重新选举 | 簇头失联（心跳超时）→ 成员自动重新选举/切换 | 状态机 |
| 簇拆分/合并 | 簇头超载 → 拆簇；簇空 → 合并 | 负载均衡 |
| 选举预算 | 选举帧的独立 token bucket（防风暴） | 预算扩展 |

## 4. 推荐的实现路径

### 阶段 1：应用层原型（Core 零修改，验证算法）
- 位置：类似 Service Router 的 Core 之外模块（ucn_cluster 库）
- 输入：现有邻居表 + LC-1 质量 + Node Snapshot
- 输出：选举结果 → 用 PATH_INSTALL 固化层级 → JOIN_PROVIDER 固准入
- 优点：不动协议线格式，可快速验证"自动选簇头 + 成员-簇头绑定 + 故障重选"

### 阶段 2：Core 扩展固化（协议级）
- 新增 ELECTION 系列控制帧（需协议版本演进，与 V5-06 Gateway 同级评审）
- 节点增加簇状态块（簇 ID、簇头 ID、容量、选举状态机）
- 簇头代理寻路 + 成员透明转发
- 独立选举预算，隔离于业务预算

## 5. 自动分簇后的规模收益（数学）

**核心收益：把"每节点 8 条远端路由"的约束变成"每成员 1 条到簇头的路径"。**

| 架构 | 单簇容量 | 总规模（2 层簇） | 总规模（3 层簇） |
| --- | --- | --- | --- |
| 无分簇（现状，泛洪） | 8 台/节点 | ~1000 台（半静态） | — |
| 自动分簇 + 静态 | 80 台/簇头（转发预算） | 80×80 = 6400 台 | 80³ ≈ 51.2 万台 |

- 成员只需 1 条路由（到簇头）→ 路由表压力骤减 → 单簇可容 80 台（10Hz 控制）
- 簇头之间用 PATH_INSTALL 互连（免泛洪）→ 上层网络规模不受寻路预算限制
- 选举是低频事件（一次选举长期稳定）→ 选举控制面开销可忽略

## 6. 关键风险与短板

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 移动性 | 移动场景簇头频繁切换 → 选举风暴 + 成员失联 | 簇头稳定优先评分、切换滞回 |
| 时间同步缺失 | 万级协同需要统一时钟 | Extended 规划（未实现） |
| 单点依赖 | 簇头失效影响整簇 | 备用簇头 + 快速重选（心跳 1-4s 感知） |
| 选举公平性 | 最优解需要全局信息，MCU 只能启发式 | 加权本地评分（质量+容量+ID） |
| 与安全结合 | 簇头是攻击目标 | 逐跳认证（S02 未完成前受限） |

## 7. 结论

> **可行**：自动分簇把"每节点 8 路由"的约束换成"每簇 80 台 + 簇头互连"，规模从 ~1000 提升到 **数千（2 层）~ 数十万（3 层，理论）**，且完全符合协议的"静态表 + 预算 + 路径安装"设计哲学（PATH_INSTALL 正是为免泛洪大规模准备的）。
> **但需要新增约 40% 的协议功能**（选举信令 + 簇状态机 + 代理转发 + 重新选举），当前代码为零；推荐两步走：先在 Core 之外做应用层原型验证算法（可复用快照/路径安装/准入），再以 V5-06 Gateway 同级评审将选举帧固化进协议。
> **工程判断**：如果目标是"几万台静态/半静态设备"，自动分簇 + PATH_INSTALL 是正确的架构方向，建议立项（类似 V5-06 的独立设计评审）；如果目标是"几千台移动无人机"，分簇+移动性管理是更大工程，建议先做 1000 台内的分层实测。
