# 07 · 万级规模可行性分析

> 结论：当前 UCN v5 已能验证固定资源节点、按需路由和首阶段单层分簇，但**尚不能宣称支持万级网络**。万级能力必须依赖局部自治、簇间聚合寻址、受控控制面和多级容量验证；W3 地址宽度或 `PATH_INSTALL` 本身都不能证明网络容量。

## 1. 必须分开的四个“上限”

| 上限 | 当前含义 | 不能推出的结论 |
| --- | --- | --- |
| Wire 地址宽度 | W0～W3 可表示不同宽度 Node ID | 可表示地址不等于可同时在线同等数量节点 |
| 单节点固定表 | Neighbor、Route、Path、Queue、Transfer、Cluster 均由产品宏确定 | 调大一个表不等于整体可扩展 |
| 单跳/多跳承载能力 | 取决于 UART/CAN/Wi-Fi 等 Bearer、帧长、负载和中继调度 | Host 模拟帧率不能当目标硬件保证 |
| 全网控制面能力 | 取决于发现范围、泛洪、拓扑变化、分簇和目录 | 数据帧能转发不等于万级寻路能收敛 |

W0 的单字节 Node ID 只是地址档位的表示边界，不是 UCN 的统一“单域最多 254 节点”承诺；W1～W3 可表达更多地址，但每台 MCU 仍只维护固定数量的局部状态。

## 2. 为什么扁平万级自组网不可取

现有 `ucn_scale_sim` 的低交付场景证明：固定预算下，全网同时按需寻路或 all-to-all 通信会快速耗尽控制帧、Pending Discovery、Route 和队列容量。该结果是**特定 Host 拓扑与流量模型的压力证据**，不是“4096 节点时协议必然崩溃”的通用物理定律。

扁平网络的主要问题是：

- 全网泛洪开销随节点密度和拓扑扩大；
- 任意节点对任意节点通信会产生近似平方级会话需求；
- 移动节点使 Route、Candidate 和安全会话持续失效；
- 中继吞吐随共享半双工介质和跳数下降；
- MCU 无法保存全网完整拓扑，且也不应保存。

因此，万级目标不能靠“继续扩大 Route 表、Hop 或 RREQ 预算”完成。

## 3. 正确的万级架构方向

```text
成员节点（只维护局部邻居和所属簇）
    ↓
单层簇头（成员租约、局部转发、局部目录）
    ↓
区域网关/上级簇头（簇前缀或 Locator 聚合）
    ↓
少量骨干路径（静态、受控安装或专用 Bearer）
```

必须同时具备：

1. 自动或配置式分簇，把变化和广播限制在局部；
2. 簇级 Locator/前缀与目录，而不是为每个远端成员安装一条精确 Path；
3. 簇内、簇间分别限速和调度；
4. 簇头容量上限、备用与失败恢复；
5. 对移动性设置滞回、最小任期和拆分/合并预算；
6. 生产身份、密钥、授权和防重放；
7. 按业务的时延/吞吐/SLA 做容量规划，而不是只数节点。

`PATH_INSTALL` 仍有价值，但它当前安装的是**精确目的地址的逐跳状态**。若给数万成员逐个安装 Path，簇头的 Path 表仍会爆炸。因此后续需要“簇 Locator + 簇间隧道/目录”，PATH 只承载少量簇间骨干或严格业务。

## 4. 容量只能按产品场景推导

假设每簇容量为 `M`，每个上级簇头可管理 `G` 个下级簇，则两层理论覆盖量约为 `M×G`，三层约为 `M×G²`。这是地址与组织结构的覆盖量，不是吞吐保证。

例如 `M=16、G=16` 时，两层为 256、三层为 4096；若要达到 10000，需要更大容量、更多层或多个独立区域。但每增加一层都会增加：

- 端到端跳数和排队时延；
- 簇头转发与目录压力；
- 故障恢复范围；
- 安全和运维复杂度。

“每簇 80 台”“每中继 800 帧/s”“75 KiB/节点”“30 ms”都只能是带明确 MCU、Bearer、帧长、频率和拓扑的产品假设，不能写成 UCN 通用保证。簇头与叶子也应采用不同 Profile，不能假设所有节点都消耗相同 RAM。

## 5. 当前已实现和未实现

| 能力 | 2026-08-15 当前状态 |
| --- | --- |
| 固定资源 Core、多介质 Link、按需 Route/Path | 已实现并有软件/部分 UART 实机证据 |
| 单层簇头选举、加入、租约、失效重选 | `ucn_cluster` 首阶段软件原型已实现 |
| 64/256/1000 节点分组收敛模拟 | 已实现干净与受损模式；受损含丢包/抖动/重复/短时单向阻断，但仍是隔离簇，不是共享无线或移动 Mesh 证明 |
| 簇间 Locator、目录、单帧隧道和聚合路由 | C06.0～C06.3 已有 Host 软件闭环：固定 Directory、Locator Cache、Cluster→Head 锚点与显式单帧 Tunnel；跨簇 Transfer、多 Gateway/聚合路由、规模/MCU 验收未完成 |
| 备用簇头、簇拆分/合并、多级簇 | 未实现 |
| 万级全负载、移动、丢包、非对称链路验证 | 未完成 |
| 生产安全与真实多 Bearer 容量 | 未完成 |

## 6. 发布口径

当前可以说：

> UCN 的局部状态和可选分簇架构为大规模网络预留了演进路径，单层分簇首阶段已完成 Host 软件验证。

当前不能说：

> UCN 已支持一万、八万或几十万节点实时自组网。

万级发布门禁至少应包括：两级 Locator/隧道实现、混合能力节点、簇头故障与拆并、受控丢包/抖动/非对称拓扑、全网高负载、目标 MCU 资源和真实 Bearer 长稳测试。
