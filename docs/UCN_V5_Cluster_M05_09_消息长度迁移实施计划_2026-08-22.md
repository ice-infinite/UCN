# CLV2-05-09 Cluster 消息长度迁移实施计划（2026-08-22）

## 1. 目标与边界

M05 已有两种严格 Cluster wire：v3 为 32 B、v4 为 40 B。当前生产 FSM 仍只收发 v3，故本项的目标不是把 production Cluster 切换到 v4，而是消除“未来 40 B control payload 无法穿过 UCN transport”的隐性长度假设。

本项只完成以下准备：

1. 将生产 v3 精确长度命名为 `UCN_CLUSTER_WIRE_V3_MESSAGE_BYTES`，保留兼容别名 `UCN_CLUSTER_MESSAGE_BYTES`；
2. 在 v4 public wire header 明确 `UCN_CLUSTER_WIRE_MAX_MESSAGE_BYTES = 40 B`，只供 dual-version transport sizing/测试使用；
3. 核对 generic Adapter/Queue 必须继续按 `UCN_MAX_FRAME_BYTES`，而不是耦合 Cluster 常量；
4. 用真实 UCN Frame + Stream、CAN-FD、Classic CAN Carrier 回归证明 40 B Cluster-sized payload 可以被承载或分段。

明确非目标：不改变 RFC4、不把 v4 raw frame 接进 `ucn_cluster_receive()`/`ucn_cluster_step()`、不修改 Cluster endpoint send path、不启用 encoder、不更改 Node/Adapter runtime 行为、不宣称 40 B payload 已能在所有产品 frame budget 中发送。

## 2. 长度合同

| 常量 | 值 | 所有者 / 用途 |
|---|---:|---|
| `UCN_CLUSTER_WIRE_V3_MESSAGE_BYTES` | 32 B | Current v3 codec 的精确 decode/encode 和 production Cluster payload。 |
| `UCN_CLUSTER_MESSAGE_BYTES` | v3 alias | 保持现有应用/测试源码兼容；含义仍是当前生产 v3 精确长度，不能改为 40。 |
| `UCN_CLUSTER_WIRE_V4_MESSAGE_BYTES` | 40 B | 冻结 RFC4 raw frame 精确长度。 |
| `UCN_CLUSTER_WIRE_MAX_MESSAGE_BYTES` | 40 B | 仅供同时覆盖 v3/v4 的 test/transport capacity sizing；不是 v4 发送开关。 |
| `UCN_MAX_FRAME_BYTES` | 产品配置 | Stream/CAN Source/Adapter Queue 的通用 UCN frame 上界；它们不得依赖 Cluster 模块。 |

因此，“所有地方都把 32 改成 40”是错误的：v3 decoder 必须继续严格接收 32 B；generic adapter 也不应引入 Cluster 依赖。迁移的正确方式是同时存在**精确 wire 长度**和**显式最大 Cluster control payload**。

## 3. Carrier 容量推导

测试固定使用 W0 UCN Frame（17 B header）承载 40 B Cluster-sized payload：总 encoded UCN frame 为 57 B。

| Carrier | 预期 |
|---|---|
| Stream COBS | 57 B frame 可被 COBS 封装、写入 source、解码并提交到 endpoint；无 Carrier-level 分片。 |
| CAN-FD | 57 B frame 可映射到合法 64 B DLC；57..63 的剩余 7 B 必为零 padding。 |
| Classic CAN | 57 B frame 通过既有 START/CONTINUE Carrier 分为 12 个物理帧；每段经 source reassembly 后应还原并提交。 |

带 route/path/E2E 的更长 UCN header 可能超过 CAN-FD 64 B；这不是静默降级。CAN-FD direct carrier 必须返回 `UCN_ERR_TOO_LARGE`，产品应选择 Classic Carrier、其他可分片 Bearer 或更大的 MTU。此项不会试图在 64 B CAN-FD 中塞入不可能的包。

## 4. 实施与自审拆分

| 子项 | 修改 | 自审判据 |
|---|---|---|
| 09-A | 常量别名 / max contract | v3 codec 仍精确 32 B；v4 仍精确 40 B；没有重定义 Core Protocol Version。 |
| 09-B | Stream capacity 回归 | 40 B payload 经实际 source 解码、Adapter Queue、Node endpoint 后到达。 |
| 09-C | CAN capacity 回归 | 同一 40 B payload 覆盖 CAN-FD 64 B padding 与 Classic CAN 12 段重组。 |
| 09-D | 隔离扫描 | production Cluster 没有 v4 API、encoder 默认 0；generic Adapter 无 `ucn_cluster*.h` 依赖。 |

## 5. 验收与后续归属

- v3/v4 长度 alias、Stream、CAN-FD、Classic CAN 三条正向路径通过；
- CAN-FD >64 B 的现有 fail-closed 行为仍保留；
- Full/Lite/Nano、Sanitizer、analyzer 与 diff check 通过；
- 不改变 `ucn_cluster_t`、Cluster FSM、生产队列结构和 Core Wire W0-W3。

Adapter 对 40 B payload 的传输准备不等于 v4 Cluster 协议已生产启用。真正的 v4 RX owner、FSM、资格、Config、quorum、Authority 仍分别归后续 M06-M13。完成本项后仍只能标记 `CODE COMPLETE / AUDIT HOLD（待独立审计）`。
