# UCN 跨节点时间同步与确定性时延建议

> 状态：**建议稿，未实现、未测试**；仅归档动机、方案分层与代价，供后续决策做与不做。
> 日期：2026-08-15
> 适用范围：在 UCN v5 工作树上评估“节点间时间戳/时钟同步 + 有界端到端时延”这一可选能力；本文不承诺把 UCN 变成 EtherCAT 式硬实时总线。

## 1. 为什么写这份建议

以 EtherCAT 的实时性为参照，考虑在通信帧里加时间戳做节点间同步。需要先澄清一个核心事实：

> **时间戳只能“测量”与“补偿”延迟，不能“创造”确定性。**

EtherCAT 的硬实时来自四件事的组合：**单主站周期调度 + 固定拓扑 + 求和帧硬件直穿（on-the-fly）+ 分布式时钟（DC）纳秒级同步**。其中时间戳同步（PTP/802.1AS 思路）只解决“各节点时钟基准对齐”这一块。UCN 的端到端抖动来自：介质本身（ESP-NOW 为 ms 级、UART/CAN-FD 为 us 级）、排队、偶发 RREQ 寻路、Token Bucket 限速、任务调度步进（UCN_STEP 默认 10 ms）。时间戳不能消除这些抖动。

UCN 能力边界文档（UCN_理论能力边界与最终目标.md）口径：

> “UCN 不能把非确定性的 Wi-Fi 变成硬实时总线。微秒级电机闭环必须留在本机；跨节点控制应按目标介质评估，并准备本地失联安全动作。”

因此本文的立场是：**加时间戳得到的是“可测量的有界延迟 + 跨节点可协作”，不是“EtherCAT 式硬实时”**。是否值得做，取决于产品是否有跨节点协作/对齐需求，而不是“想变得实时”。

## 2. 时间戳能做什么、不能做什么

| 能做 | 不能做 |
| --- | --- |
| 测量端到端单程延迟（T1→T2），用于诊断与日志关联 | 消除介质、排队、寻路、调度引入的抖动 |
| 跨节点事件排序（日志、遥测、编队动作） | 在没有预留资源时承诺端到端延迟上界 |
| 有线介质 + 硬件打点下做时钟偏移补偿（us~数十 us 级） | 把无线 + 多跳 + 无预留变成硬实时 |
| 验证“固定路径 + 预留预算”方案实际达到的延迟界 | 替代本地失联安全动作（本机闭环必须保留） |

## 3. 现状核对（2026-08-15 工作树）

| 现状 | 含义 |
| --- | --- |
| v5 基础头 W0~W3 = 17/21/26/30 B，**无时间戳字段** | 要加需扩展帧头或新消息类型 |
| Q0 FIFO / Q1 Latest + deadline（ucn_time.h） | deadline 是**单节点本地语义**（本机过期判断），不是跨节点时间 |
| 各节点时钟为独立的 uint32_t ms 单调时钟 | 无共同时间基准，跨节点事件无法直接对齐 |
| Cluster 控制面已有独立 Token Bucket（FAST 40/s 门限） | 同步报文可复用该预算，不挤占业务 Q0/Q1 |
| UCN_STEP 默认 10 ms → 维护服务上界约 800 ms | 协议任务层打时间戳的抖动会被限制在 ~10 ms 级 |
| Adapter/Port 层没有统一的“线时刻”接口 | 缺硬件时间戳，同步精度上限受制于驱动打点位置 |

## 4. 方案分层

### 4.1 方案 A：单向 T1 时间戳（轻量，先做，推荐起步）

- Q0 帧携带发送方本地 T1（可选字段，+4 B）；接收方记录本地 T2。
- 用途：**端到端延迟估算、日志关联、跨节点事件排序**；让 Q1 Latest 用“帧龄”判断过期，比本地猜 deadline 更准。
- 代价：每帧 +4 B，零状态、零控制面流量、零同步协议。
- 不做任何节点间同步，立即可用、风险最低。

### 4.2 方案 B：轻量主从同步（简化 PTP，有跨节点协作需求时做）

- 时间源（簇头或配置的 Time Master）周期发 SYNC(T1) → 成员记 T2 → 回 DELAY_REQ → Master 回 DELAY_RESP(T4)。
- 四时间戳法：链路延迟 d = ((T2−T1)+(T4−T3))/2，偏移 offset = T2 − T1 − d，成员本地时钟一次补偿；频率补偿可后续加。
- **硬前提：四个时间戳必须在驱动/ISR 层打“线时刻”**，否则抖动毁掉精度（协议任务层打点只有 ~10 ms 级）。
- 代价：Cluster 控制面（0xA0）新增 2 个报文类型、每节点约 12 B 固定状态、每 1 s 约 3 帧流量、Adapter 硬件时间戳接口。
- 预期精度：UART/CAN-FD 有线 **us~数十 us**；ESP-NOW/Wi-Fi 仅 **ms 级**（需实测）。

### 4.3 方案 C：完整分布式时钟（PTP 风格，慎做）

- 方案 B + 频率补偿（速率差）+ 透明/边界时钟（多跳逐跳补偿），最接近 EtherCAT DC。
- MCU + 多跳 + 无线场景下收益/代价比很低；**除非有明确的多节点精密协作需求（编队同步、分布式采样），否则不建议做**。

### 4.4 方案 D：不靠时间戳的“有界延迟”（补充思路）

- 端到端延迟“有界”并不需要时间戳：**Q0 固定路径（PINNED_STRICT）+ 预留 Token 预算 + 无重传 + 固定跳数 + 接收端 deadline 过期丢弃**（UCN 已有 Q1 Latest 语义），有线介质上可给出工程可承诺的 ms 级上界。
- 时间戳在此的作用是**验证和报告这个界**，而不是创造这个界。

## 5. 代价量化

| 代价项 | 估算 | 说明 |
| --- | --- | --- |
| 帧开销 | 每帧 +4 B（仅 T1）或 +8 B（T1+序号/标志） | v5 头 17/21/26/30 B → 21/25/30/34 B；UCN_MAX_FRAME_BYTES 不变时 payload 缩小；100 B 帧 +8 B 约 8% 带宽（只加在 Q0 帧可减半） |
| 内存 | 每节点约 12~20 B 固定状态（时间源 ID、offset、上次同步时刻，可选频率比） | 固定表，无动态内存 |
| 控制面流量 | SYNC/DELAY 每 100 ms~1 s 一次、每次 20~40 B | 复用 Cluster Token Bucket，需在预算内 |
| CPU | 打/读时间戳 + offset 计算 us 级 | 可忽略；真正成本在硬件时间戳 |
| 硬件时间戳（关键） | 协议层打点精度约 10 ms（无价值）；驱动/ISR 打点才有 us 级 | 每个 Adapter 实现“线时刻”接口，属 Port 层工作 |
| 精度上限 | ESP-NOW/Wi-Fi：ms 级；UART/CAN-FD：ISR 打点 us~数十 us | 目标板实测后才能承诺 |

## 6. 落地路线（若决定做）

1. **第一步**：帧头加可选 T1 字段（Q0 帧，+4 B），Node API 暴露 tx_time_ms / rx_age_ms——延迟诊断、日志关联立即受益，零同步复杂度。
2. **第二步**：确有跨节点协作需求时，在 Cluster 控制面加 SYNC/DELAY + Adapter 硬件时间戳接口，做 offset 补偿；有线介质下宣称“us~ms 级节点同步”。
3. **第三步**：确定性靠固定路径 + 预留预算 + 有线介质 + 本地失联安全；时间戳作监控手段。
4. **明确不承诺**：无线 + 多跳 + 无预留下实现硬实时；微秒级闭环留在本机（文档口径）。

## 7. 决策点

- 是否需要**跨节点时间对齐**（日志关联/编队/分布式采样）？→ 需要才考虑方案 B/C。
- 是否只想要**延迟可观测**？→ 方案 A 足够，代价最小。
- 目标介质是否以**有线 UART/CAN-FD 为主**？→ 硬件打点下才值得做高精度同步。
- 是否愿意动 **Adapter/Port 层**加“线时刻”接口？→ 方案 B/C 的硬前提。

> 边界说明：PTP 四时间戳、频率补偿、分布式时钟为通用领域知识，未在本仓库核对外部规范原文；精度数字为工程估计，需目标板实测。
