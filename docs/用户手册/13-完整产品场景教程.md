# 完整产品场景教程

本章把前面的单项 API 组合成可落地的产品方案。示例只展示应用集成边界：产品仍需实现自己的驱动、时钟、持久化、安全 Provider 和业务任务。

## 场景 A：两块小 MCU 通过 UART 固定通信

### 目标

节点 1 读取传感器，节点 2 接收最新状态并下发一个关键命令。拓扑固定，不需要动态发现和多路径。

### 选择

- Feature Profile：Nano。
- Link：每节点一个 UART Stream Source。
- Route：启动时静态添加对端路由。
- Endpoint：状态使用 Q1，命令使用 Q0。
- 运行模型：裸机主循环或单独 Protocol Owner Task。

### 实施顺序

1. 为两块板固定或从 Flash 加载不同 Node ID。
2. 初始化 UART、Ring、Stream Source、Adapter Queue、Link、Node。
3. `ucn_node_register_link()` 后用 `ucn_node_add_route()` 安装对端静态路由。
4. 节点 2 注册状态 Endpoint 和命令结果 Endpoint；节点 1 注册命令 Endpoint。
5. 中断只把 UART 字节写 Ring 并通知 Owner。
6. Owner 先排空 Source，再执行 Node step。
7. 传感器任务用 `ucn_node_send_endpoint()` 发送 Q1 状态；控制任务使用 Q0 命令并等待业务 ACK Endpoint。

### 验收

- 拔掉 UART 后发送返回 Link Down 或路由失败，不出现内存增长。
- 100 Hz 状态下，目标只消费最新值，不排队几秒前的样本。
- 命令结果能用业务 request ID 与原命令对应。

## 场景 B：三到十个 MCU 自动发现和寻路

### 目标

多个传感器节点通过 ESP-NOW、Wi-Fi 数据报或其他 Packet Bearer 自动发现；目标节点不需要预写每条路由。

### 选择

- Feature Profile：Lite。
- Admission：实验室可 Open，产品使用 Provider。
- HELLO：按 Link 使用 Scheduler，加入随机抖动。
- Route：首次发送触发发现，也可由产品提前调用 `ucn_node_discover_route()`。

### 实施顺序

1. 每个物理 Peer/逻辑 Bearer 建立独立 Link 实例。
2. 设置 Node 的 Join Admission Provider，并明确拒绝未知身份的策略。
3. 启动 HELLO Scheduler；不要把心跳转成无界全网洪泛。
4. Owner 周期运行后，通过 Neighbor Summary 确认直连关系。
5. 向非直连目标发送前调用发现；`ucn_node_route_pending()` 为 true 时不忙等，继续执行 Owner。
6. 路由建立后发送 Endpoint 数据，并记录 Route Quality。
7. 关闭中间节点，观察租约失效、RERR/重新发现和业务降级。

### 验收

- 新节点加入不会让所有节点同时高频广播。
- 非直连目标可以经一到多跳到达。
- 中间节点离开后，旧路由被清理，不永久黑洞。
- 未授权 Node 不能仅靠发送 HELLO 获得产品权限。

## 场景 C：网关同时连接 UART、CAN 和 Wi-Fi

### 目标

一个 Full 网关具有两路 UART、一路 CAN-FD 和一个 Wi-Fi Bearer。普通数据自动走最佳路径，关键控制固定走 CAN，批量日志允许分流。

### 选择

- Feature Profile：Full。
- 每个物理实例一个 Link 和 Adapter Queue。
- 关键命令：Pinned Failover 或 Pinned Strict。
- 状态：Auto Best。
- 批量/多流：在可验证路径间 Auto Balance。

### 实施顺序

1. 分别初始化 UART0、UART1、CAN-FD、Wi-Fi Source，并注册四个 Link。
2. 为每条 Link 设置符合介质速率的基础 Cost，并持续提交真实 metrics。
3. 对关键 Endpoint 安装 Policy Path，再安装 `PINNED_FAILOVER` Route Policy。
4. 状态 Endpoint 使用 `AUTO_BEST`，需要会话稳定性时绑定 Q1 Flow Lease。
5. 日志或 Transfer 流量使用独立 Endpoint/Traffic Class，满足容量后才启用 Balance。
6. 查看 Link Quality、Policy Stats 和 Route Quality，验证选择原因。

### 故障演练

- CAN 断开：关键流只在 Failover 允许时切换；Strict 模式必须明确失败。
- Wi-Fi 拥塞：动态 Cost 上升后普通状态可切到 UART，但要经过迟滞/验证窗。
- UART 队列满：不能因此阻塞 CAN Source 的 Owner 预算。

## 场景 D：远端命令一个任务并返回结果

### 目标

节点 A 的业务任务向节点 B 的舵机任务发送命令；B 执行后返回结果。节点内任务和跨 MCU 使用同一 Service 语义，本机消息不绕完整网络协议。

### 消息设计

```c
typedef struct actuator_command {
    uint32_t request_id;
    int16_t target;
    uint16_t timeout_ms;
} actuator_command_t;

typedef struct actuator_result {
    uint32_t request_id;
    int16_t final_position;
    int16_t result_code;
} actuator_result_t;
```

### 实施顺序

1. 为舵机任务绑定 Command Endpoint，为请求方绑定 Result Endpoint。
2. Service Router 初始化后，把两个 Binding 设置为 ready。
3. A 调用 `ucn_service_send()`；远端消息进入 Remote TX Queue。
4. Protocol Bridge 将消息提交给 Node，网络负责寻路、转发和投递。
5. B 的 Bridge 把 Endpoint Frame 交给本地 Service Inbox。
6. 舵机任务调用 `ucn_service_inbox_take()`，校验 request ID、范围、超时和权限后执行。
7. B 用同一 request ID 发送 Result；A 根据 request ID 完成业务事务。

### 重要语义

`ucn_service_send()` 返回 `UCN_OK` 只表示消息所有权被本地 Router 接受；不代表已经跨网，也不代表舵机执行。产品必须自己定义业务结果、超时、幂等和重复命令策略。

## 场景 E：发送 2 KiB 参数或文件块

### 目标

节点 A 向节点 B 发送 2 KiB 参数块，要求完整性校验、超时和明确完成结果。

### 选择

- 构建 `ucn_transfer`。
- 使用 T2K class。
- A 提供至少一个 TX Slot；B 提供匹配的 RX Slot 与缓冲。
- Peer window 从 1 开始，实测稳定后再提高。

### 实施顺序

1. Node 和 Endpoint 先初始化并证明小包正常。
2. 初始化 Transfer，设置同一个单调时钟和 Peer capability。
3. B 注册 Transfer 接收回调；回调处理完后释放 RX handle。
4. A 调用 `ucn_transfer_send()`，并保持发送缓冲不可修改，直到 completion。
5. Owner 每轮先处理 Core；只有 Core 报当前无工作时再调用 `ucn_transfer_step()`。
6. completion 成功后，业务再校验参数版本、内容摘要和应用条件。

### 验收

- 中途断链后得到明确失败或在有界次数内恢复，不永久占用 Slot。
- B 忘记 release 时，统计能显示 RX Slot 压力并在有界保持期后处理。
- 相同 T2K 在 1/2/3 跳分别记录吞吐、P99 延迟和重试，不只看平均值。

## 场景 F：按 Endpoint 开启安全

### 目标

传感器状态允许明文，控制命令和参数更新必须认证加密；中间节点只按外层路由信息转发密文。

### 实施顺序

1. 产品实现 AEAD、RNG、Key Lookup、序列持久化和 ACL Provider。
2. 初始化 Security，再把 Node 接入安全上下文。
3. 默认策略设为拒绝未知受保护流。
4. 为命令和参数 Endpoint 安装 required override；状态 Endpoint 按产品风险选择明文或安全。
5. 验证中间节点不需要解密业务内容，目标节点才能认证并交付。
6. 测试错误 Key、篡改、重放、序列掉电恢复和权限拒绝。

## 组合产品的最终检查

无论采用哪个场景，发布前都应回答：

- Node ID、Session ID、Endpoint、Service ID 如何分配和持久化？
- 哪些消息是 Q0，哪些是 Q1，谁负责消费和业务 ACK？
- 无路由、队列满、断链、重放和安全失败时业务如何降级？
- 每个 Link 的基础 Cost、动态指标、切换迟滞和最大跳数是多少？
- 目标 MCU 的 Flash、RAM、栈、CPU、吞吐、P99 延迟是否实测？
- 诊断接口是否默认授权关闭，是否可能泄露拓扑或密钥信息？
