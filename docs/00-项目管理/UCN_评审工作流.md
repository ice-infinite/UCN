# UCN 评审工作流（分级冗余度）

> 原则：证据优先、测试门禁、按任务规模决定评审冗余度。每个交付物必须带可复现证据（测试/门禁输出），评审只认证据不认描述。

## 1. 任务分级

| 档位 | 适用 | 角色 | 流程 |
|---|---|---|---|
| 小修复（S） | 单点缺陷修复、文档/注释、≤2 个函数的小改 | 1 复现 + 1 规格 + 单写手 + **双对抗评审**（5 角色） | 复现（测试先行，红）→ 规格（期望行为/禁止事项清单）→ 写手实现（测试转绿）→ 双评审对抗 → 提交 → 人终审 |
| 大实现（L） | 新子系统、跨文件重构、M03+ 级语义改动 | 1 复现 + 1 规格 + **双写手** + **三评审**（7 角色） | 复现 → 规格 → 双写手并行（任务切分明确）→ 三评审（语义/测试/一致性）→ 提交 → 人终审 |

## 2. 角色职责

- **复现 Agent**：测试先行。把缺陷/需求写成能红的测试或门禁脚本；交付：失败的测试 + 失败证据。
- **规格 Agent**：把任务书翻译成可检查规格：允许/禁止边、验收标准、MUST NOT 清单（对照方案文档任务行与历次审计决定）。交付：规格清单。
- **写手 Agent**：只实现规格要求，不得越界；交付：diff + 自验证证据（构建/测试/golden）。
- **对抗评审**：按证据审查（复现测试是否真红/真绿、是否越界、是否引入新语义）；交付 PASS/CONDITIONAL/HOLD + 发现清单。
- **双写手**：大实现按模块切分并行写；交付前由各自自验证 + 合并验证。

## 3. 门禁（所有档位通用）

1. 测试先行：先有失败测试（或等价门禁），写手才动生产代码；
2. Golden Trace 37 行逐字节不变（M01 期间）；
3. clean 6 路矩阵 ALL PASS（full/lite/nano/asan/analyzer/core_only，tools/m00_matrix.sh）；
4. -Wall -Wextra -Wpedantic -Werror 零告警；
5. 评审全 PASS 后才提交推送 GitHub；用户终审后才算关闭。

## 4. 档位判定

- 生产 diff 行数 ≤ 60 且函数 ≤ 2 且无新文件 → S 档；
- 其余（新子系统、跨文件、语义层改动、新测试文件成体系）→ L 档；
- **豁免条款（S 档特例）**：纯新增、零协议行为变更的代码（Golden Trace 逐字节不变 + 无生产调用点 + 未接线），即使行数/函数数超过 S 阈值，仍按 S 档执行（单写手 + 双对抗评审）；判定依据以 commit 时的 golden/行为证据为准，并在 OP 记录中声明豁免理由；
- 边界情况取 L 档（宁可多审，不可走偏）。

## 5. 并行化规则（写面串行、读面并行）

- 可并行：多个评审 Agent（同一快照、不同视角）；只读分析（检查清单、规格核对、规模模拟、文档整理）；互不冲突的独立交付（不同仓库/目录）。
- 不可并行：多个写手同时改同一 git 工作树（diff 互相踩）；评审与写码同时进行（评审对象漂移，证据必须对应确定快照）；同一文件的任何双写。
- 顺序门禁（Code→审→修→复审→提交→人终审）不可打散：Golden/矩阵证据链要求逐步验证。
- M02 拆模块后，跨模块大实现可用 `git worktree` 隔离工作树实现并行写（L 档双写手）；单模块内仍串行。
- 并行只读任务的结果必须标注其基于的工作树快照（commit/未提交状态），防止证据混淆。

## 6. 记录

- 每轮交付在 docs/00-项目管理/01-项目操作记录.md 记 OP 编号；
- 档位判定、角色名单、评审结论与发现随 OP 记录；
- 评审 C（任务与设计一致性）按本文档核对流程符合性。
