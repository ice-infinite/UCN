# 资源、性能与参数调优

UCN 采用静态容量和固定所有权，资源上限应在产品设计阶段确定。调优的目标不是把所有宏设到最大，而是在目标 MCU 的 RAM、Flash、实时性和最大网络规模之间取得可验证的平衡。

## 1. 先确定产品负载模型

在修改任何容量前，先写出以下表格：

| 项目 | 产品需要回答的问题 |
| --- | --- |
| 节点规模 | 本节点直连多少 Peer，全网大约多少节点 |
| Link 数量 | UART、CAN、Wi-Fi 等物理实例各有几条 |
| 跳数 | 正常、最坏和允许的最大跳数 |
| 消息模型 | Endpoint 数量、频率、大小、Q0/Q1/Q2/Q3 占比 |
| 大消息 | 是否需要 T128～T8K、最大并发和接收保持时间 |
| 任务通信 | 本地 Service 数量、Q0 深度、Q1 Latest 数量 |
| 安全 | 哪些 Endpoint 必须受保护，密钥和序列保存在哪 |
| 诊断 | 是否允许远程 Trace/Snapshot，最大分页大小 |

没有这张表时，增加内存只能暂时隐藏背压，不能证明系统稳定。

## 2. Profile 与资源基线

| Profile | 适合的产品 | 资源策略 |
| --- | --- | --- |
| Nano | 固定拓扑、小 MCU、单跳或静态路由 | 只保留 Core 必需表，动态能力返回配置错误 |
| Lite | MCU 自组网、动态邻居和路由 | 为 Neighbor、Route 和控制面预留固定容量 |
| Full | 多介质、策略、路径、负载均衡 | 在 Lite 基础上增加 Policy、Path 和质量快照 |

Wire Profile W0～W3 决定线上的地址/字段能力，Feature Profile 决定本机编译进哪些功能。两者不能混为一谈。低资源节点可以接收其 Wire 能力范围内的帧，但不能因为“网络里存在高级节点”就自动获得本机未编译的 Full API。

## 3. 主要静态容量旋钮

实际宏名和默认值以产品配置头及 `include/ucn` 为准。调优时重点核对以下类别：

- Link、Bearer 与 Endpoint handler 数量。
- Neighbor、Route、Pending Discovery、去重记录数量。
- Q0 FIFO、Q1 Latest、Q2 Normal FIFO、Q3 Bulk FIFO 与 Adapter RX Queue 深度。
- Full 的 Policy Path、Route Policy、Flow Binding、Path Forward 数量。
- Event Runtime Source 数量与每轮 Source/Owner 预算。
- Service Binding、Inbox 和 Remote TX 数量。
- Transfer TX/RX Slot、Peer Capability、总缓冲字节、窗口和并发数。
- 安全会话、ACL、Key Slot 与持久序列槽位。

配置调整顺序建议为：先缩小实际产品不需要的表，再增加已被测试证明会满的表；每次只调整一个容量族，并重新记录对象大小、链接映射和最坏延迟。

## 4. 在目标板上测量资源

Host 的 `sizeof` 只能用于比较版本变化，不能代替 MCU 结果。目标板至少收集：

1. 链接后的 Flash text/rodata/data/bss。
2. `ucn_node_t`、Link、Adapter Queue、Runtime、Service、Transfer 和 Security 对象大小。
3. Protocol Owner、Driver/ISR 下半部、业务任务的栈高水位。
4. 各静态内存池的峰值占用和拒绝次数。
5. 关闭日志与开启日志两种情况下的 CPU、延迟和吞吐。

推荐把对象放在显式的静态产品上下文中：

```c
typedef struct product_ucn_context {
    ucn_node_t node;
    ucn_link_t links[PRODUCT_LINK_COUNT];
    ucn_adapter_rx_queue_t rx_queues[PRODUCT_LINK_COUNT];
    ucn_event_runtime_t runtime;
#if PRODUCT_ENABLE_SERVICE
    ucn_service_router_t service;
    ucn_service_protocol_bridge_t bridge;
#endif
#if PRODUCT_ENABLE_TRANSFER
    ucn_transfer_t transfer;
#endif
} product_ucn_context_t;

static product_ucn_context_t g_ucn;
```

这样 map 文件和链接器报告能直接显示 UCN 的静态占用，避免隐藏的堆分配。

## 5. 吞吐为什么低于物理波特率

物理波特率不是业务载荷吞吐。近似预算为：

```text
有效吞吐 = 物理速率
         × 物理编码效率
         × Carrier效率
         × UCN帧载荷比例
         × ACK/重试效率
         × 调度占空比
         × 多跳空间复用效率
```

UART 还包含起止位；Classic CAN 需要多帧 Carrier；安全会增加认证字段；Transfer 有分片头、确认与重试；多跳的同一半双工介质可能需要逐跳转发。因此不能用 `3 Mbit/s ÷ 8` 直接当成应用层 KiB/s。

多跳性能还受拓扑影响：不同 Bearer 可以并行，同一共享无线信道上的相邻跳通常不能同时无冲突发射。增加一跳的损失不是协议头长度的固定百分比，而是链路、调度、重试和空间复用共同结果。

## 6. 延迟预算

一条业务消息的最坏延迟至少包含：

```text
生产任务等待
+ 本地队列等待
+ Owner 唤醒延迟
+ 编码和安全处理
+ 每跳介质排队与传输
+ 转发节点 Owner 调度
+ 目标投递与业务任务唤醒
```

Q0 适合必须可靠排队的关键命令，Q1 适合只关心最新值的实时状态，Q2/Q3 适合普通和批量数据。把高频 IMU 样本全部放入 Q0，会让旧样本排队并放大控制延迟；通常应使用 Q1 Latest 或业务侧降采样。

## 7. 调优顺序

### 7.1 第一层：硬件和驱动

- 使用中断/DMA/SDK 回调驱动 Ring 或物理帧队列。
- 确保 ISR 只搬运和通知，不执行 Node/Service/Transfer。
- 测量真实线速、错误率、FIFO overflow 和总线恢复。
- 先证明单 Carrier 连续收发稳定，再测 UCN。

### 7.2 第二层：Protocol Owner

- 外设事件到来应立即唤醒 Owner。
- 给 Q0～Q3、Source、Node maintenance、Transfer 设置有界预算。
- 避免某个高流量 Source 长期饿死其他 Bearer。
- 兜底轮询周期只负责漏事件和 deadline，不应成为主要数据路径。

### 7.3 第三层：消息和队列

- 高频状态优先 Q1 Latest。
- 关键命令使用 Q0，但要限制生产速率和重试次数。
- 普通参数/查询使用 Q2 FIFO；批量或可延后的小消息使用 Q3 FIFO。
- 大消息使用合适的 Transfer class，不要一律申请 T8K。
- 窗口大小必须与 Peer RX Slot、MTU、错误率和 Owner 预算匹配。

### 7.4 第四层：路由与 Cost

- 先配置符合物理现实的静态基础 Cost。
- 再启用基于占用、错误、延迟和稳定性的动态增量。
- 使用迟滞、验证窗和 Lease，避免指标轻微变化就切换路径。
- 关键流可固定路径或 Failover；大流量再考虑 Balance。

## 8. 推荐性能测试矩阵

| 维度 | 最少测试点 |
| --- | --- |
| 消息大小 | 单帧最小/最大、T128、T512、T2K、T8K（若启用） |
| 跳数 | 1、2、3 跳及产品最大允许跳数 |
| Bearer | 每种单独测试，再做混合并发 |
| 交通类别 | Q0、Q1、Q2/Q3、Transfer 并发 |
| 网络状态 | 稳态、节点加入、节点离开、链路抖动、重路由 |
| 安全 | 明文、受保护、安全失败与重放 |
| 压力 | 单流满载、所有节点满载、队列背压、长时间运行 |

每次记录：有效载荷吞吐、P50/P95/P99 延迟、丢弃、重试、队列峰值、路由切换、CPU、栈、功耗和温度。只报告平均吞吐无法判断实时控制是否可用。

## 9. 调优完成条件

- 最坏产品负载下没有未解释的队列溢出。
- Q0 延迟和丢失满足业务门限，Q1 不积压旧状态。
- 所有表和 Slot 到达上限时 fail-closed，而不是越界或动态扩容。
- 断链和重路由期间，关键业务有明确的中断、重试或降级语义。
- 性能结论来自目标 MCU 与实际 Bearer，不把 Host 模拟数据当作实机结论。
