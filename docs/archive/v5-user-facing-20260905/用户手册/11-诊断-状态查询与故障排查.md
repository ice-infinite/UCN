# 诊断、状态查询与故障排查

本文面向已经完成基本收发、但需要回答“为什么没有入网、为什么没有路由、数据停在哪一层、为什么变慢”的产品集成人员。诊断的原则是沿数据实际经过的层逐层缩小范围，不要一上来就修改 Cost、超时或队列容量。

## 1. 先确定故障停在哪一层

一条入站消息通常经过：

```text
外设/SDK回调
  -> Driver Ring 或物理帧队列
  -> Stream/CAN Source
  -> Adapter RX Queue
  -> Protocol Owner
  -> Node 解码、去重、转发或本地投递
  -> Endpoint / Service / Transfer
  -> 业务任务
```

出站方向则相反。排查时从最靠近硬件的一层开始确认“是否收到”，再向上移动。若 Adapter 从未收到数据，继续调整路由策略没有意义；若 Node 已完成本地投递，问题就不在网络层。

建议每个产品至少提供以下只读诊断页：

| 页面 | 数据来源 | 主要回答的问题 |
| --- | --- | --- |
| Driver | BSP/SDK 计数器 | 中断、DMA、FIFO、总线错误是否正常 |
| Adapter | `ucn_adapter_rx_get_stats()` | 物理数据是否进入 UCN，是否队列满 |
| Owner | `ucn_event_runtime_get_stats()`、`ucn_event_runtime_get_owner_stats()` | Owner 是否被唤醒，预算是否耗尽 |
| Node | `ucn_node_get_stats()` | 解码、投递、转发、路由请求发生了什么 |
| Neighbor/Route | Neighbor 摘要与 Route Quality | 是否入网，是否有可用下一跳 |
| Policy | Link Quality 与 Policy Stats | 为什么选择或拒绝某条链路 |
| Service/Transfer | 各自 Stats | 消息是否堵在本地服务或分片层 |

所有查询最好都由唯一 Protocol Owner 执行，或者由产品把 Owner 中取得的只读快照复制给诊断任务。不要让 Web、Shell、CLI 任务直接并发遍历 `ucn_node_t` 内部表。

## 2. 本地统计查询

### 2.1 Node 与 Adapter

```c
const ucn_node_stats_t *node_stats = ucn_node_get_stats(&node);
const ucn_adapter_rx_stats_t *rx_stats = ucn_adapter_rx_get_stats(&rx_queue);
```

返回值是对象内部只读指针，生命周期跟随对象；调用方不得释放或修改。读取一组相关字段时，应在 Owner 上下文内完成或复制成产品自己的快照，避免统计在打印过程中变化。

诊断顺序：

1. Driver 收包计数不增长：检查引脚、波特率、CAN 位时序、Wi-Fi Peer、IRQ/DMA。
2. Driver 增长而 Adapter 不增长：检查 Source 是否被唤醒、Carrier 解帧和提交回调。
3. Adapter 入队增长但 Owner 不处理：检查事件通知、Owner 优先级、每轮预算和兜底定时器。
4. Owner 已处理但 Node 报 malformed/CRC/version：检查两端 Wire Profile、MTU、Carrier 与构建版本。
5. Node 已本地投递但业务没收到：检查 Endpoint handler、Service ready 状态或 Transfer RX release。

### 2.2 Event Runtime

```c
const ucn_event_runtime_stats_t *rt =
    ucn_event_runtime_get_stats(&runtime);
const ucn_protocol_owner_stats_t *owner =
    ucn_event_runtime_get_owner_stats(&runtime);
```

重点观察：事件是否产生、某个 Source 是否长期占满预算、Owner 是否依赖兜底轮询才工作、待处理标志是否持续不归零。正常系统应主要由外设事件唤醒，定时器负责协议 deadline 和漏通知保底，而不是持续空轮询。

### 2.3 Service 与 Transfer

```c
const ucn_service_stats_t *svc = ucn_service_get_stats(&service_router);
const ucn_service_bridge_stats_t *bridge_stats =
    ucn_service_protocol_bridge_get_stats(&service_bridge);
const ucn_transfer_stats_t *xfer = ucn_transfer_get_stats(&transfer);
```

若 Q0 Inbox 或 Remote TX 经常满，首先降低生产速率、提高消费任务优先级或将连续状态改为 Q1 Latest；不要直接把所有队列放大。Transfer 超时时，还要同时查看 Core 路由、窗口能力、RX Slot、完成回调和底层 Link 的队列状态。

## 3. 邻居、路由和链路质量

### 3.1 查看直连邻居

先查询数量，再复制到产品提供的静态数组：

```c
size_t count = ucn_node_copy_neighbor_summaries(&node, NULL, 0U);

ucn_neighbor_summary_t summaries[PRODUCT_DIAG_NEIGHBOR_LIMIT];
size_t copied = ucn_node_copy_neighbor_summaries(
    &node, summaries, PRODUCT_DIAG_NEIGHBOR_LIMIT);
```

`count` 可能大于产品显示上限，界面必须同时显示“总数”和“本页数量”，不能把截断后的数组误称为全网节点表。Neighbor 只表示本地已知的直连关系，不等于整个网络拓扑。

### 3.2 查看到目标的路由质量

```c
ucn_route_quality_t quality;
ucn_result_t rc = ucn_node_get_route_quality(&node, target, &quality);
```

`UCN_OK` 表示当前存在可报告的 Route Quality；`UCN_ERR_NOT_FOUND` 表示此刻没有可用路由记录。它不保证下一帧一定成功，链路状态、租约和队列可能在之后变化。

Full Profile 还可读取：

```c
const ucn_policy_link_quality_snapshot_t *link_quality =
    ucn_node_get_link_quality(&node, &uart_link);
const ucn_policy_stats_t *policy_stats = ucn_node_get_policy_stats(&node);
```

排查“为什么没走 Cost 最低的链路”时，还要核对：路由是否满足 MTU/Wire Profile、是否被固定路径策略约束、是否正在 Q1 Flow Lease 内、链路是否过载、是否处于验证或故障恢复状态。最小静态 Cost 只是基础值，不是唯一决策依据。

## 4. 远程诊断控制帧

路径追踪、节点快照和 Policy 诊断是低频管理功能，不能替代常态遥测。远端必须显式安装 Authorizer：

```c
ucn_node_set_path_trace_authorizer(&node, authorize_trace, context);
ucn_node_set_node_snapshot_authorizer(&node, authorize_snapshot, context);
ucn_node_set_policy_diagnostic_authorizer(&node, authorize_policy, context);
```

发起查询：

```c
ucn_node_request_path_trace(
    &node, target, PRODUCT_TRACE_RECORD_LIMIT, on_trace, context);

ucn_node_request_node_snapshot(
    &node, PRODUCT_SNAPSHOT_RESULT_LIMIT, on_snapshot, context);

ucn_node_request_policy_diagnostic(
    &node, target, section, index, on_policy_page, context);
```

使用规则：

- Authorizer 默认拒绝，产品按来源节点、角色和维护模式放行。
- 查询结果是有界记录或分页结果，不是永久完整拓扑数据库。
- 诊断帧优先级低于正常 Q0/Q1 工作，网络忙时允许延迟或超时。
- UI 必须显示查询时间、来源节点、是否截断和是否过期。
- 不允许自动高频轮询全网快照，否则诊断本身会变成网络负载。

## 5. 常见故障决策表

| 现象 | 第一检查点 | 常见原因 | 建议动作 |
| --- | --- | --- | --- |
| 两节点看不到彼此 | Driver、Adapter、HELLO | 接线/Peer 错、Source 未运行、Wire 不兼容 | 先做点对点 Carrier 回环，再开动态发现 |
| 有邻居但发不出去 | Route Quality、route pending | 尚未寻路、约束不满足、路由租约过期 | 调用发现并持续运行 Owner，不要忙等 |
| 只有小包成功 | Link MTU、Transfer 能力 | 单帧上限、分片未启用、Peer class/window 未配置 | 使用 Transfer 并核对两端容量 |
| 经常 `UCN_ERR_NO_SPACE` | 各层队列统计 | 生产快于消费、Owner 预算不足 | 先限流/提速消费，再评估容量 |
| 经常 `UCN_ERR_LINK_DOWN` | Link/Driver 状态 | 物理静默、总线错误、Peer 离线 | 保留重试边界并触发重新选路 |
| 路由频繁切换 | Link Quality、Policy Stats | 指标抖动、切换迟滞过小 | 调整采样、验证窗和迟滞，不只改静态 Cost |
| Transfer 超时 | Core 路由、窗口、RX Slot | Owner 调度顺序错、窗口过大、目标未 release | 先 Core 后 Transfer；核对完成/释放回调 |
| 安全帧全失败 | Security Stats/Provider | Key ID、序列持久化、ACL、AEAD 不一致 | 在测试环境逐项验证 Provider 合同 |
| 本机任务收不到 | Service ready/Inbox | 任务未 ready、Endpoint 未绑定、Q0 已满 | 先检查绑定与 ready，再检查 Bridge |

## 6. 推荐的现场日志格式

每条故障日志至少包含：

```text
time_ms node_id session_id ingress_or_egress_link
peer_id endpoint traffic_class result
route_or_path_id wire_profile payload_length
owner_iteration queue_depth reason
```

不要打印密钥、明文安全载荷或完整设备身份凭据。高频路径使用计数器和采样日志，避免串口打印本身拖慢 Owner。

## 7. 故障排查验收

产品集成完成前，应证明：

1. 可以区分“物理未收”“Adapter 堵塞”“无路由”“本地业务未消费”。
2. 队列满、链路断开、CRC 错、版本错和安全拒绝都有不同计数或日志原因。
3. 远程诊断默认关闭，授权后有界，忙时不会抢占 Q0/Q1。
4. 所有诊断快照都标注时间和截断状态。
5. 关闭调试日志后，协议行为与队列容量不发生变化。
