## 当前最高优先级边界

- UCN 以 MCU 独立组网为主，不依赖 Linux；Linux/ROS 2 是可选 Host/Bridge。
- 仓库提供 SDK 无关的 Stream 与 CAN/CAN-FD Source，但不直接打开 UART、Wi-Fi、CAN 控制器或配置引脚。
- Core 安全层定义 Policy 与 Provider，不内置可直接宣称生产安全的身份、密钥和 AEAD 实现。
- 默认 `ucn_cluster` 使用 Cluster Wire v3/32 B；Wire v4/40 B 与 M10/M11/M13 仍有显式隔离和默认关闭边界。
- 当前软件矩阵、Host 模拟和部分 ESP32-S3 实测不能代替真实 Flash 掉电、无线多 Bearer、长期功耗和发布验收。

## 如何判断一句话是否代表“已经可用”

官方文档把能力拆成四层，避免把“源码中存在”误读成“产品已经可发布”：

1. **合同已定义**：头文件、Wire 或配置规范已经给出确定输入、输出和失败语义，但可能仍未接入默认产品路径。
2. **软件已验证**：已有单元、模拟、静态分析或 Host 集成证据；这证明模型在对应构建条件下成立，不自动覆盖目标 MCU、驱动和物理介质。
3. **实机已验证**：报告绑定具体固件、板卡、接线、速率和测试时长；结论只适用于该台架，不向未测 Bearer 或规模外推。
4. **发布已放行**：兼容性、资源、掉电、安全、回滚和发布矩阵全部签字。当前 Cluster Wire v4 等能力仍未到这一层。

每篇正文开头的“文档级别、实现状态、适用版本、最近核对”用于定位该文档属于哪一层；正文中的限制与证据段进一步说明结论覆盖范围。

## 信息冲突时的裁决顺序

读者遇到历史建议、审计报告、操作记录与官方文档说法不一致时，按以下顺序判断：

1. 当前 checkout 的公共头、实现与构建开关；
2. 本目录与当前提交绑定的官方文档；
3. `docs/evidence` 中绑定固件、硬件和日志的证据；
4. 项目任务表与操作记录；
5. `docs/archive` 中的历史建议和阶段性审计。

历史材料可以解释决策来龙去脉，但不能单独证明当前行为。若发现本目录与源码不一致，应先把差异登记到任务表，再更新官方正文、证据链接和操作记录，不能只改其中一处。

## 面向不同读者的入口

- 方案负责人先看项目总览、总体架构、能力成熟度和发布边界。
- MCU/RTOS 集成人员先看配置与资源、API 参考、平台集成和 Adapter 合同。
- 协议开发者先看核心协议、路由、传输、Cluster 与兼容迁移章节。
- 测试与审核人员先看诊断、测试矩阵、证据等级、兼容性和发布清单。
- 现场运维人员从诊断章节的状态快照、故障索引和恢复步骤进入，再回查对应模块合同。
