## 主要构建产物

| Target | 默认进入普通构建 | 责任 |
| --- | --- | --- |
| `ucn_core` | 是 | Core、Node、Transport、Source、Profile 选择、可选 Service |

## Profile 对源码的影响

- Nano：`src/node/ucn_node_nano.c`；不加入 `src/routing/ucn_path.c` 和 `ucn_policy.c`。
- Lite：动态 Mesh Node，但不编译 Full Path/Policy；关闭 API 由 Stub 失败关闭。
- Full：Node + Candidate + Path + Policy + Diagnostics。
- `UCN_FEATURE_SERVICE` 与 Profile 正交，关闭时不加入 Service 源码。

## 产品链接原则

最小产品只链接 `ucn_core` 和一个所需 Port。按需再链接 Transfer、Cluster 或 Federation。Linker 不拉入的 Archive 不增加产品代码；对象 RAM 只有产品实际实例化才占用。

实验 target 必须通过显式 CMake option 构建，并不因为公共头存在就自动进入默认产品。

## 直接源码构建

不使用 CMake 时，所有翻译单元必须看到一致的 `UCN_PROFILE`、`UCN_FEATURE_SERVICE` 和用户配置宏，否则公共对象布局可能不一致。推荐把配置作为全局编译定义，而不是在单个 `.c` 文件前临时 `#define`。

## 1. 从源码到固件的关系

```text
公共头 + 产品配置
        ↓
ucn_core / 可选archive / port target
        ↓
产品 BSP、Driver、应用对象
        ↓
最终 ELF/MAP/BIN
```

CMake “构建了一个静态库”不等于链接器把其中全部对象拉入固件；反过来，应用实例化大型 public storage 才会真正产生对应 RAM。

## 2. 最小产品组合

| 产品需求 | 建议链接 |
| --- | --- |
| 固定点对点小消息 | `ucn_core` + 一个 Port/BSP |
| 自动 Mesh | Lite/Full `ucn_core` + Adapter/Source |
| 任务 Service | 上述 + `UCN_FEATURE_SERVICE=ON` |
| 8 KiB 消息 | 上述 + `ucn_transfer` + 静态 slot |
| Current Cluster | 上述 + `ucn_cluster` + persistence/安全配置 |
| Host 规模测试 | core/cluster + simulator target，不进入 MCU 固件 |

## 3. 实验 target 的隔离

M10/M11/M13 需要显式 CMake option。实验头也通过宏门禁阻止普通生产文件误包含。审计时不仅检查 option，还要搜索默认 `ucn_cluster` 是否引用实验符号。

Wire v4 optimized release gate 是测试 target；其 encoder enable 宏不能作为 public compile definition 传播给 `ucn_cluster`。

## 4. Profile 的编译效果

Nano 使用独立精简 Node 实现；Lite/Full 共享动态 Mesh 主体但 Full 加入 Candidate/Path/Policy/Diagnostics。关闭功能的 Stub 保留必要公共符号并返回明确错误，避免应用在链接阶段才发现 Profile 不兼容。

Profile 宏会影响公开对象布局，因此库和应用必须同配置。常见错误是：库按 Nano 编译，应用头按 Full 编译，链接成功后却以不同偏移访问 storage。

## 5. 推荐构建目录

```text
build_full_debug/
build_full_release/
build_lite/
build_nano/
build_service_off/
build_product_x/
build_asan/
build_analyzer/
```

不要在同一构建目录反复切换 Profile 后继续使用旧对象。每个发布证据保存 configure 输出、compile definitions 和 CTest 列表。

## 6. 如何确认功能是否真的进入固件

1. 查看 CMake option 和 target link；
2. 检查静态库符号；
3. 查看最终 link map 和 section；
4. 检查产品是否实例化对象；
5. 运行启动日志/API view；
6. 通过行为测试，而不是只看编译成功。

## 7. 源码目录的维护规则

- 平台文件只放 `src/ports` 或产品 BSP；
- 通用 carrier/source 放 `src/adapters`；
- 业务协议不进入 `src/core`；
- 默认关闭的研究模型有独立 target；
- 公共 API 放 `include/ucn`，私有 helper 不被产品包含；
- 每个新增 target 同步 API 链接测试、Profile 组合和文档映射。
