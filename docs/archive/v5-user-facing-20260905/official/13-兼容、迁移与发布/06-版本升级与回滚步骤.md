# 版本升级与回滚步骤

> 文档级别：`NORMATIVE`
> 实现状态：`CURRENT（规则）；RELEASE NO-GO`
> 适用版本：UCN 5.0.0 / Core Wire v5
> 事实源：版本宏、Wire/API/Storage 合同、CMake 与发布门禁
> 最近核对：`codex/v5-adaptive-wire@a093862`，2026-08-25
> 硬件状态：完整发布实机门禁未完成

1. 冻结候选 commit、配置、工具链和固件 hash；
2. 检查 Wire/API/ABI/Storage 兼容矩阵；
3. 备份诊断与持久化状态；
4. 小范围升级并观察入网、路由、业务和 Cluster；
5. 扩大灰度；
6. 失败时隔离节点，按既定策略回滚固件与 Record。

Cluster/Wire 跨版本不得无计划全网同时切换。旧固件无法识别新 Record 时不能只刷旧 bin。

## 1. 形成升级清单

对每种设备列出当前→目标：project、Core Wire、API/Port、Cluster Wire/API、Record schema、Profile、产品配置和bootloader。标记是否需要全量同时升级、是否支持混跑、Storage是否迁移。

## 2. 准备发布包

包含目标固件与hash、上一稳定固件、配置/分区、迁移/检测工具、兼容矩阵、回滚判定、串口/救援步骤和已知问题。发布包在离线台架完成升级→断电→回滚演练。

## 3. 升级前Fence与备份

关键Head/执行器先停止接受新命令、撤销/Fence Authority，导出诊断和Record header。普通节点停止业务并等待队列/Transfer完成或明确Abort。不要在写Config/Record中途直接OTA重启。

## 4. Canary

先选非关键、可现场恢复的节点。升级后验证：启动/迁移、Node ID/session、Link、Neighbor、Route、业务、安全、资源和长稳。Cluster网络先升级codec接收能力，不立即启用新Authority。

## 5. 分批扩大

按故障域/Cluster分批，保持每批后仍有可用quorum和回滚通道。记录每台固件hash和完成时间；失败率/错误计数超过预设阈值自动暂停，不继续滚动。

## 6. 回滚

先隔离失败节点并判断Wire/API/Storage。旧固件可读当前Record时整体刷回；不可读则运行官方向下迁移，或受控擦除并生成新identity。禁止只替换library/应用一半。

## 7. 回滚后验证

确认旧网络不接受新格式、没有Node/Cluster/session/sequence复用、Route/Directory清理旧locator、业务和安全策略恢复。保留失败候选板和原始Storage供分析。

## Cluster特殊顺序

升级Head前先确保Backup/其他voter处于兼容状态；Joint Config按旧/新集合双quorum迁移；v3 legacy只能non-voting。若M05未放行，不执行生产v4Authority升级。

## OTA失败安全

bootloader应验证签名/hash、A/B镜像和启动确认。应用迁移Record失败时不应反复写坏介质或进入网络；救援固件保持最小有线诊断和只读导出能力。

## 记录

每次升级形成设备清单、开始/结束、版本前后、迁移结果、测试、异常、是否回滚及最终状态。这样后续可以回答“哪块板运行哪份协议”。
