# 升级、回滚与持久化介质处理

> 文档级别：`GUIDE`
> 实现状态：`CURRENT（诊断方法）`
> 适用版本：UCN 5.0.0 / Core Wire v5
> 事实源：状态视图、统计 API、测试与现有实测记录
> 最近核对：`codex/v5-adaptive-wire@a093862`，2026-08-25
> 硬件状态：部分实测；未测项不得推断

升级前保存固件/配置 hash、Wire/API/Storage 版本和持久化诊断。新固件首次启动按 schema 迁移；未知或不可安全迁移的 Record 应 fail-closed，并由产品流程决定擦除或恢复。

回滚前确认旧固件能理解当前 Record、Node ID/Session 和 Cluster Tombstone。不能理解时先隔离网络，避免旧身份和序列重用。

## 升级前采集

- 当前/目标固件commit、version、build config和hash；
- Core/Cluster Wire、Port/API、Storage schema；
- Node ID、plain/security session、next sequence区间；
- Cluster Active/Max Epoch、Config、Record generation、Tombstone；
- 各Link/Route状态和关键错误计数；
- 双槽原始header/CRC（敏感内容按安全策略处理）。

备份用于恢复/审计，不表示可以把旧Record写回任意新固件。

## 首次启动迁移

新固件应先离网读取双槽，选择最新有效generation，严格decode旧schema，生成canonical新state并原子写新槽，reload验证后才建立新boot incarnation并联网。未知schema/脏缺省/serial非法必须fail-closed。

legacy PREPARED迁移只能匹配明确旧格式；未来真实新PREPARED不能被自动abort。schema或来源无法区分时需要升级schema或人工恢复流程。

## 回滚决策

```text
旧固件能读当前schema且理解Tombstone/session?
  ├─是：先Fence，刷回，load验证，再重新入网
  └─否：是否有官方向下迁移工具?
       ├─是：离网原子迁移后回滚
       └─否：导出诊断，受控擦除并以新identity加入
```

受控擦除必须同时考虑Cluster ID历史和Security nonce。只擦Cluster Record却保留旧session，或反之，都可能产生身份复用。

## 双槽介质操作

永远写非当前槽：erase→program完整record→校验→写commit marker/使generation生效。掉电后至少旧槽仍有效。不要先擦两个槽；Flash写成功返回是否真正durable取决于MCU/cache/电源和Provider合同。

## 现场故障

若升级后节点反复重启/无法入网，先停止自动批量重刷，保留一块原始故障板和串口/Flash dump。使用安全救援固件只读检查schema/CRC；不默认格式化，避免丢失根因与身份历史。

## 灰度

先升级非关键节点，观察Wire兼容、入网、业务、资源和Record迁移；再升级Head/网关。Cluster v3/v4跨版本需要明确legacy non-voting阶段，不能随机混跑权威角色。
