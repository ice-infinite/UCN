# 规模模拟、流量模型与结果解释

> 文档级别：`NORMATIVE`
> 实现状态：`CURRENT（测试规范）`
> 适用版本：UCN 5.0.0 / Core Wire v5
> 事实源：CMake、tests、tools、results 与审计门禁
> 最近核对：`codex/v5-adaptive-wire@a093862`，2026-08-25
> 硬件状态：实机证据按具体报告；规范本身不代表已验收

`ucn_scale_sim` 测 Core 在给定节点、拓扑、流量、表容量和故障模型下的收敛/吞吐；`ucn_cluster_sim` 测选举、分组、隔离、恢复和控制流量。

报告必须包含 seed、拓扑、节点数、每节点流量、payload、链路速率、step、丢包和容量宏。只报告“1000 节点通过”没有可复现意义。

模拟结果用于发现算法/容量问题和比较趋势，不等于 RF 同频干扰、MCU CPU、内存和功耗已经满足。

## 拓扑模型

至少包含line、ring、star、binary tree、mesh/随机几何和分簇拓扑。每种拓扑注明最大节点度数，确保不超过`UCN_MAX_LINKS`。同样1000节点，line的最坏hop和tree/mesh完全不同，不能合并为一个结果。

## 流量模型

定义source/destination选择、每秒消息数、traffic class、payload/Class、是否双向、突发长度、Transfer窗口、并发和应用消费速度。高负载应分别测试：少数热点、all-to-all、随机pair、多条不相关路径并行。

## 故障模型

- 固定丢包率与burst loss；
- 延迟/jitter/reorder/duplicate；
- 单向链路、短时抖动、长期分区；
- Link/Node down与恢复；
- 动态Cost和容量满；
- Cluster Head/Backup/Directory故障。

使用固定seed便于复现，再用seed集合观察分布。只挑一个成功seed不够。

## 采集指标

Core：收敛时间、route discoveries、control frames/node、delivery/goodput、p95/p99、hop、RERR、表满/丢弃；Cluster：Head/Member数、隔离组、双Authority violation、恢复时间、控制峰值、re-election；资源：静态对象、最大队列/并发状态。

## 极限测试

逐步增加节点/流量直到首次违反合同，记录：最后全通过点、首个失败点、失败类型和配置。极限不是只看程序是否崩溃；延迟超预算、控制风暴、表持续满或不收敛都算达到上限。

## 结果解释示例

“1000节点在seed X、binary tree、每节点0.2 msg/s、15%独立丢包、固定Host step下41.8s收敛”只对该模型成立。它不能改写成“UCN支持1000节点实时通信”，更不能外推万级。

## 模拟到实机

从模拟选取代表性小拓扑（例如4～8板）复现相同故障和流量，比较趋势。差异用于校准Driver/RF/CPU模型，而不是修改模拟结果让它“看起来一致”。
