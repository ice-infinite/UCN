## 追踪表应包含什么

每个需求/任务ID至少映射：源码实现、正向test、负向test、模拟/硬件（若需要）、证据报告和当前状态。只有模块名到一个总测试可执行文件，无法证明具体合同被覆盖。

示例：

| 合同 | 源码 | 正向 | 关键负向 |
| --- | --- | --- | --- |
| Frame W0～W3 | frame codec | golden encode/decode | 版本/长度/字段/CRC/output不写回 |
| RERR依赖方向 | node routing | A-B-C断链 | 无关Route不得删除/广播 |
| Transfer deadline | transfer | 高uptime send | 长空闲、首次step、回绕 |
| CAN连续Carrier | CAN Source | 两条连续完整帧 | complete槽不能被下一START覆盖 |
| Config Commit | M07 | Prepare→Joint→双quorum→Commit | 无Joint/错Backup/重入/txid错绑 |

## 覆盖类型

- API：参数域、NULL、所有权、错误不写回；
- FSM：每条合法边、每条非法边、终态不可逆；
- Wire：字节级golden与逐字段negative；
- 时间：deadline边界、回绕、陈旧时间；
- 容量：空、满、N+1、恢复后可复用；
- 并发：task/ISR、Provider重入、多个Source；
- 跨模块：Persistence→ACK、Authority→Federation、MTU→Transfer。

## 更新规则

新增/删除功能时同提交更新矩阵。审计发现漏洞后登记R编号，并把独立probe转成正式回归；没有回归的修复不能长期防止复发。

## 默认关闭组件

对Archive必须有两类证据：ON时功能/负例通过；OFF时默认静态库无object/symbol且生产源码无调用。只验证ON不能证明产品隔离。

## 文档合同

枚举/版本/任务数等容易漂移的事实用脚本解析公共头和任务表。例如Cluster文档门禁核对Phase、Wire Type、版本/尺寸和M14任务；脚本本身也应有错误输入测试。
