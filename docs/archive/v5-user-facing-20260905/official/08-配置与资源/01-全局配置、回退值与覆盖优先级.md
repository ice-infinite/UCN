# 全局配置、回退值与覆盖优先级

> 文档级别：`REFERENCE`
> 实现状态：`CURRENT`
> 适用版本：UCN 5.0.0 / Core Wire v5
> 事实源：ucn_config.h、ucn_profile.h、CMake 与资源门禁
> 最近核对：当前工作区，2026-09-02
> 硬件状态：Host 资源可用；目标 MCU 资源需按产品配置实测

## 优先级

`ucn_config.h` 的配置顺序是：

1. 编译命令行已经定义的宏；
2. `UCN_USER_CONFIG_HEADER` 指定的产品头；
3. `ucn_config.h` 内每个 `#ifndef` 下的库默认值。

因此产品只需要覆盖关心的参数，未覆盖项继续使用库内 fallback，不会因产品头不完整而失去默认值。

预处理后的效果可以理解为：

```c
/* 构建系统或产品头先定义 */
#define UCN_MAX_LINKS 2U

/* 进入 ucn_config.h 后，已有值不会被覆盖 */
#ifndef UCN_MAX_LINKS
#define UCN_MAX_LINKS 4U
#endif
```

命令行定义优先级最高，适合 CI 做配置矩阵；产品头适合固化量产差异；库 fallback 只保证“未配置仍可构建”，不代表适合每一种硬件。

## 推荐做法

建立单独的产品配置头，例如 `product_ucn_config.h`：

```cmake
set(UCN_USER_CONFIG_HEADER "product_ucn_config.h" CACHE STRING "")
set(UCN_USER_CONFIG_INCLUDE_DIR "${CMAKE_CURRENT_SOURCE_DIR}/config")
```

配置头只写产品差异，并纳入版本控制。不要在某一个 `.c` 文件局部定义改变公共结构大小的宏。

一个产品头建议按以下顺序组织：

```c
#ifndef PRODUCT_UCN_CONFIG_H
#define PRODUCT_UCN_CONFIG_H

/* 1. Profile 与正交 Feature */
#define UCN_PROFILE UCN_PROFILE_LITE
#define UCN_FEATURE_SERVICE 1

/* 2. Core 容量 */
#define UCN_MAX_LINKS ((size_t)2U)
#define UCN_MAX_NEIGHBORS ((size_t)6U)
#define UCN_MAX_ROUTES ((size_t)8U)

/* 3. 队列、Transfer、时间参数 */
#define UCN_TX_Q0_DEPTH ((size_t)4U)
#define UCN_TX_Q1_DEPTH ((size_t)8U)
#define UCN_TX_Q2_DEPTH ((size_t)2U)
#define UCN_TX_Q3_DEPTH ((size_t)1U)
#define UCN_TRANSFER_MAX_MESSAGE_BYTES ((size_t)2048U)

/* 4. 产品安全默认 */
#define UCN_SECURITY_REQUIRED_BY_DEFAULT 1

#endif
```

示例值只是展示分组方式。产品应根据实际规模和资源报告确定，不应直接复制。

## 哪些配置会影响 ABI

凡是决定数组长度、可选字段、Feature 裁剪或公共对象成员的宏，都可能改变 `sizeof` 和布局，例如 Link/Route/Neighbor/Endpoint/Policy 容量、Profile 和 Service Feature。库与应用若看到不同值，可能“编译和链接都成功，但应用按错误偏移访问对象”。

因此推荐让所有 target 都通过同一个 interface target 继承定义，而不是分别手写：

```cmake
target_compile_definitions(product_ucn_config INTERFACE
    UCN_USER_CONFIG_HEADER=\"product_ucn_config.h\")
target_include_directories(product_ucn_config INTERFACE
    "${CMAKE_CURRENT_SOURCE_DIR}/config")
target_link_libraries(ucn_core PUBLIC product_ucn_config)
target_link_libraries(app PRIVATE product_ucn_config)
```

实际 target 名称以项目 CMake 为准，关键是配置只存在一个传播源。

## 合同

- 宏必须在包含任一 UCN 公共头前生效；
- 全部库和应用目标使用相同配置；
- 容量、duration、Profile 依赖由预处理错误、static assert 和配置合同测试拦截；
- 修改配置后应清理旧构建目录，避免对象文件混用旧布局。

## 覆盖后的核对流程

1. 在 CMake configure 输出中确认产品头路径和 Profile；
2. 查看 `compile_commands.json`，确认库、测试和应用拥有相同定义；
3. 编译配置合同测试，检查非法依赖确实失败；
4. 输出关键公共对象 `sizeof`，与基线比较；
5. 查看最终 link map，确认被关闭模块没有进入固件；
6. 在启动日志打印只读配置摘要和固件 hash，便于现场定位。

如果用户配置头找不到，构建应直接失败；不能悄悄退回默认配置，否则量产固件可能在错误容量和安全策略下运行。
