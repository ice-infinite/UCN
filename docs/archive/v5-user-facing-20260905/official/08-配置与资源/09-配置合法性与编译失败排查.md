# 配置合法性与编译失败排查

> 文档级别：`REFERENCE`
> 实现状态：`CURRENT`
> 适用版本：UCN 5.0.0 / Core Wire v5
> 事实源：ucn_config.h、ucn_profile.h、CMake 与资源门禁
> 最近核对：`codex/v5-adaptive-wire@a093862`，2026-08-25
> 硬件状态：Host 资源可用；目标 MCU 资源需按产品配置实测

## 常见失败

- 不同 target 使用不同 `UCN_PROFILE` 或容量宏，导致 ABI/对象布局不一致；
- 开启 Policy 但关闭 Path，或开启 Path 但关闭 Dynamic Mesh；
- duration 超过回绕安全范围；
- Frame/MTU/Transfer 配置互相矛盾；
- 低资源产品表容量不足，却仍注册不适配的规模测试；
- 测试专用 encoder/experiment 宏泄漏到生产 archive；
- 修改产品配置后复用旧构建缓存。

### 失败为什么会发生

UCN 的很多配置参与公共结构布局和条件编译。一个 target 认为 `UCN_MAX_LINKS=2`，另一个认为是 4 时，函数签名看起来没变，但对象大小已不同；这是比普通编译错误更危险的 ABI 问题。Feature 依赖错误则可能产生“API 存在、内部表被裁掉”的不完整实现，所以应尽量在预处理阶段拒绝。

## 排查顺序

1. 查看 CMake configure 输出中的 Profile、用户配置头和 Feature；
2. 检查 compile command 是否对所有目标一致；
3. 运行配置合同测试；
4. 查看第一条 `#error`/static assert，而不是后续连锁错误；
5. 清理构建目录后重配；
6. 比较最终 archive symbols 和 link map。

### 具体证据

```powershell
# 查看 CMake 缓存中的 UCN 选项
cmake -LA -N build | Select-String UCN_

# 生成/查看编译命令，核对每个 translation unit 的 -D
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON

# 干净重建
cmake --build build --target clean
cmake --build build --config Debug

# 运行失败时显示完整输出
ctest --test-dir build -C Debug --output-on-failure
```

如果怀疑旧缓存，最可靠的方法是新建另一个 build 目录，而不是手工删除几个对象文件。

### 症状到原因

| 症状 | 优先检查 |
| --- | --- |
| `undefined reference` 只在 Nano/Lite 出现 | 公共 API 是否缺 profile stub，archive 是否包含对应对象 |
| `sizeof`/static assert 失败 | 产品头是否对全部 target 一致，容量宏是否合法 |
| Scale 测试稳定 NO_SPACE | 拓扑最大度数是否超过 `MAX_LINKS`，是否应按容量跳过 |
| Release 失败、Debug 通过 | 未初始化/padding 比较、优化相关 UB、测试 fixture 是否完整清零 |
| 实验 API 在默认固件出现 | 测试宏/实验 source 是否泄漏到生产 target |
| 改宏后行为没有变化 | CMake cache、PCH/旧对象、产品头路径是否实际生效 |

## Fail-closed 要求

非法组合必须在编译或初始化阶段明确失败。不能用 stub 返回成功、忽略超容量项或自动降低协议版本来“让构建通过”。

错误层级应明确：非法编译组合用 `#error`/static assert；运行配置或 Provider 合同错误返回 `UCN_ERR_CONFIG`；资源满返回 `UCN_ERR_NO_SPACE`；状态转换非法返回 `UCN_ERR_STATE`/`ACCESS`。调用方只有看到准确错误，才能决定重试、降载还是停机。

## 修复后验证

修复不能只证明原构建成功，还要加入最小反例：例如旧六字段初始化的严格编译、低 Profile 公共 API 链接、128 B/3-Link 产品配置、Release Codec、Feature OFF。这样后续改动才不会重新打开同类问题。
