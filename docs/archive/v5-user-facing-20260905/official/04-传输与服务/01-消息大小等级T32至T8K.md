# 消息大小等级 T32 至 T8K

> 文档级别：`NORMATIVE`
> 实现状态：`CURRENT`
> 事实源：`ucn_transfer.h/.c`、Transfer tests
> 最近核对：`a093862`，2026-08-25

| Class | 最大逻辑消息 | 当前路径 |
| --- | ---: | --- |
| T32 | 32 B | 能装入单帧时直接 Node Send |
| T64 | 64 B | 能装入单帧时直接 Node Send |
| T128 | 128 B | 固定 Slot 分片/ACK/重组 |
| T256 | 256 B | 同上 |
| T512 | 512 B | 同上 |
| T1K | 1024 B | 同上 |
| T2K | 2048 B | 同上 |
| T4K | 4096 B | 同上 |
| T8K | 8192 B | 同上 |

## 等级不是固定物理帧

T8K 表示业务允许发送最大 8 KiB 逻辑消息，不表示一帧变成 8 KiB。实际按当前 Route/Link MTU 拆为多个普通 UCN Fragment Frame。

## 发送前条件

- 目标 Peer 已登记最大 Class、Window 和并发能力；
- 本地编译的 `UCN_TRANSFER_MAX_MESSAGE_BYTES` 覆盖该 Class；
- 有空闲 TX Slot；
- 对端 Endpoint 已按产品协议约定；
- 安全策略满足。

不满足时失败关闭，不自动把大消息截成小消息。

## RAM 影响

大档主要增加 RX 重组缓冲和对象尺寸。产品按最大真实业务选择档位；只有小控制消息的节点不应默认分配 T8K。

`ucn_transfer` 是独立 Archive。Core-only 不链接它，不增加 8 KiB 缓冲。

## 为什么“消息等级”比任意长度配置更适合 MCU

任意允许 1 B～无限大看似灵活，却让接收端无法在编译前知道要分配多少 RAM，也无法在握手中用小字段声明能力。T32～T8K 把上限冻结成九档，发送方可以按实际长度选最小可容纳 Class，接收方可以明确声明最大 Class。

等级约束的是完整逻辑消息，不要求业务必须填满整档。例如 300 B 消息选择 T512，只发送实际 300 B；不会为了“对齐等级”补成 512 B 业务数据。

## Class 选择流程

```text
实际消息长度
  ↓ 选择最小可容纳Class
本地 UCN_TRANSFER_MAX_MESSAGE_BYTES 是否覆盖
  ↓
Peer 最大Class/Window/并发是否允许
  ↓
消息能否在一个普通Frame中直接发送
  ├─ 是：T32/T64 Direct 路径
  └─ 否：占用TX Slot，进入Fragment/ACK流程
```

最小 Class 选择既减少能力要求，也使诊断更准确。发送 40 B 数据不应无理由声明 T8K，否则一个只支持 T64 的对端会被错误拒绝。

## Direct 与 Fragment 的边界

T32/T64 只是“允许 Direct 的小等级”，是否真的单帧发送还取决于当前 Wire Profile、Flags、安全 Tag 和 MTU。若 64 B 业务在当前路径放不进单帧，必须走 Transfer 分片；不能因为 Class 叫 T64 就越过 Frame 上限。

Direct 完成状态是 `SENT`，表示 Node 已接受单帧发送；分片事务收到最终累计 ACK 后是 `DELIVERED`。二者都不等于业务任务执行成功。

## Peer Capability 为什么必须先登记

发送端需要知道接收端：

- 最大消息 Class；
- 最大 Window；
- 允许并发数；
- Endpoint/产品是否支持对应 Payload；
- 当前 Session/安全能力是否匹配。

没有能力记录时盲发 8 KiB，可能让小 MCU 每片都回复 NO_SLOT 或在半路失败，浪费整个网络。能力过期/Session 变化后应重新建立，不能继承旧 Peer 的 T8K 承诺。

## RAM 预算示例

如果 `UCN_TRANSFER_MAX_MESSAGE_BYTES=8192`、RX Slots=2，单是两个 RX 数据数组理论上就需要约 16 KiB，尚未包含 bitmap/状态、TX Slot、Node、Driver Ring 和 Task 栈。把最大档降为 512 B 可以显著缩小对象，但该固件也必须明确拒绝 T1K～T8K。

TX 端通常借用调用方消息缓冲还是复制、缓冲必须保持多久，以公共结构/API 合同为准；应用不能在发送未完成前复用被借用数据。

## 如何按业务选档

| 业务 | 建议 |
| --- | --- |
| 8～24 B 控制/状态 | 普通 Endpoint 或 T32 Direct |
| 40～60 B 小结构 | T64，按实际 MTU决定 Direct/Fragment |
| 100～300 B 参数块 | T128/T256/T512 |
| 1～4 KiB 标定/日志块 | T1K～T4K，评估窗口和 RAM |
| 8 KiB 固件/大块 | T8K 只是单消息上限；完整固件还需上层分块、版本、签名和恢复协议 |

UCN Transfer 不是文件系统，也不自动提供断点续传或固件签名。超过 8 KiB 的对象要在产品层拆成多个有编号的 Transfer 消息。

## 失败与降级

- 本地最大 Class 不足：发送前拒绝；
- Peer 最大 Class 不足：发送前拒绝，不截断；
- 无 TX/RX Slot：明确 NO_SLOT/NO_SPACE；
- Direct 当前 MTU 不足：选择 Fragment，而不是越界编码；
- Fragment 最小数据都放不下：路径不可用；
- 业务需要 T8K 但产品只构建 T512：应升级产品配置，不在运行时动态分配。
