# 命令、结果与业务确认语义

> 文档级别：`NORMATIVE`
> 实现状态：`CURRENT`；业务协议由产品定义
> 最近核对：`a093862`，2026-08-25

## 五个阶段

| Stage | 能证明什么 |
| --- | --- |
| `LOCAL_INBOXED` | 本机目标 Inbox 已接受 |
| `REMOTE_ROUTER_QUEUED` | 源节点 Router 已接管远端消息 |
| `LINK_QUEUE_ACCEPTED` | Bridge/Core/Link 本地发送队列已接受 |
| `REMOTE_INBOXED` | 目标 Router 明确回报进入 Inbox |
| `REMOTE_EXECUTED` | 目标业务任务明确回报执行结果 |

前 3 个阶段不能推断后 2 个。

## Command Guard

高风险 Q0 可在 Payload 前加入 12 B 产品 Guard：Command ID、issued time、valid duration、Result Endpoint 和 Flags。远端 Validator 检查权限、时效和幂等后再交给任务。

Guard 不是所有消息强制字段，不增加普通传感器帧开销。

## Result Header

业务结果可用 8 B Header 返回 Command ID、Stage、Status 和产品 detail code。状态包括 Accepted、Succeeded、Rejected、Failed、Expired。

## 推荐请求/结果流程

```text
A 生成唯一 command_id
  → 发给 B 的控制 Endpoint
B Bridge/Validator 接收
  → 投递任务 Inbox
B 任务执行或拒绝
  → 发 Result 到 A 指定 Endpoint
A 以 command_id 匹配挂起请求
```

网络重试可能带来重复命令，B 必须按 Command ID 做业务幂等；不能只依赖 Frame 去重窗口覆盖长时间业务事务。

## 为什么必须把五个阶段拆开

如果 `ucn_service_send()` 返回 OK 就向用户显示“舵机已转动”，实际可能只是命令留在 A 的 Remote Queue。Link 随后断开、B 未 Ready、B Validator 拒绝或舵机卡死都会使执行失败。

阶段拆分让每个参与者只报告自己能证明的事实，避免跨层伪承诺。

## Command Guard 的字段责任

| 字段 | 作用 | 边界 |
| --- | --- | --- |
| `command_id` | 业务幂等和 Result 关联 | 应在约定域内唯一/单调 |
| `issued_at_ms` | 签发时刻 | 只有共享时间域才可跨节点比较 |
| `valid_for_ms` | 命令有效期 | 过期后不得排队执行 |
| `result_endpoint` | 结果返回到哪个 Endpoint | 必须是产品允许的静态 Endpoint |
| `flags` | 产品扩展语义 | 未知位应拒绝或按冻结合同处理 |

Guard 12 B 是可选业务前缀，不是 Core Header。普通 IMU 样本不需要为它付费。

## 没有同步时钟怎么办

两个 MCU 的 uptime 不可直接比较。没有同步时间时，产品可以：

- 用持久单调 command generation；
- 由 B 发 challenge/lease，A 在该 lease 内使用；
- 只把 valid duration 作为 A 的本地 pending timeout，B 用 Command ID 防旧命令；
- 使用安全 Session + nonce + 有界 replay 表。

不能把 `issued_at_ms` 塌缩成“看起来差不多就接受”。

## 目标端的安全执行顺序

```text
安全认证/Source ACL
  ↓ Guard格式与Result Endpoint
Command ID replay/幂等
  ↓ 时效/lease
设备状态与参数范围
  ↓ 写目标Inbox
任务再次检查执行条件
  ↓ 执行动作/持久化
发送Result终态
```

例如参数写入只有在 Flash commit/reload 验证成功后才能回 `SUCCEEDED`；写请求进入 Inbox 只能回 `ACCEPTED`。

## 重复命令如何幂等

B 已执行 command 42，但最终 Result 丢失。A 超时后重发相同业务命令：

- Frame Sequence 可能是新的，Core 会接受；
- B 的业务幂等表识别 command 42 已完成；
- B 不再次驱动舵机，而是重发相同终态 Result；
- 相同 ID 但 Payload/目标状态不同应判冲突并拒绝。

幂等表是有界的，产品必须定义保留期、重启持久化和 ID 轮换策略。

## Result Header 如何解释

`REMOTE_INBOXED + ACCEPTED` 只表示 B 的业务 Inbox 接管。`REMOTE_EXECUTED` 必须搭配终态 `SUCCEEDED/REJECTED/FAILED/EXPIRED`。Detail Code 由产品冻结，例如参数范围错误、机械限位、Flash 错误。

Result 本身也可能丢失，因此 A 的 pending 表要有 Deadline。超时表示“未收到可证明终态”，不一定能断定 B 没执行；对危险动作要设计查询状态或幂等重试。

## 一次完整舵机命令示例

1. A 分配持久/会话唯一 `command_id=1001`；
2. 构造 Guard + 目标角度 Payload，Deadline=30 ms；
3. Service 返回 `REMOTE_ROUTER_QUEUED`；
4. Bridge event 报 `LINK_QUEUE_ACCEPTED`；
5. B Validator 验证 Source、Command ID、时效和角度范围；
6. B Inbox 成功，可选返回 `REMOTE_INBOXED/ACCEPTED`；
7. B 舵机任务执行并读取反馈；
8. B 返回 `REMOTE_EXECUTED/SUCCEEDED` 或 `FAILED + detail`；
9. A 匹配 1001 后关闭 pending；
10. 超时/链路切换重试仍使用 1001，不创建第二个动作。

## 验证清单

- [ ] 每个 API/事件只报告它能证明的阶段；
- [ ] Guard encode/decode 字节序和长度固定；
- [ ] 过期、未知 flags、非法 Result Endpoint 在投递前拒绝；
- [ ] 相同 Command ID 相同请求幂等，相同 ID 冲突请求拒绝；
- [ ] Result 丢失后的重试不会重复执行；
- [ ] 参数/Flash/舵机真实终态由业务任务产生，而非 Bridge 推断；
- [ ] pending/幂等表容量、保留期和重启策略已定义。
