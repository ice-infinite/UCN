# 吞吐、延迟与背压调优

> 文档级别：`GUIDE`
> 实现状态：`CURRENT` 机制；数值必须目标板实测
> 最近核对：当前工作区，2026-09-02

## 先定位瓶颈层

```text
业务产生率
→ Service Queue
→ Node Q0～Q3
→ Frame/Transfer Header
→ Owner Step/Source budget
→ Link Driver Queue
→ 物理速率与半双工/冲突
→ 多跳重复占用
→ ACK/重试
```

“串口 3 Mbit/s”不等于业务 Payload 375 kB/s。UART 8N1、Frame Header、COBS、ACK、任务调度、多跳中继和窗口都会扣除有效吞吐。

## 调优顺序

1. 确认 Driver 实际波特率/DMA/中断和 Ring 无丢失；
2. 确认 Owner 被立即通知，Step 不被低优先级任务饿死；
3. 增大单片有效 Payload，减少每片固定头；
4. 在 RTT 较高且队列足够时增加 Transfer Window；
5. 按 Peer 能力增加有限消息并发；
6. 调整 Node/Adapter Queue 前先看峰值 RAM；
7. 多跳半双工线形拓扑考虑每跳重复发送和中间节点收发切换；
8. 根据真实 metrics 调整 Cost/Balance，而非只看名义速率。

## 背压处理

- Service Queue 满：业务决定丢旧、拒绝或降频；
- Node Queue 满：Q0 可有界本地重试，Q1 Latest 可覆盖，Q2/Q3 FIFO 明确返回背压；
- Adapter/Source Ring 满：Driver/ISR 计数并排查 Owner 预算；
- Transfer Slot 满：等待完成或降低并发；
- Link Queue 满：缩小窗口/并发或提升 Driver service。

## 报告要求

吞吐必须同时记录 Payload bytes/s、Wire bytes/s、消息档、Window、并发、Hop、波特率、错误、CPU 和测试持续时间，不能只报一个“速度”。

## 理论线速与业务吞吐的区别

UART 3 Mbit/s、8N1 每字节需要 10 bit，理论原始上限约 300 kB/s，而不是 375 kB/s。之后还要扣除 COBS delimiter/编码、Core Header、Transfer 14 B Header、ACK、重传和任务空隙。多跳链还会让相同数据在每段重新发送。

一个粗略单片效率：

```text
payload_efficiency = fragment_data_bytes
                   / carrier_wire_bytes_for_fragment
```

总吞吐还要乘以成功率和链路有效占空比。只有把每层字节计数记录下来，才能判断损耗在 Header、空闲等待还是重传。

## 为什么小 Fragment 会特别慢

每片都固定承担 Core Header、14 B Transfer Header、Frame CRC、COBS/CAN Carrier 和 ACK 相关成本。片数据只有 16 B 时，固定成本可能超过业务数据；片数据增大后效率明显提高。

但片越大也会：

- 占用 Link 更久，增加 Q0 等待；
- 在错误时重传更多字节；
- 超过路径最小 MTU；
- 增加 Driver Ring 连续空间要求。

因此要用真实错误率和 Q0 延迟共同选择，不是无条件最大化。

## Owner/事件模型为何决定性能

Driver 有中断并不自动使协议实时。如果 ISR 收到数据后只写 Ring，Owner 仍每 10 ms 轮询一次，就平白增加最高 10 ms 等待。标准做法是 ISR/DMA completion 通知 Owner，Owner 按固定 budget 批量 drain；轮询作为丢通知或无中断平台保底。

Budget 太小会频繁唤醒和积压，太大可能让一个 Link 饿死其他 Link/Q0/维护工作。需要测每次 drain 数、step 时长和各队列高水位。

## 多跳流水线

链式全双工 UART 理论上可让不同段重叠工作，但当前中继仍需完整 Frame 接收和校验后再转发。性能取决于：

- Adapter 是否批量/事件驱动；
- 中继能否同时 RX 一条 Link、TX 另一条；
- Owner 是否及时轮转 Link；
- Window 是否覆盖端到端 RTT；
- ACK 是否占用同一半双工方向。

不能用单跳线速乘一个简单常数预测 3 跳；必须对每个消息档实测。

## 分层定位步骤

1. **Driver-only**：用测试模式测物理收发、DMA/Ring、错误；
2. **Adapter Frame**：传固定完整 UCN Frame，测 Carrier 编解码；
3. **Node Direct**：单帧 Endpoint，排除 Transfer；
4. **Transfer single-hop**：九档、不同 fragment/window；
5. **multi-hop**：保持其他参数相同测每增一跳损失；
6. **Service/Task**：加入 Inbox、任务唤醒和业务处理；
7. **mixed load**：Q0 + Q1 + Transfer + 维护帧；
8. **fault**：丢包、断链、切路、重试。

跳过前层直接看最终速度，会难以判断是 UART、Adapter、Node Queue 还是 Transfer Window 拖累。

## 参数调优关系

| 参数 | 增大可能收益 | 代价/风险 |
| --- | --- | --- |
| Fragment data | Header占比下降 | Q0阻塞、错误重传增大 |
| Window | 覆盖RTT、吞吐上升 | 队列/RAM/Go-Back-N代价 |
| TX/RX Slots | 并发增加 | 对象RAM显著上升 |
| Owner drain budget | 减少积压 | 其他Link/维护饥饿 |
| Queue depth | 吸收短峰值 | 延迟上升、掩盖长期超载 |
| 波特率 | 原始带宽上升 | 信号完整性、Driver/CPU压力 |
| Q1 Latest | 避免历史积压 | 不保证每样本到达 |

## 压力测试应观察什么

- 业务产生/接受/实际交付字节；
- Frame/Fragment/ACK 数和重传；
- 每层 Queue 高水位、NO_SPACE、overwrite/drop；
- Owner step P50/P95/P99/最大；
- ISR/Ring overflow；
- 目标任务 Inbox→处理延迟；
- Route/Heartbeat 是否在负载下稳定；
- CPU、最小 Heap、Task 栈高水位和功耗；
- 不同 Hop/消息档的相对损失。

## 何时应该换架构而不是继续调参

如果单链路持续业务本身已超过物理可用带宽，增加 Queue/Window 只会增加延迟；应降低数据率、压缩、批量、启用多 Bearer 分流或换高速介质。若大文件吞吐是核心需求，UCN 可负责统一寻址/控制，但产品也可为数据面选择专门高速 Bearer，而不是强迫低速 CAN 承担所有大块。
