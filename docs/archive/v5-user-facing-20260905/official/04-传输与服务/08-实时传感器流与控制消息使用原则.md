# 实时传感器流与控制消息使用原则

> 文档级别：`GUIDE`
> 实现状态：基于当前 Q0～Q3、Endpoint 和 Service 合同
> 最近核对：当前工作区，2026-09-02

## 一个节点可以有多个传感器

不需要每个 IMU、气压计、温度计都配一个 MCU Node。一个 Node 用不同 Endpoint 区分数据源，任务或驱动在本机生产消息。

## 建议映射

| 数据 | 推荐语义 | 原因 |
| --- | --- | --- |
| IMU 高频样本 | Q1 Latest + sample sequence/timestamp | 旧样本积压通常无价值 |
| 温度/气压状态 | Q1 Latest 或低频 FIFO | 频率低，可容忍覆盖 |
| 舵机目标值 | Q0 + Command ID/有效期 | 关键控制且需要拒绝过期命令 |
| 参数写入 | Q0 + Result + 持久化结果 | 必须区分入队与落盘 |
| 普通参数/查询结果 | Q2 FIFO | 保序，但不占用 Q0/Q1 的主要预算 |
| 日志/批量数据 | Q3 FIFO 或 Transfer | 小块可直接 Q3；需要完整交付的大消息使用 Transfer |

## 实时性

实时性由端到端预算决定：任务产生→Router/Node Queue→Owner 调度→Link/介质→远端 Owner→Inbox→任务调度。UCN 不控制产品任务优先级和 Driver DMA。

Q1 Latest 降低队列积压，但允许丢弃旧样本。要求每样本到达时必须显式使用序号、足够带宽和可靠传输设计。

## 控制安全

- 控制 Endpoint 与传感器 Endpoint 分开；
- 要求远端 Q0 Validator；
- 使用短有效期和 Command ID；
- 目标任务检查当前系统状态后再执行；
- 返回显式 Result；
- Link/Route 失败时进入产品安全状态，不无限重发旧舵机命令。

## 从需求反推消息语义

先问“消费者错过一条会怎样”，再决定 Q0～Q3/Transfer：

- 错过旧值没关系，只需最新状态：Q1 Latest；
- 每条事件都必须按序处理：Q0 FIFO 或产品事件队列；
- 普通消息需要 FIFO、但不要求关键优先级：Q2；
- 小块批量数据可延后且允许 Best Effort：Q3；
- 数据大于单帧且必须完整：Transfer；
- 命令必须知道执行结果：Q0 + Command ID + Result；
- 数据量持续高于链路能力：不是换个队列就能解决，必须降采样、压缩或提高带宽。

## 高频 IMU 设计示例

IMU 任务以 1 kHz 采样，不一定要以 1 kHz 单样本逐帧发送。可以根据控制需求选择：

1. 每样本 Q1：低延迟，但小帧 Header/调度占比高；
2. 4～8 样本批量：提高有效载荷，增加少量批等待；
3. 本地控制任务使用 Service Fast Path 每样本，远端监控降采样到 100 Hz；
4. Payload 带 sample sequence 和采样时间，消费者可检测丢样/陈旧；
5. Q1 Latest 防止消费者变慢时堆积无限历史。

协议统一数据路径，但产品仍要根据控制环路决定采样、批量和远端频率。

## 舵机控制设计示例

舵机目标命令一般包含 Command ID、目标位置/速度、有效期和 Result Endpoint：

- 使用 Q0 FIFO，不能 Latest 覆盖中间状态，除非产品明确采用“只执行最新 setpoint”的另一套 ABI；
- Validator 检查 Source、范围、时效和当前模式；
- 任务执行前再次检查限位/故障；
- 超过 Deadline 的旧命令不因队列恢复而执行；
- Result 区分 Accepted、Succeeded、Rejected 和 Failed；
- 网络失联后进入产品定义的保持、回中或断能安全状态。

UCN 负责消息与网络边界，不替代电机控制安全状态机。

## 同一传感器的请求与流式模式

节点 A 获取 C 的气压数据有两种方式：

| 模式 | 流程 | 适用 |
| --- | --- | --- |
| Request/Result | A 发请求，C 读取一次并返回 | 低频按需、需要关联结果 |
| Streaming | C 按配置周期向 A 推送 | 持续实时数据 |

Streaming 的订阅建立、周期修改和取消应使用产品控制 Endpoint；不能假设 Core 自动知道 A “想要哪一种数据”。Path 只决定去 C 的路线，Endpoint 才区分 C 的 IMU、气压和温度。

## 数据新鲜度判定

网络 Sequence 用于 Frame 去重，不等于传感器采样 Sequence。批量、重发或多源时，两者含义不同。实时 Payload 建议携带：

- sensor/sample sequence；
- 本地采样 timestamp 或 time domain ID；
- sensor instance ID；
- status/validity；
- ABI version。

没有跨节点同步时钟时，远端 timestamp 主要用于相对顺序；接收方还应记录本地 receive time 和最大可接受 age。

## 带宽预算

```text
wire_rate ≈ samples_per_second
          × (Core header + security + service/transfer header + payload)
          × hop retransmission factor
```

多个传感器同时发送时要汇总，而不是逐个都按“链路还有空间”配置。还需为 Heartbeat、Route、ACK 和故障恢复留控制余量。

## 任务调度边界

即使 UCN 已把消息放进 Inbox，业务 Task 仍可能因 RTOS 优先级低而晚处理。实时时延测试必须从传感器采样/命令产生一直量到目标任务消费/执行，单看 Link TX complete 不足。
