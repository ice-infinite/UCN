# 模块边界与依赖规则

> 文档级别：`NORMATIVE`
> 实现状态：`CURRENT`
> 事实源：`src/`、`CMakeLists.txt`
> 最近核对：`a093862`，2026-08-25

| 模块 | 责任 | 允许依赖 | 禁止依赖 |
| --- | --- | --- | --- |
| `src/core` | 配置、Frame Codec、Endpoint、纯 Cost Resolver | 公共头、C99 | Node 私有状态、RTOS、SDK |
| `src/node` | Node 生命周期、Neighbor、HELLO、重复抑制、路由控制 | Core 语义、公共 API | Port、具体 Driver |
| `src/transport` | Adapter Queue、Preset、Event Runtime、Protocol Owner | Node/Core API | 具体 RTOS/外设 SDK |
| `src/adapters/stream` | Byte Ring、COBS+0、Owner Source | Runtime、Frame 上限 | UART/USB SDK、任务对象 |
| `src/adapters/can` | CAN Ring、CAN-FD、Classic Carrier、Bus State | Runtime、Frame 长度 | CAN 寄存器、过滤器、引脚 |
| `src/routing` | Full 的 Path、Policy、负载均衡 | Link/Node/Endpoint | Port、SDK |
| `src/service` | 本机 Router 与远端 Bridge | Node/Endpoint | RTOS 任务实现、SDK |
| `src/ports` | Bare metal/RTOS/Host 运行外壳 | 公共 API | 其他 Port 私有实现 |
| `src/extended` | Transfer、Cluster、Federation | Core 公共 API、固定表 | 动态内存、SDK、业务对象 |

## 公开与私有边界

- 产品包含 `include/ucn/`；不得包含 `src/..._internal.h`。
- `ucn_node_t` 和 `ucn_cluster_t` 由公共头保持 opaque；只有唯一 owner 翻译单元按需包含 storage 头。
- 应用不得直接读取 Queue、Route、Neighbor 或 Cluster 私有字段，必须使用公开 API/View/Stats。
- Port、Adapter 和 Source 只持有借用指针或调用者存储，不获得业务对象所有权。

## 依赖方向

正确方向是：

```text
Product Driver → Source/Adapter → Node/Core
Product Task   → Service/Endpoint → Node/Core
Extended       → Node/Core public API
Port           → Protocol Owner / Event Runtime
```

Core 不反向调用 ESP-IDF、HAL、Zephyr、FreeRTOS 或产品业务函数，除非它们以明确回调注入。

## Feature 裁剪

- Nano 选择 `ucn_node_nano.c`，不编译 Full Path/Policy。
- 非 Full 对关闭 API 提供可链接且失败关闭的 Stub。
- Service 可通过 `UCN_FEATURE_SERVICE=OFF` 独立移除。
- Transfer、Cluster、Federation 和实验 Archive 需要显式链接。

## 1. 为什么要冻结依赖方向

UCN 同时服务裸机、多个 RTOS、Host 模拟和不同厂商芯片。如果底层模块反向依赖上层业务或 SDK，任何一次平台变化都会迫使协议代码分叉。冻结依赖方向可以让：

- Core 在没有 RTOS/硬件时独立单测；
- 同一个 Stream Source 同时服务 UART、RS-485 和 USB CDC；
- 产品替换 ESP32 为 STM32 时只重写 BSP/Adapter；
- Nano/Lite/Full 真正裁剪代码，而不是到处留运行时 `if`。

## 2. 允许的调用链

### 发送方向

```text
Application
  -> Service/Transfer（可选）
  -> Node public API
  -> Route/Path/Policy
  -> Link ops
  -> Product Adapter/Driver
```

### 接收方向

```text
Driver ISR/DMA callback
  -> Source ring
  -> Event Runtime / Owner
  -> Adapter Queue
  -> Node receive
  -> Endpoint / Service handler
```

接收方向看似从硬件“向上调用”，实际 ISR 只写 Ring。真正的 Source service、Node receive 和业务分发仍由 Owner 顺序调用，避免驱动栈直接进入业务。

## 3. 禁止的依赖示例

| 禁止做法 | 为什么错误 | 正确替代 |
| --- | --- | --- |
| `src/core` 包含 ESP-IDF 头 | Core 无法跨平台/Host 测试 | 在产品 Adapter 保存 ESP context |
| Endpoint handler 直接修改 Route 表 | 绕过不变量和容量合同 | 调用公开 Route/Policy API |
| ISR 调用 `ucn_node_step()` | 与任务并发、耗时不可控 | ISR push + notify Owner |
| Transfer 读取 `ucn_node_t` 私有字段 | Storage layout 形成隐式 ABI | 使用 Node 公共发送/能力 API |
| Port 文件写死 UART 引脚 | Port 与 BSP 耦合 | 产品配置/Driver 传入 context |
| Cluster 直接改 Core Neighbor 内存 | 两个状态机所有权冲突 | 复制 Neighbor summary |

## 4. Opaque 对象和 Storage 头

业务文件只看不完整类型，可以保存 `ucn_node_t *`，但不能 `sizeof` 或访问字段。唯一 Node owner 翻译单元包含 storage 头并分配对象：

```c
/* 概念示意，精确声明以公共头为准。 */
#include "ucn/ucn_node.h"
#include "ucn/ucn_node_storage.h"

static ucn_node_t g_node;
```

这种设计允许内部增加 Queue/Route 字段时，通过 Storage Layout/API Version 明确触发全量重编译，而不会让业务代码依赖字段位置。

## 5. Callback 注入规则

Core 可以调用产品代码，但只能通过明确 ops：

- Link send/status/metrics；
- Security seal/open/authorize；
- Port time/critical/notify；
- Persistence load/submit/poll；
- Endpoint/Service handler。

每个 callback 必须定义调用上下文、是否允许同步完成、数据所有权和重入规则。没有这些合同的“万能回调”容易造成栈借用、递归 Owner 或 ISR/task 锁混用。

## 6. 新介质如何归类

以新增 SPI peer-to-peer 介质为例：

1. SPI 驱动和 DMA 位于产品 BSP；
2. 如果传输是字节流，可复用 Stream Source；如果是完整 datagram，实现自定义 Source；
3. Adapter 把 chip-select/peer 映射为 Link context；
4. Link ops 报告 MTU、状态和指标；
5. Node/Route 不新增任何 SPI 专用分支。

如果为新介质修改了 Core Route 算法去读取 SPI 寄存器，说明模块边界已经破坏。

## 7. 独立 Archive 的链接含义

`EXCLUDE_FROM_ALL` 或默认 OFF 的 target 只有被产品显式链接时才贡献代码。头文件能被包含、单元测试能构建，都不代表最终固件包含该 archive。发布审计应同时检查：

- CMake option；
- target link libraries；
- archive symbol；
- 生产源码引用；
- 最终 map。

这对 Cluster Wire v4 和 M10/M11/M13 尤其重要。

## 8. 边界验证

仓库通过 Core-only、Profile、Service-OFF、公共头编译、默认 archive symbol 和生产引用扫描验证依赖边界。新增模块后应补同类门禁，避免“测试 target 无意把实验宏传播给生产库”。
