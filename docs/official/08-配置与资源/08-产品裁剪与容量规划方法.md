# 产品裁剪与容量规划方法

> 文档级别：`REFERENCE`
> 实现状态：`CURRENT`
> 适用版本：UCN 5.0.0 / Core Wire v5
> 事实源：ucn_config.h、ucn_profile.h、CMake 与资源门禁
> 最近核对：`codex/v5-adaptive-wire@a093862`，2026-08-25
> 硬件状态：Host 资源可用；目标 MCU 资源需按产品配置实测

## 步骤

1. 列出硬件 RAM/Flash、Bearer 数、最大邻居和最大并发；
2. 选择 Nano/Lite/Full；
3. 决定 Service、Transfer、Cluster、Federation 和实验 Archive 是否链接；
4. 缩放固定表、队列、窗口和 payload；
5. 运行配置合同、单元测试、规模模拟和资源报告；
6. 在目标 MCU 测 stack/heap/CPU/功耗并保留余量；
7. 压力、断链和长稳后再冻结产品配置。

### 第一步：写清需求而不是先改宏

需求表至少包括：节点/邻居/目的地上限、每节点 Bearer 实例数、消息大小和频率、是否需要跨 MCU/任务 Service、最大允许延迟、断链恢复时间、安全等级、是否使用 Cluster，以及最坏并发事务数。没有流量模型时，队列和窗口大小只能靠猜。

### 第二步：建立对象清单

列出每个固件实例实际创建多少个 Node、Link、Adapter、Event Source、Transfer、Service、Security、Cluster/Federation 对象。相同库配置下，创建两个 Node 实例会近似重复其静态对象占用；“支持多个串口”也意味着每个串口需要独立 Link/驱动上下文和 RX ring。

### 第三步：按风险裁剪

优先关闭完全不用的模块，再降低容量；不要删除错误检查、重放窗口或安全状态来省少量 RAM。对于控制系统，宁可减少同时缓存的普通路由，也不要让 Q0/persistence continuation 缺少必要槽位。

## 典型取舍

- 减小路由/邻居表可省 RAM，但可能增加发现和淘汰；
- 增大 Adapter Queue 可吸收突发，但会增加延迟和内存；
- 增大 Transfer 窗口提高吞吐，也增加 buffer 与重传压力；
- 缩短 heartbeat 加快故障感知，会增加控制流量和误判风险；
- Cluster/Federation 只应在业务确实需要时加入小 MCU 产品。

产品配置应以版本化头文件和构建 preset 固化，禁止现场只改一个源文件中的局部宏。

### 示例：小型飞控传感器节点

假设 1 个 CAN、1 个 UART、最多 4 个直连邻居，只发布 IMU/气压计服务，不承担 Cluster Head。可从 Lite 开始，按实际需要决定是否保留 Security，减少 Link/Neighbor/Route/Transfer slots，关闭 Cluster/Federation 和不需要的诊断。若同一节点还要接 USB 调试，则 `MAX_LINKS` 必须把 USB 算进去。

### 示例：多 Bearer 网关

网关同时有 2 路 CAN、2 路 UART、Wi-Fi、USB，并要固定路径/负载均衡及跨任务 Service，应从 Full 开始，`MAX_LINKS` 至少覆盖 6 个实例，Neighbor/Bearer-per-neighbor 按拓扑扩大；同时为 Event Runtime source、RX ring、Q0～Q3 和 Transfer 并发预留空间。网关通常不是因为 Core 对象最大，而是因为多驱动 buffer、日志和网络 SDK 占 RAM。

### 冻结前清单

- 配置头、CMake preset 和固件版本一一对应；
- Debug/Release、Nano/Lite/Full 相关矩阵通过；
- 容量边界 `N-1/N/N+1` 均有明确行为；
- 最大业务+控制突发不造成无界积压；
- 实机 RAM/Stack/CPU/功耗有余量；
- 回滚到上一配置时 Wire/Storage/ABI 有明确策略。
