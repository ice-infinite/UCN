# 从配置到收发的完整顺序

## 1. 冻结产品配置

先选择 Profile、Feature、最大 Link/Peer/Route/Transfer 数、Address Class、Security Suite、
动态或静态 Address Authority、最大消息等级和 Bearer。把全部覆盖值放进一个 Product Config
头，通过 CMake 统一传给库和应用。保存 `ucn_v6_compiled_manifest()` 到构建证据。

## 2. 准备基础依赖

实现单调时钟、持久化 Provider、随机数/密钥 Provider、任务与 ISR 锁、Owner 通知以及每条
Bearer 的 Driver。所有 callback 都必须非阻塞或有明确异步 completion；Provider 内同步重入
协议 API 必须被 gate 拒绝。

## 3. 初始化顺序

建议顺序如下：

1. 校验编译期与链接库 Manifest；
2. 初始化 shared callback gate；
3. 初始化 Identity Authority/Bootstrap 或加载本机 Binding；
4. 初始化 Protocol Owner 与 Security；
5. 初始化 Capability、Route、Metric、QoS、Transfer；
6. 按 Feature 初始化 Realtime、Cluster；
7. 初始化 Adapter/Port，逐条注册 Link；
8. 只有持久状态 reload、Key、ACL 和 Link readiness 全部成立后才允许入网或发送。

任何步骤失败都不得留下半启用节点。最简单做法是直到全部 Owner 初始化成功才发布对外
ready 标志，并在失败路径关闭 Driver、清理 volatile queue，但保留 durable state 供下次恢复。

## 4. 主循环

Driver/ISR 发布事件并通知 Owner。Owner 被唤醒后在预算内按顺序处理 RX/completion/timer、
安全和状态机，再调度 QoS/Adapter TX；还有事件时立即继续或再次通知，不等待心跳。Timer
只负责 deadline、lease、重试和无中断 fallback。

## 5. 发消息

应用构造完整 Message Context，先决定是否需要 Operation Journal 和 Realtime Envelope，再
查询 Capability/Path Budget。单帧放得下时进入 Security→Route→QoS；否则创建 Transfer，
逐片由相同路径发送。`UCN_OK` 的具体含义要看 API：可能只表示入队/接受，不等于远端执行。

## 6. 收消息

接收路径必须在业务回调前完成长度、Wire、Hop Tag、Replay、Route、E2E Tag、ACL、Realtime
和 Operation 检查。业务回调返回失败时，是否重试由 Delivery/Operation 合同决定；不能简单
重复执行 durable request。

## 7. 故障和升级

断链时先标记 Link not ready、推进 Instance Generation，随后使 Route/Transfer pending 失效。
安全会话吊销必须同步清除相关 Route、QoS 和 Replay 状态。v6 不在线升级 v5 状态；从 v5
切换必须刷入 v6 固件并按产品流程清除或转换独立存储介质，不能加载旧 Record。
