# 路由规模、跳数、寻址距离与复杂度

> 文档级别：`NORMATIVE REFERENCE`
> 实现状态：`CURRENT`
> 最近核对：`a093862`，2026-08-25

## 三个不同上限

1. **地址上限**：Wire Profile 能表示多少 Node ID；
2. **本地工作集**：一个 Node 的 Neighbor/Link/Route/Candidate/Path 固定表有多大；
3. **可运行网络规模**：由拓扑、业务、控制流量、介质冲突、RAM、时延和故障模型共同决定。

地址能表示 4G Node 不代表单一 MCU 保存 4G 条 Route，也不代表一个广播域可容纳 4G 节点。

## 跳数

默认产品上限 16。W0/W1/W2/W3 线表示上限分别 4/16/64/254。每一跳都增加：

- Carrier 发送时间和介质竞争；
- Queue/Owner 调度延迟；
- 丢包概率和重传代价；
- 路由状态失效概率；
- MTU/Profile 共同能力约束。

因此“能寻址多远”不是公里或无限跳，而是业务时延和可靠性允许的有效路径长度。

## AODV 控制复杂度

首次无 Route 时，RREQ 可能在 Hop Scope 内扩散；已有 Route 后普通发送为逐跳表查找。网络高频全对全、频繁移动和极短缓存会显著增加控制代价。

## 本地占用

内存主要由编译期表决定，而不是全网节点总数线性灌入每个 Node。产品可降低 Link/Route/Neighbor/Path/Flow 上限换取 RAM，也会减少并发拓扑能力。

## 规模证据解释

Host `ucn_scale_sim` 可实例化大量真实 Node 对象并统计收敛/流量/占用，但虚拟时间和虚拟 Link 不包含无线 PHY、MCU CPU、中断和功耗。规模结论必须附模拟参数，不能直接写成实机规格。

## 节点不保存“所有经过它的路线”

一个边缘节点通常只需要：直连 Neighbor、自己实际通信目标的 Route、少量 RREQ/Discovery 状态。中继节点因承载更多目标会占用更多 Route/Path 槽，但仍受编译期上限限制。网络中存在 1000 个 Node，不表示每个 Node 都保存 999 条 Route。

这与互联网路由器类似：转发依据目标前缀/下一跳，普通终端不会保存全球每条端到端路径。UCN 规模更小且表是静态上限，但“分布式下一跳”原则相同。

## 寻址距离与可达距离

Wire Node ID 只提供逻辑地址空间；无线射频距离由功率、天线、频段和环境决定；多跳可达距离又受 Hop、延迟和中继可用性影响。因此至少要分别回答：

| 问题 | 决定因素 |
| --- | --- |
| 能表示多大 Node ID | W0～W3 |
| 本节点能同时记住多少目标 | Route/Neighbor/Path 表容量 |
| 一帧最多转发几次 | 产品 Hop 上限和 Wire Profile |
| 物理能走多远 | 每跳介质覆盖和拓扑 |
| 业务是否仍可用 | 端到端时延、吞吐、丢包和故障恢复 |

## 每跳吞吐为何下降

在半双工共享介质上，同一 Payload 每经过一跳都再次占用信道，理想上限可能接近单跳吞吐除以同信道重用次数；实际还叠加 Header、ACK、调度和冲突。在独立 UART 链式中继中，每段可并行程度取决于 Owner、缓冲和全双工能力，但 store-and-forward 仍产生队列和复制开销。

所以“互联网跨很多节点仍很快”不能直接类比单 MCU 的串行 store-and-forward：互联网骨干拥有高速并行链路、硬件队列、流水线 ASIC、分层路由和巨量内存。UCN 的目标首先是小 MCU 上的可预测资源和统一多 Bearer，不是替代高速 IP 骨干。

## AODV 最坏控制压力

首次发现时，RREQ 在允许拓扑范围传播，最坏控制量与可达边/转发次数相关；RREP 沿返回路径，RERR 沿依赖路径。以下场景会显著放大压力：

- 所有节点同时启动并互相发送；
- Route TTL 太短导致反复发现；
- 拓扑高速变化；
- 无 jitter 的同步 HELLO/RREQ；
- 全对全大流量；
- 表容量太小导致有效 Route 被频繁回收。

控制预算、jitter、发现槽、Hop Scope 和缓存共同限制瞬时风暴。

## 如何估算本地 RAM

概念公式：

```text
Node RAM ≈ 固定Node对象
         + Link表容量 × Link状态
         + Neighbor/Bearer容量 × 对应记录
         + Route/Candidate/Discovery/去重表
         + 可选 Path/Policy/Flow/诊断表
         + Adapter Driver Ring 与队列
         + Service/Transfer/Cluster 可选对象
         + Task栈和SDK缓冲
```

只报告 `sizeof(ucn_node_t)` 会漏掉外部 Driver Ring、RTOS 栈和可选对象。产品要用 Map/ELF 和运行时栈高水位核对完整预算。

## 规模测试应分层

1. **单对象容量测试**：表满、回收、边界 Node ID/Hop；
2. **Host 多节点模拟**：不同拓扑的收敛时间、控制帧和工作集；
3. **压力模型**：全体节点高负载、故障、入网风暴；
4. **少量实机多跳**：校准每跳延迟和吞吐损失；
5. **目标规模实机/混合台架**：加入真实 RF、CPU、ISR、功耗；
6. **产品限制签字**：给出支持节点、活跃 Route、Hop、业务速率，而不是引用 Wire 最大值。

## Cluster 在大规模中的作用

Cluster 可把成员、Authority、目录和跨簇 Locator 分层，减少“所有节点维护所有节点”的需求。但 Cluster 不是普通路由必须条件，也不会自动把一个不稳定共享无线网变成万级可靠网络。其成熟度、默认关闭组件和发布门禁以 Cluster 专章为准。

## 发布参数清单

产品规格至少应同时公布：

- Wire Profile 和 Node ID 范围；
- 每 Node 最大 Link/Neighbor/Route/Candidate/Path/Flow 数；
- 最大与推荐 Hop；
- 支持的并发 Transfer/Service；
- 典型与最坏业务速率；
- 路由发现和故障恢复时间；
- 测试拓扑、介质和 MCU；
- 超出容量时的失败行为。

只有这组参数一起给出，读者才能判断“网络最多支持多少节点”在具体产品上的真实含义。
