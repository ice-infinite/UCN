# 32 B～8 KiB 可靠传输

## 1. Message Class

v6 定义 32、64、128、256、512 B、1、2、4、8 KiB 九档消息上限。档位是调用方声明的最大
业务对象容量，不等于单个物理帧。实际能否发送由本地 Profile、对端 Capability、Path Frame
MTU、安全开销和 Fragment 头共同决定。

Nano 默认最高 256 B，Lite 最高 2 KiB，Full 最高 8 KiB。所有 Profile 都能解析 Transfer
控制帧和合法 Wire，只是低档节点会在能力协商时明确拒绝超过本地容量的新 Transfer。

## 2. 精确 Payload Budget

`path_frame_mtu` 是 UCN frame 上限，Carrier MTU 是底层一次承载上限，两者不得混写。
`max_payload(path, frame_contract, security_suite, address_class)` 必须扣除地址、扩展、CRC、
Hop/E2E Tag 和 Transfer Fragment 头。不能用固定“MTU-常数”跨 A0～A3 或不同 suite 分片。

## 3. Selective Repeat

发送端先 `send_begin()`，再由 `next_fragment()` 取得窗口内未发送或待重传片段。只有 Adapter
确认提交后才 `record_fragment_submit()`；SACK 只确认对应 Transfer/Binding/Session/Path
Generation 的片段。窗口、位图和重试次数均有编译期上限。

接收端按 offset/length/fragment index 写入固定重组槽，重复片不重复计数，重叠、越界、总长
变化或摘要错绑立即拒绝。全部片段到齐后才暴露 completed view，业务消费后显式 retire。

## 4. Credit 与流水线

Credit 表示某 Link/Peer 当前允许占用的接收与队列预算，不是全网带宽承诺。发送前 reserve，
提交或取消后 finish；Session/Path reopen 会使旧 reservation 失效。多跳吞吐只有在各跳拥有
独立缓冲和窗口、能够流水转发时才不会天然按 `1/hops` 降低；单缓冲停等或半双工共享介质
仍会接近 1/n。

## 5. 可靠性边界

Transfer 保证片段重组和确认，不等于业务副作用 exactly-once。Request/Result 的重复执行由
Operation Journal 处理。链路断开、Credit 耗尽、超时和重试耗尽必须返回确定结果；不能无限
重试，也不能用增大缓存掩盖 Owner 或 Bearer 吞吐不足。
