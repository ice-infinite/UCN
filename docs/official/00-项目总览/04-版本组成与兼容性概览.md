# 版本组成与兼容性概览

> 文档级别：`NORMATIVE`
> 实现状态：`CURRENT`
> 最近核对：`a093862`，2026-08-25

UCN 不能只用一个“v5”判断兼容性。至少要分别核对以下层级：

| 层级 | 当前值/状态 | 影响 |
| --- | --- | --- |
| 项目/库版本 | `5.0.0`，由 `ucn_version()` 返回 | 发布和源码基线 |
| Core Wire | `UCN_PROTOCOL_VERSION=5` | 普通 UCN 帧是否能互解 |
| Core Wire Profile | W0/W1/W2/W3 | 字段宽度、头长度、MTU 和表示范围 |
| Port API | `UCN_PORT_OPS_API_VERSION=2` | Port 对象布局和全量重编译 |
| Cluster Current Wire | format v3，32 B | 默认 `ucn_cluster` 控制面兼容 |
| Cluster API | `UCN_CLUSTER_API_VERSION=2` | opaque object/storage 与调用方源码 |
| Cluster Wire v4 | format v4，40 B | 独立 Codec/实验体系，不能当作 Current v3 |
| Cluster Persist Record | 以当前 `ucn_cluster_persist.h` schema 为准 | Flash/NVM 升级与恢复 |
| 实验组件 API | 由显式 CMake Feature 和头文件门禁控制 | 默认产品不自动获得这些符号/行为 |

## 兼容判断顺序

1. 双方 Core Wire version 是否一致；
2. 接收端允许的最大 Wire Profile 是否覆盖发送档；
3. 地址、Hop、Cost、Payload 等字段能否在该档表达；
4. 双方 Feature/Profile 是否具有对应高级行为；
5. Cluster/Transfer/Service 等可选组件是否同时启用且协议一致；
6. API/ABI/Storage 变化是否已全量重编译或迁移。

低 Build Profile 可以解码高 Wire Profile 的普通 Endpoint 帧，但不会因此获得未编译的 Path、Policy 或诊断功能。Wire 解码兼容和 Feature 行为兼容是两件事。

Cluster Current v3 与 Wire v4 也不是自动混跑关系。dual-stack 只存在于明确的独立 Archive/测试边界，不能因为仓库有两个 Codec 就宣称默认产品可混跑。

## 1. 为什么会同时存在多个版本号

UCN 将版本拆开，是为了避免改一个平台接口就被迫修改线上 Wire，也避免只改持久化布局却让网络中的所有节点同时升级。

例如 Port API 从旧结构升级到 v2，影响的是应用如何提供 ISR/task 回调和结构体布局；普通 Core Frame 的线上格式仍可以保持 Wire v5。相反，Cluster Wire 从 v3 设计到 v4 会改变固定帧长度和 Type 语义，但不必改变 Core Wire v5。

```text
项目版本 5.0.0
├─ Core Wire v5
│  └─ W0/W1/W2/W3
├─ Port API v2
├─ Node Storage layout v5
├─ Cluster API v2 / Storage layout v2
├─ Cluster Current Wire v3
├─ Cluster Target Wire v4
└─ Cluster Persistence Record v4
```

## 2. 四类兼容性

### 2.1 Wire 兼容

Wire 兼容回答：“两个已经烧录的节点能否互相解析线上字节？”它取决于版本、长度、字段合法域、Capability 和安全模式。Wire 不兼容通常表现为 `UCN_ERR_VERSION` 或 `UCN_ERR_MALFORMED`，不能靠结构体强转解决。

### 2.2 API 兼容

API 兼容回答：“旧源代码包含新头文件后是否还能编译？”函数重命名、参数变化或公开字段变化都可能破坏 API。

### 2.3 ABI 兼容

ABI 兼容回答：“用旧头文件编译的对象能否与新静态库链接并正确运行？”即使函数名没变，结构体大小、字段顺序和调用约定变化也会破坏 ABI。UCN 当前仍处于发布前优化阶段，破坏性结构升级要求全部对象重新编译。

### 2.4 Storage 兼容

Storage 兼容回答：“新固件能否读取设备 Flash 中的旧记录，旧固件能否回读新记录？”它与网络 Wire 完全不同。Cluster Record v4 可以读取某些旧 schema，不表示刷回旧固件一定安全。

## 3. Core Wire Profile 的协商逻辑

W0～W3 不是四个独立协议，而是 Core Wire v5 下的字段宽度等级。发送方先根据目标地址、Cost、Hop、Payload 和可选字段计算最低够用档，再与本地发送上限、远端接收上限和当前 Link MTU 求交。

概念流程：

```text
required_profile = 能表达当前帧全部字段的最低档
allowed_profile  = min(本地TX上限, 远端RX上限, 路径能力)

required_profile <= allowed_profile ? 发送 : 明确失败
```

协议禁止为了发出去而截断高位 Node ID、Cost 或其他字段。

## 4. Build Profile 为什么不是 Wire 协商

Build Profile 是本地裁剪。Lite 没有 Path/Policy 状态机，但可以接收一个 W3 普通 Endpoint Frame；随后它仍只执行自身编译的 Endpoint/Route 能力。如果 Frame 类型要求未编译功能，应按功能门禁拒绝，而不是因为 Wire 解码成功就假装支持。

## 5. Cluster v3/v4 的特殊边界

Current v3 固定 32 B，Target v4 固定 40 B。严格 dispatcher 只有在“版本与精确长度同时匹配”时才分派：

| 输入 | 结果 |
| --- | --- |
| v3 + 32 B | 可进入 v3 decoder |
| v4 + 40 B | 可进入 v4 decoder/实验接口 |
| v3 + 40 B | 拒绝 |
| v4 + 32 B | 拒绝 |
| 未知版本或 31/39/41 B | 拒绝 |

当前默认产品仍只把 v3 接入生产 FSM。Host dual-stack 测试证明两个 Codec 不互相误解，不代表生产节点已经能用 v4 参与 Join、Config 或 Authority。

## 6. 升级示例

假设产品从旧 Port 结构升级到 Port API v2，但保持 Core Wire v5：

1. 修改 Port 初始化为具名字段，并填写 `struct_size/api_version`；
2. 实现独立 task/ISR 临界区与通知；
3. 清理所有旧 `.o/.a` 并全量重编译；
4. 线上其他 Wire v5 节点可以不因 Port API 变化而升级；
5. 若同时修改产品配置导致 Frame/Capability 变化，再单独评估 Wire 兼容。

## 7. 失败处理原则

- 不认识的 Wire 版本：拒绝，不降级猜测；
- 结构体版本/大小不匹配：初始化失败，不读取新增字段；
- Storage schema 损坏或未知：fail-closed，不把全零当 Factory Empty；
- Profile 没有共同能力：返回配置/状态错误，不截断；
- 回滚目标无法理解新 Record：先隔离网络并执行明确迁移或擦除流程。
