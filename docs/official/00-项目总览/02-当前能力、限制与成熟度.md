## 1. 如何阅读“当前实现”

本表中的“实现”只表示仓库里存在对应源码、公共或受限接口，并且有一定软件测试。它不自动包含以下结论：

- 所有 Build Profile 都编译了该功能；
- 功能默认链接进产品；
- 已经在所有 MCU、RTOS 和 Bearer 上运行；
- 已完成生产安全或掉电验证；
- API 和 Wire 已经对外承诺长期稳定。

因此 UCN 使用四个维度描述成熟度：

| 维度 | 需要回答的问题 | 典型证据 |
| --- | --- | --- |
| 代码存在性 | 源码和 API 是否存在 | 公共头、source list、符号表 |
| 默认启用性 | 默认产品是否会链接和执行 | CMake 默认值、生产引用扫描 |
| 软件验证 | 定义范围内行为是否通过测试 | CTest、negative、fuzz、sanitizer |
| 产品验证 | 真实硬件和故障条件是否验收 | 固件 hash、接线、日志、掉电/长稳报告 |

只有四个维度都满足对应发布清单时，才能写“生产就绪”。

## 2. Core 当前能完成的闭环

### 2.1 两节点直连

产品注册 Link 和 Endpoint 后，节点可以通过预配置直连 Route 或一跳 Neighbor 发送普通 Frame。Node 负责版本、长度、Hop、队列、重复抑制和 Endpoint 分发；Adapter 负责把 Frame 送入真实驱动。

### 2.2 Lite/Full 动态组网

Lite/Full 使用 HELLO 建立一跳 Neighbor，用 Heartbeat 维护存活。当目标不直连且 Route Cache 没有有效项时，AODV-Lite 发起有界 RREQ/RREP；链路断开后 RERR 使相关 Route 失效并触发后续重寻路。

### 2.3 Full 多路径策略

Full 在基础 Route 之外增加 Candidate、显式 Path、Policy 和本地动态 effective cost。应用可以选择自动最优、严格固定、断链回退或仅对 Q1 开启负载均衡。

### 2.4 任务和大消息

Service 让同一 MCU 任务和远端 MCU 使用相同 Service ID/Operation 语义；Transfer 在 Core 轻量 Frame 上提供 T32～T8K 分片、重组、ACK 和 CRC32。二者都是可选组件，不使用时不会强迫 Core-only 产品承担全部静态 buffer。

## 3. 各成熟度层的准确口径

### 3.1 当前默认能力

Core Wire v5、Node、Link、Endpoint、Adapter Queue 和所选 Profile 的功能属于默认代码路径。默认 Full 构建会包含 Dynamic Mesh、Path、Policy 和 Diagnostics；Nano/Lite 会按 Profile 裁剪。

### 3.2 可选但已形成软件合同

Service、Transfer、Stream Source、CAN Source、各 Port 外壳、Security Provider 接口和 Cluster Current 属于可选 target 或配置。它们有源码和测试，但产品只有在明确链接、配置并完成 BSP 后才真正具备该能力。

### 3.3 隔离实验能力

Cluster Wire v4 codec、M07～M09 组件以及 M10/M11/M13 Archive 属于 Target/实验层。尤其需要注意：

- v4 decoder/semantic test 通过不等于生产 RX 会消费 v4；
- encoder 默认关闭，普通产品不会发 v4；
- 实验状态机可能要求调用者提供测试中的冻结 Config/Persistence 对象；
- M10/M11/M13 CMake 默认 OFF，不属于默认 `ucn_cluster` archive。

## 4. 已有证据能证明什么

- 单元和集成 CTest 证明固定输入、状态转换、拒绝路径和模块联动符合当前测试合同；
- Full/Lite/Nano 与 Service-OFF 构建证明主要 Feature 组合可以独立编译和运行对应测试；
- ASan/UBSan、`-fanalyzer`、Release 和 deterministic fuzz 提高了内存、未初始化、优化差异和 malformed 输入的覆盖；
- Host 规模模拟证明在给定拓扑、容量、seed、流量和理想化链路模型下能够收敛；
- ESP32-S3 多板 UART/部分 ESP-NOW 历史实测证明指定固件、接线和场景下的真实收发与多跳 Transfer 能运行。

这些证据都是“带条件的证明”。例如四板 UART 三跳结果不能推导出四节点 ESP-NOW、CAN-FD、BLE 或 24 小时长稳也已经通过。

## 5. 尚缺的产品证据

### 5.1 MCU 资源

Host 的 `sizeof`、archive text 和静态 frame 用于回归趋势，不代表 ESP32、STM32 或其他 MCU 的最终 RAM/Flash/Task Stack。产品必须使用真实编译配置记录 map、high-water 和峰值。

### 5.2 物理介质

仓库 Source 的软件测试覆盖 COBS、Classic CAN carrier、CAN-FD padding 等合同；真实控制器的 DMA、FIFO、Bus-Off、过滤器、无线拥塞和掉线恢复仍需具体 BSP 实测。

### 5.3 安全

Provider 合同和测试密钥只能证明协议调用顺序。生产密钥存储、硬件随机数、AEAD 实现、序列持久化、密钥轮换和攻击面审计仍属于产品门禁。

### 5.4 Cluster 持久化和 Target FSM

Persistence mock/record 测试不能替代真实 Flash 双槽、擦写中断和掉电。Wire v4 Target 还缺默认生产 RX/TX/FSM/Authority 接线，因此整体保持 `AUDIT HOLD / RELEASE NO-GO`。

## 6. 仍不能宣称

- 所有 RTOS 和所有 MCU 已完成可编译、可烧录和资源验收；
- Wi-Fi/ESP-NOW/CAN/USB 等真实 Driver 已由 UCN 自动配置；
- 安全体系已经达到生产密钥和抗攻击要求；
- 多 Bearer 切换在所有在途数据下零丢失、零抖动；
- Cluster Wire v4 Target FSM 已完成默认产品接线；
- 真实 Flash 撕裂写、可控掉电、长稳、功耗和 EMC 已全部验证。

## 7. 判断一个功能能否用于产品

以“我要在 STM32 + FreeRTOS 上通过 CAN 发送 T2K 消息”为例，不能只查到 Transfer 支持 T2K 就结束。应依次确认：

1. 当前 Profile/Feature 是否链接 Transfer；
2. 静态 TX/RX slot 是否满足并发和 RAM；
3. CAN Source 与真实控制器 BSP 是否接好；
4. 当前 CAN/Path MTU 是否会触发正确分片；
5. Owner Task 是否满足 step/ACK deadline；
6. 目标板压力、Bus-Off、重连、长稳和资源是否有证据；
7. 如果消息敏感，生产 Security Provider 是否完成。

只有这一条链路全部闭环，才能对该**具体产品配置和场景**写“可用”。每个“已完成”都应回到对应官方专题和 [`evidence/`](../../evidence/README.md) 查看版本、配置和限制。
