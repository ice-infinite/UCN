一句话定义：**UCN 是面向 MCU 的 C99 静态通信与自组网核心，用统一的 Node/Link/Endpoint 语义屏蔽 UART、CAN、Wi-Fi 等承载差异，并通过可选 Extended 组件扩展大消息和 Cluster 控制面。**

## 阅读后应能回答的问题

- 没有 Linux 时，多个 MCU 能否独立发现和多跳通信；
- UCN 与 UART、CAN、Wi-Fi Mesh、ROS 2 等体系各自负责什么；
- 一个节点上的多种传感器数据如何区分；
- “发送成功”“Transfer 完成”“业务执行完成”有什么区别；
- Nano/Lite/Full、W0～W3、Core Wire v5、Cluster v3/v4 分别是什么；
- 为什么源码存在不等于功能默认启用或已经可以发布。

## 事实边界

本目录给出当前源码的高层解释。精确 API 以公共头为准，默认启用性以 CMake 为准，实测结论以 evidence 中绑定 commit/硬件的报告为准。历史建议和审计材料只用于追溯，不能覆盖本目录的当前状态。

## 从问题到模块的对应关系

第一次接触 UCN 时，可以先从实际问题定位后续章节：

| 实际问题 | UCN 中负责的模块 | 不由该模块负责的内容 |
| --- | --- | --- |
| 同一 MCU 的任务如何交换传感器和控制消息 | Endpoint、Service、本地派发 | RTOS 调度策略和具体任务优先级 |
| 两个 MCU 如何通过 UART、CAN 或无线互通 | Link、Adapter、Port、Node | 芯片 SDK 初始化、引脚复用和电气设计 |
| 不知道目标在哪时如何找到并转发 | Neighbor、Route、Path、Policy | 互联网级 BGP、全局一致路由表 |
| 大于单帧的数据如何可靠交付 | Transfer 分片、累计 ACK、重组 | 业务对象序列化格式和数据库事务 |
| 同一目标存在多条链路时如何选择 | Cost、Candidate、Q1 Path、负载策略 | 未提供 Metrics 时凭空判断物理质量 |
| 大规模节点怎样降低平面控制开销 | Cluster、Federation、持久化模型 | 当前默认产品已经放行 Wire v4 Cluster |
| 如何防监听、篡改和错误降级 | Security Policy 与 Provider 接口 | 仓库内置生产密钥体系或认证基础设施 |

这张表的重点是区分“UCN 给出统一协议语义”与“产品仍须提供的驱动、密钥、存储和调度实现”。例如 UART 已有通用 Stream Source 和 Carrier，不代表库会替产品选择 UART 控制器或配置 3 Mbaud。

## 建议的理解顺序

先建立三个层次，再阅读细节：

1. **承载层**解决字节怎样进出芯片，包括 UART、CAN、Wi-Fi、USB 以及它们的 Driver Ring 和 Adapter。
2. **网络与传输层**解决节点、端点、路径、队列、分片、重试和错误传播，使业务不必针对每种承载重写一套通信流程。
3. **控制与治理层**解决策略、安全、诊断以及可选 Cluster；这些能力有各自的启用条件和成熟度，不能因为源码存在就默认生效。

阅读任何能力时都应继续追问四件事：它是否编入当前 Profile、是否默认启用、是否接到生产数据路径、是否有与目标硬件一致的证据。四个答案缺一，都不能直接扩大为产品承诺。

## 本目录不替代什么

项目总览用于建立共同语言，不替代 API 参数说明、Wire 字段表、状态机不变量或测试报告。需要写代码时应继续进入对应专题；需要作发布决策时必须回到[兼容、迁移与发布](../13-兼容、迁移与发布/README.md)和[测试与一致性](../12-测试与一致性/README.md)，逐项检查仍在 `AUDIT HOLD` 或 `RELEASE NO-GO` 的边界。
