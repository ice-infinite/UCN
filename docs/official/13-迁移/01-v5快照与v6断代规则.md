# v5 快照与 v6 断代规则

## 1. 历史保存

v5 最后实验快照为提交 `c554239f0940d77a0a0a3baef81c6742be1a0c90`，保存于分支
`v5-final-experimental` 和 Tag `v5.0.0-experimental-final`。它不是生产发布，也不会继续在
v6 当前树中维护。旧用户资料位于 `docs/archive/v5-user-facing-20260905/`。

## 2. 明确不兼容

v6 不兼容以下 v5 资产：

- Core Wire v5、W0～W3、Cluster v3/v4 和双格式 dispatcher；
- 旧 Node/Transfer/Realtime/Cluster 公开结构体 ABI；
- 旧 Record schema、legacy PREPARED abort 和自动迁移；
- 旧 CMake Profile/Feature/compatibility 开关和 target；
- 通过 Stub 保持“符号存在但返回 CONFIG”的兼容方式。

旧输入仍有负向测试，目的是明确拒绝，不是降级处理。

## 3. 产品迁移

从 v5 迁移到 v6 应视为换协议固件：先停止网络，保留可回滚的 v5 镜像和持久介质备份，刷入
v6 后用新的 Product Manifest 初始化独立存储。不能让 v6 直接 decode v5 Record，也不能在
同一 Realm 混跑并期待自动协商。

若产品必须现场迁移业务数据，应编写离线、单向、可审计的产品工具：读取 v5 备份、验证
完整性、转换允许的非安全业务配置、生成全新的 v6 record。Binding Generation、Session、
Key、Replay、Vote、Authority、Realtime generation 等安全状态不得直接复制。

## 4. 回滚

回滚到 v5 只能恢复与该 v5 固件匹配的完整 v5 存储快照，并与 v6 Realm 隔离。已在 v6 发布
过的 Address/Group/Key Generation 不能通过回滚再次使用。生产系统应采用分区、Realm 或
后端 Authority Fence 防止两个版本同时声称相同身份。

## 5. 当前分支规则

`v6-development` 不允许重新加入可编译的 legacy/archive 源码。需要查旧实现时使用 Git
分支/Tag；Compatibility Removal gate 会拒绝当前 `src/`、`include/ucn/`、`tests/` 和
`tools/` 中的非 v6 发布资产。
