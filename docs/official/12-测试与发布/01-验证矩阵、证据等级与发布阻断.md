# 验证矩阵、证据等级与发布阻断

## 1. 软件矩阵

最小发布软件矩阵包含 Full Debug/Release、Lite Debug、Nano Debug、Nano Feature-Off；每项
都运行完整可用 CTest，而不是只编译。额外运行 ASan/UBSan、GCC `-fanalyzer`、Clang
`-Wall -Wextra -Werror`、中文构建目录、安装树外部消费者和 v6-only denylist。

`v6_source_boundary_gate` 检查运行时无 heap、无旧头、无旧源码/测试/工具、无旧 CMake 开关、
模块依赖和 Bearer 文件；安装门禁真正执行 install，再由独立 CMake 工程
`find_package(UCN 6 CONFIG REQUIRED)` 并链接 `UCN::ucn`。

## 2. 模型和负向

每个状态机不仅验证成功路径，还要验证输出不写回、半提交回滚、过期边界、错误代际、重放、
容量、callback 重入和 Provider 假成功。Wire 使用精确 golden 与固定 seed fuzz；Journal、
Route、Transfer、Realtime、Cluster 覆盖重启/乱序/重复/超时。规模模拟用真实 Owner/Store，
但 Host 可为创建多个逻辑节点使用堆，不能混入生产 archive。

## 3. 硬件证据

每份实机 PASS 必须绑定 40 位 commit、固件和日志 SHA-256、板号、芯片/SDK/编译器、供电、
接线、引脚、速率、Bearer、开始/结束时间和阈值。至少覆盖：多跳吞吐和尾延迟、Q0～Q3、
32 B～8 KiB、断链/reopen、队列满、丢包/乱序、ISR/DMA、Flash 掉电、CPU/栈/RAM、功耗与
24 小时长稳。

不同 Evidence Level 不能互相替代：Host 假驱动不证明 UART，UART 不证明 ESP-NOW，单跳不
证明多跳，平均值不证明 P99/P999，软件重启不证明撕裂写。

## 4. 发布阻断

以下任一项存在即不得生成 1.0 RC：

- Compatibility Manifest 仍有 PENDING；
- P0/P1 外审问题未关闭；
- required Profile/Feature/编译器矩阵失败；
- 安全 Suite/Key/ACL/随机数仍是测试 fake；
- 目标产品所需 Bearer、掉电、资源、性能或长稳证据缺失；
- 文档仍引导旧 API，安装包含旧头/符号/target；
- 证据不绑定同一候选 commit 或 artifact hash 不符。

## 5. 当前状态

V6-15 已把源码和构建发布面切为单一 v6，MSVC 软件矩阵也已通过；当前仍需要补真实
ESP32-S3/CAN/USB/Flash、Realtime hardware timestamp、长稳与有效 TSan。故只能声明软件自审结果，不能标记
release-ready。详细当前数字见 V6-14/V6-15 实现报告和任务表。
