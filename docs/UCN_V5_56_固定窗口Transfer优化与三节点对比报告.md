# UCN V5-56 固定窗口 Transfer 优化与三节点对比报告

> 日期：2026-08-14
> 状态：代码、Host 软件回归和三块 ESP32-S3 的 3,000,000 baud UART 两跳重复实测已完成。
> 台架：A=COM5/ESP32-S3-N16R8，B=COM34/ESP32-S3-N16R8，C=COM38/ESP32-S3-N8R8；A—B—C 两段 UART，ESP-NOW 同时在线；A→C 路由为 2 Hop/Cost 68。

## 1. 优化目标与结论

V5-55 的 3M 基线使用严格 Stop-and-Wait：每发一个 Fragment 都必须等该片 ACK 后才能发下一片。在线路位速率继续提高时，两跳转发、协议循环和 ACK 往返成为主要空洞，3M～5M 吞吐几乎不再增长。

V5-56 在不改变 v5 Wire 格式、不增加动态内存、不让中继重组的前提下，增加了**显式协商的有界固定窗口**：

- 默认本机窗口仍为 1；未声明能力的旧对端也按 1 处理。
- 当前编译默认最大窗口为 4，只有本机和对端都显式允许时才实际使用 2～4。
- ACK 仍是现有 8 B 载荷，`next_expected_offset` 解释为累计 ACK；没有新增线上字段或协议版本。
- 接收端继续严格顺序、零乱序缓存；出现缺口时回 ACK 当前连续偏移。
- 发送端对缺口或超时执行有界 Go-Back-N，从已确认偏移重发当前窗口；仍受既有重试次数和消息绝对 Deadline 限制。
- 窗口只增加少量偏移/状态字段，不为每个在途 Fragment 复制 Payload。

三轮最终固件结果：T128～T8K 共 21/21 阶段完整交付，0 Fragment 重试、0 CRC/COBS/长度/溢出/no-space/partial 错；七个可靠等级的等权平均有效吞吐由 **12.523 KiB/s 提升到 19.121 KiB/s，提升 52.7%**。T8K 由 14.041 提升到 24.750 KiB/s，端到端确认时间由 570.3 ms 降到 323.3 ms。

## 2. 实现和兼容策略

新增公开配置/API：

```c
#define UCN_TRANSFER_MAX_WINDOW ((uint8_t)4U)

ucn_transfer_set_tx_window_size(&transfer, 4U);
ucn_transfer_set_peer_window_capability(&transfer, peer_node_id, 4U);
```

初始化后的运行期窗口固定为 1。产品必须先用 `ucn_transfer_set_peer_capability()` 建立对端 Class 能力，再显式设置对端窗口能力。只设置本机窗口、不设置对端窗口时，有效窗口仍为 1，因此不会主动向旧 v5 Transfer 对端流水发送。

`ucn_transfer_config_t` 没有插入新字段，旧位置初始化继续可编译。窗口设置在 TX Slot 空闲时才允许修改；存在活动发送时返回 `UCN_ERR_ACCESS`，避免半条消息改变可靠性语义。

当前没有把窗口能力塞入 HELLO，也没有自动推断。这样避免改变已部署 v5 控制帧；代价是产品当前需使用静态配置、受控目录或应用层能力交换。未来若做自动协商，必须作为可选扩展单独完成旧 v5 互通测试。

## 3. 公平对比方法

两组都使用相同板卡、接线、3M UART、A→B→C 两跳、Cost 68、相同九档各 8 KiB 业务量和后台 Heartbeat/Ping：

- 基线：V5-55 原始窗口 1 固件，3 个正式日志。
- 优化：最终 API 兼容版本窗口 4 固件，重新完整写入三块板后采集 3 个正式日志。
- T32/T64 继续走无端到端 ACK 的 Direct 路径，只作观察，不并入可靠吞吐平均。
- T128～T8K 使用 Fragment/累计 ACK，要求远端实际收到 100%、内容/CRC 正确且 Completion 成功。

T128 只有一个 Fragment，没有可流水的后续片，所以窗口没有收益；本轮约 4% 波动属于调度/控制流样本差异。T256 开始出现收益，T1K～T8K 稳定为约 1.66～1.82×。窗口 4 不是把 UART 位速率提高 4 倍，而是减少 ACK 往返造成的空洞。

Direct T32/T64 的三轮平均交付率分别为 99.609% 和 98.177%，仍不是可靠消息。固定窗口只作用于 T128～T8K，不改变 Direct 的语义。

## 5. 故障恢复与软件门禁

专项虚拟 Link 覆盖：

1. 本机窗口 4、对端未显式允许时退化到窗口 1，峰值在途片数为 1。
2. 窗口 4 丢失 START Fragment：接收端无 Slot 时累计 ACK 0，发送端有界回退并最终只交付一次。
3. 窗口 4 丢失中间 Fragment：后续乱序片不缓存，接收端回连续偏移，发送端 Go-Back-N 后恢复。
4. 活动 TX 中修改窗口被拒绝；非法 0、超编译上限和未知 Peer 均失败关闭。
5. 旧 `ucn_transfer_config_t` 位置初始化与新 API 公共符号均进入链接测试。

验证结果：

- Windows Full/Lite/Nano：各自 `1/1` 通过。
- 512 B 最大消息、2 RX Slot、最大窗口 2 的低资源产品配置：`5/5` 通过。
- WSL Ubuntu 24.04 GCC 13.3 ASan+UBSan+Leak：`1/1` 通过。
- GCC `-fanalyzer`：构建和 `1/1` 通过。
- 三目标 PlatformIO 最终窗口 1/窗口 4 均重新构建成功。

## 6. 固定资源变化

相对 V5-55 优化前固件，最终窗口 4 固件的 PlatformIO 静态资源为：

| 节点 | 优化前 RAM/Flash | 优化后 RAM/Flash | 变化 |
| --- | ---: | ---: | ---: |
| A / N16R8 | 63,756 / 602,631 B | 63,788 / 603,159 B | RAM +32 B，Flash +528 B |
| B / N16R8 中继 | 48,756 / 596,127 B | 48,756 / 596,163 B | RAM +0 B，Flash +36 B |
| C / N8R8 | 55,796 / 598,431 B | 55,828 / 598,887 B | RAM +32 B，Flash +456 B |

A/C 日志中的 `sizeof(ucn_transfer_t)` 从 8672 B 变为 8700 B，增加 28 B；大块占用仍来自已有 8 KiB RX/TX 产品缓冲，并非窗口复制。最终三轮最小 Heap 与基线同量级：A 294,480～294,536 B、B 309,564 B、C 304,540 B；没有重启、Panic 或 Watchdog。

同一份优化后源码仅把运行期窗口从 1 改为 4 时，三板静态 RAM 完全相同，Flash 仅有 -8～+4 B 的 LTO 常量差异。窗口大小不会按 4 倍增加 Payload RAM。

## 7. 实机稳定性和边界

- 最终三轮可靠等级 21/21，窗口峰值均为 4，Recovery=0；说明正常台架确实形成流水，不是仍按窗口 1 运行。
- 三轮 UART Wire 错均为 0；Queue Drop 总数为 5/5/6，对比基线 7/7/6，没有因窗口 4 恶化。
- 背景 Ping 持续运行，但个别轮次 A/C 为 49～50/50～51，最大累计 RTT 约 120 ms；这仍不是 Q0 严格时延门禁。
- 本报告只证明短线 3M UART 两跳。尚未覆盖有损无线、Bearer 切换中 Transfer、多发送源、窗口 2/3 的实机权衡、硬件流控、长线/EMC/温漂、CPU%、功耗和真实 RTOS 调度抖动。
- 当前恢复是 Go-Back-N，不是 Selective Repeat；窗口内一个缺口可能重发已经收到的片。窗口 4 是 MCU-first 的受控折中，不建议在没有压力和丢包数据时盲目继续增大。
